# DIUCS (overwatch)

Mission: get this product developed, verified and finished to a high quality. The lead developer works autonomously and is the only developer; there is one long-lived branch, `main`.

- **Start every session, and re-run after any context compaction or summary, by invoking the `diucs-delivery` skill** (`.claude/skills/diucs-delivery/SKILL.md`). It holds the rules: the ledger, evidence, independent verification, tenancy (DEC-130 to DEC-134), and the autonomy rules (DEC-133: no human gates; ask the owner only if genuinely stuck).
- Decisions are in `docs/delivery/decisions.md` and override the specs and the task prompts.
- `main` is the only long-lived branch. Task branches are short-lived; fast-forward into `main`, push `main` rarely (the owner's request, 2026-10-28: pushes were billing GitHub Actions): at most once per wave of deliveries, or when asked, and never a push per commit, delete the task branch.
- Neo4j tests run in parallel on one shared Neo4j, each run in its own tenants: there is no lock to queue on (TEN-033 to TEN-035). The container `diucs-test-shared-neo4j` is started on demand and kept (`make neo4j-shared-down` removes it); `DIUCS_TEST_NEO4J=owned` gives one private container per run, `DIUCS_TEST_NEO4J_URI` (+ `_USER`, `_PASSWORD`) attaches to another instance. From `backend/`: `uv run pytest <paths>` for your own files, `make test-integration` for the whole integration and contract suites (the parallel phase `-n 4 -m "not exclusive"`, then the exclusive phase `-m exclusive`), `make test-parallel` for everything. What runs alone, by marker: `exclusive` (the Service Bus emulator, the compose stack, anything that must not share the machine) runs in a session of its own after the parallel phase and waits for other runs to finish; `schema` and `lifecycle` tests use a private container (`own_neo4j`), which the harness lock starts one at a time. Never wrap pytest in a `flock` any more, and never `wipe_all` the shared database (a run wipes only its own tenants).
