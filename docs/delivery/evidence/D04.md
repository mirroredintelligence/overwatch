## Decisions and assumptions
- **DEC-023** (committed before the first red commit): `current_due` searches back 8 days, not only today and yesterday as the prompt says. The prompt's version returns None on a Monday before 08:00 for a weekday-only service that was due on Friday evening, which loses the overdue state for D05 and D07. Verifier confirmed this reading under domain-rules 1.5.
- **DEC-024** (committed before the second red commit): 14:00 is a due time whenever the window opens at or before 14:00. This follows domain-rules 1.4, the only exception there being "opens after 14:00". The prompt's extra exception "or closes at or before 14:00" is dropped, and so is the plain-time check `start < 14:00 < end`, which broke overnight windows. Consequence: a window that ends at 12:00 gets a 14:00 due while the service is closed. Missing a due is the larger risk, so the rule book wins. The owner can change this by amending the rule book.
- **[ASSUMED]** alignment and the 14:00 second slot from domain-rules 1.4, held as the named constant `TWICE_A_DAY_SECOND`.
- **Spring-gap collision:** on 2026-03-29, a local 01:00 (absent from the clock) maps to 01:00Z, the same instant as local 02:00. The due list keeps one instant, so there are no duplicates.
- **every-2-hrs window end:** the closing time is included (prompt wording). domain-rules 1.4 says "up to its end". Both give 20:00 for 08:00 to 20:00.
- **next_due** returns None only if no due time falls in its search; for any valid profile it does not.
- DEC-023 and DEC-024 numbers may collide with other unmerged branches. The orchestrator renumbers at delivery.
