## Decisions and assumptions
- DEC-010 stub in the red commit: type definitions plus a `NotImplementedError` body. No behaviour.
- Only ASCII is recognised. Input is first normalised (trim, collapse whitespace); any non-ASCII remainder is unrecognised. Reason: Python's `upper()` maps dotless `ı` to `I` and long `ſ` to `S`, so `CONFıRMED` and `YEſ` would otherwise be read as keywords. Fullwidth and Arabic-Indic digits are rejected for the same reason. This is my choice and goes beyond the prompt; the prompt does not forbid it.
- Figure digits: leading zeros are stripped before the length check, so arbitrarily many leading zeros are accepted and values above 999 are rejected without converting huge integers.
- Reference length 3 to 8 digits follows the prompt. Note that DEC-007 says references are generated as 4 digits; the parser accepts 3 to 8 as the prompt says, and the generator (a later task) decides the length.
- Parser does not know the prompt, as the prompt says; `1` after a decline is `Number(1)`.
- Prompt wording differences: none material.
