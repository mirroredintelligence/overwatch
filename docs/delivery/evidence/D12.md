# Evidence: D12 Report flag rules

Builder: build-D12 · Branch: `task/D12-report-flags` · Prompt: `docs/plan/prompts/D12.md`

## Summary
`flags_for_report` raises `many-changes` (3 or more reports for one service within 5 minutes ending at the new report, counting the new one, edges inclusive) and `differs-from-phoned` (a new text or link figure differs from an advisor-phoned figure for the same service in the previous 60 minutes). Flags come back in rule order, each at most once. Every report time is converted to UTC before it is compared or subtracted, so London-zoned times across the 2026-03-29 and 2026-10-25 clock changes are measured in real elapsed time. `out-of-range-twice` is not produced here (D11).

**Resubmission.** The verifier passed `b5dba5a` with one finding; the coordinator treated it as blocking. This is a DST defect, not a boundary defect. Two London-zoned datetimes share one `tzinfo` object (`ZoneInfo` is cached), so Python subtracts and compares their wall-clock fields. Example: 00:58 GMT to 02:02 BST is 4 minutes of real time but reads as 1h04 on the wall clock, so a many-changes flag was missed. The autumn change and the phoned comparison fail the same way. The earlier clock tests used UTC input, which has no such problem, so they did not catch it. The fix converts every instant to UTC first. The module docstring and DEC-025 point 3 now say so.
