## Readiness tests (running state plus config healthcheck)
Two tests cover readiness. Neither runs `up --wait` itself.
- `test_every_compose_service_reports_healthy` runs `docker compose -f infra/docker-compose.yml ps --format json` and asserts the service set is exactly `neo4j, redis, servicebus-sql, servicebus-emulator, servicebus-ready`. It checks running state for all five. It checks `Health = healthy` for each service except `servicebus-emulator`. The emulator reports no health status of its own, so its readiness is gated by `servicebus-ready`, whose healthcheck calls the emulator's `/health` endpoint and is healthy only on HTTP 200.

## Service Bus retention
Messages are not kept when the stack is taken down (`down`), because `servicebus-sql` has no volume. Entities are recreated from `infra/servicebus-config.json` on each emulator start. A plain `docker compose restart` of the SQL container keeps its writable layer, so messages may survive that. That case was not tested.

## Decisions and assumptions
- **DEC-008 applied.** `infra/docker-compose.yml` is for local use. `test_infra_up.py` connects to that stack on purpose, because it proves the stack itself. It does not start its own containers. The shared harness (F10) will start its own Neo4j per run.
- **DEC-012 applied** as described above, with the one cross-driver exception.
- **Pinned versions** (checked against Docker Hub and MCR on 2026-10-24): Neo4j `5.26.32-community` (latest 5.x line); Redis `7.4.11-alpine`; Service Bus emulator `2.0.1` (newest pinned version; the `latest` tag was not used); SQL Server `2022-CU27-ubuntu-22.04`. Azure SQL Edge was not used: the current emulator documentation names SQL Server 2022 for its SQL container, and the default compose template in the emulator installer repository still shows SQL Edge. A reviewer may want to confirm this choice.
- **Emulator health.** The emulator image has no shell and no curl, so it cannot run a healthcheck. A probe container (`servicebus-ready`, same SQL image, which has bash) checks `http://servicebus-emulator:5300/health`. This is a deviation from the prompt's "healthchecks on every service" wording.
- **Credentials.** `MSSQL_SA_PASSWORD` defaults to `DiucsLocal-Only!2026` in compose and can be overridden through `infra/.env`. It is local-only. The emulator's SAS key is the documented static value `SAS_KEY_VALUE`.
- **Python client versions:** `neo4j` 6.4.1, `redis` 8.1.0, `azure-servicebus` 7.15.0, run under the Python 3.14 interpreter that `uv` selects for the project.
- **Duplicate detection on `inbound.replies`.** The window is `PT20S`, the minimum shown in the emulator documentation example. A second run of the queue test within 20 seconds fails, because the same message id is treated as a duplicate. This is in `infra/README.md` and lesson L6. The test keeps the prompt's `smoke-1` id. Observed queue results:
- Second verification (coordinator's run): 0 messages received about 20 seconds after the previous run's send. The next run, about 15 seconds later, passed. Measure the 20 seconds from the previous send, not from the previous run's end. The coordinator's figures are reported as observed and were not reproduced exactly here.
- My own reruns in the first fix: a rerun made within seconds of the previous passing run failed with 0 messages. A rerun after about 25 seconds passed.
- The F10 harness must use unique message ids for every test that sends to `inbound.replies`. `smoke-1` is kept only for this infrastructure smoke test.
- **Entity config** follows the emulator documentation structure (`UserConfig`/`Namespaces`). `DefaultMessageTimeToLive` is `PT1H`, the emulator maximum. `MaxDeliveryCount` is 10 on every queue and subscription (the prompt sets no value).
