## Finding 1: the first-start timeout is a password bug, not flakiness
Symptom (verifier, full run at `772ded2`): `test_harness_container_survives_stop_and_start_and_is_ready_again` raised `Neo4jNotRunning` after 120 s at its first start, before any stop. Re-running the two restart tests alone passed.

Root cause, reproduced:
- `start_throwaway_neo4j` set `NEO4J_AUTH=neo4j/<password>` with `secrets.token_urlsafe(16)`. That alphabet includes `-`, so the password starts with `-` in about 1 in 64 containers.
- Neo4j's entrypoint passes the password to `neo4j-admin dbms set-initial-password`. A leading dash makes `neo4j-admin` read it as an option. The container exits with code 64 and log line `Missing required parameter: '<password>'`. Reproduced by hand with `NEO4J_AUTH=neo4j/-abcDEF123`.
- `wait_until_ready` then polls `docker exec ... cypher-shell` against a stopped container. Every poll fails, and after the 120 s deadline it raises `Neo4jNotRunning`. The 120 s matches the reported timeout.
- Measured rate of a leading dash: 0.01545 over 200,000 samples of `token_urlsafe(16)`, against the expected 1/64 = 0.01563.

So the failure is intermittent (about 1 in 64 starts, which is why a rerun of the two tests passed) and deterministic once it happens. It is not a load problem. Ten idle starts took 10 to 13 s each. Five concurrent starts took 24 to 27 s each. Neither came near 120 s.

Fix: `new_container_password()` returns `secrets.token_hex(16)`, 32 lowercase hex characters, which never start with `-`. Test: `tests/unit/support/test_container_password.py` (5000 samples: hex and no leading dash). The timeout is unchanged, because raising it would not have fixed this.

Not done: `wait_until_ready` still waits the full 120 s when the container has already exited. A fail-fast check on `State.Running` would make that failure quicker to diagnose. It is not needed for this fix and has no test yet. Recorded as a residual, not claimed.

## Decisions and assumptions
- The new tests are in new files, `tests/integration/support/test_harness_restart.py` and `tests/unit/support/test_container_password.py`. The F10 file is untouched.
- Tests 1 and 2 use their own `throwaway_driver()` container, so a stop does not affect other tests.
- `stop_container`, `start_container`, `wait_until_ready` and `new_container_password` are new in `tests/support/neo4j.py`. `_wait_until_healthy` stays in the G14 module as the health gate.
- `start_throwaway_neo4j` calls `wait_until_ready` and removes the container on timeout. Its behaviour is otherwise unchanged.
- Without `--rm`, a container left running when pytest is killed hard stays until removed by hand. With `--rm` it also stayed running in that case, because `docker run -d` detaches, so the leak profile is unchanged.
- The G14 module's stop and start calls now go through the harness helpers, which raise `RuntimeError` on failure.
- No `[ASSUMED]` values were used.
