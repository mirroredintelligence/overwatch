# Evidence: G14 Neo4j connection lifecycle, health and recovery

Builder: build-G14 · Branch: `task/G14-neo4j-lifecycle` · Prompt: `docs/plan/prompts/G14.md`

## Summary
One `Neo4jConnection` owns the process's single `AsyncDriver`: it verifies connectivity on `open()`, closes idempotently, hands out sessions that always close, and rolls back failed writes. `neo4j_health` reports `ok` or `degraded`, is bounded by its timeout, and never raises. The container holds the connection, and `startup()` and `shutdown()` open and close it. Recovery was run for real: the Neo4j container was stopped during an in-flight write and restarted. The write's partial-write proof is the rollback test; see the zero-probe caveat.

## Zero-probe caveat
The assertion `await _count_probes(recovery_conn) == 0` after recovery is a weak check. The server discards uncommitted work during an outage, so the assertion cannot fail on its own during the outage. It is kept only as a secondary check. The partial-write proof is `test_a_write_that_raises_mid_transaction_leaves_no_node_behind` (rollback on a raised exception, count read back in a fresh session).

## Decisions and assumptions
- Connection, health and container wiring follow DEC-012. The four pool values are the [ASSUMED] defaults.
- `Neo4jConnection` takes the four values as `Neo4jPoolOptions`, a frozen dataclass, instead of reading settings, because adapters may not import bootstrap (import-linter layers contract).
- `pool_connection_count()` reads `driver._pool.connections`, a private attribute of neo4j 6.4.1. It is for tests and diagnostics only.
- The driver's own transaction retry (30 s default) is kept. `run_read` and `run_write` can run a write more than once, so writes must be idempotent (P15).
- `Container.neo4j_driver` is replaced by `Container.neo4j` (a `Neo4jConnection`). Later tasks call `container.startup()` and use `container.neo4j.run_read` or `run_write`. Lesson L12 covers this; lesson L14 covers the timing and the retry budget (it corrects L13 to 31 to 43 s).
- Recovery tests need no environment variables; they start their own restartable container. The non-recovery tests use the harness's `NEO4J_URI` and never default to the shared stack.
- F11 is the named follow-up that moves the recovery tests onto `harness_driver` (see the harness split).
