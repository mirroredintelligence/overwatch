# Evidence: I04 Idempotent message consumer framework

Builder: build-I04 · Branch: `task/I04-consumer-framework` · Prompt: `docs/plan/prompts/I04.md`

## Summary
`IdempotentConsumer` (consumer.py) marks (message id, consumer name) as processed and runs the handler in one Neo4j unit of work, so the marker and the handler's writes commit together or not at all. `ServiceBusRunner` (servicebus_runner.py) feeds it from a queue or subscription and completes, abandons or dead-letters each message by the outcome. Before this task there was no consumer framework.

## Hazards

- **H-30 (new, round 2):** an outage longer than the bus delivery limit dead-letters capacity events that were still in flight. The control is the retry pause; the alarm is for the O-series and is not built. The limit is about 8 to 10 minutes with 31 to 43 s per attempt (about 2.5 minutes if attempts fail at once), from 10 deliveries and about 151 s of pauses (DEC-119 item 5). The row is in `docs/delivery/hazard-log.md`. Candidate hazard for the owner: a message applied twice (for example a duplicate text) if a consumer skips the framework; this framework is the control.

## Tenant isolation
This task reads, writes and receives data, so the transitional rule in `multi-tenancy.md` applies (the tenancy seam is not delivered). Result: **tenant-pending, one statement.** No two-tenant test is possible yet.

Tenant-pending statements:
- `Q-PROCESSED-MARK` (P15, used by `IdempotentConsumer` through `uow.processed.mark_if_new`): the `Processed` node is keyed by message id plus consumer name only (`key` has no tenant id). The consumer binds no tenant from message properties, so the same message id arriving for two tenants would be dropped as a duplicate for the second. The runner copies no tenant property into `BusMessage` either.
- TEN-020 owns the tenant property on bus messages and TEN-025 owns the tenant binding in consumers; both must add the tenant to the `Processed` key and bind it before the handler runs. Until then I04 adds no new Cypher statement, no global counter and no global unique key; the one statement it uses is the P15 one named above.
- Cross-scope reads: none. The consumer reads nothing but its own marker.

## Decisions and assumptions
DEC-119 (pause after a retry, any failure caught, one backoff schedule). Other assumptions: (1) a dead-letter reason is the PermanentError text cut to 100 characters, so a handler must not put payload text in it; (2) the BusMessage `topic` is the entity name (queue or topic), the event type is the Service Bus subject, falling back to the `event_type` application property; (3) only PermanentError dead-letters, so a ValidationFailed from a handler is retried until the bus's max delivery count; (4) no lock renewal for long handlers (the queue lock is one minute); (5) the session path (`sessions=True`) opens `max_concurrency` NEXT_AVAILABLE_SESSION receivers; it is proved with a fake client, not against the emulator; (6) no OpenTelemetry span: no telemetry dependency exists yet (O-series).
