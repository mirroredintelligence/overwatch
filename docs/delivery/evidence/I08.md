A search of the diff for UK postcode and NHS-number shapes found nothing; a search for credential-shaped text found only the marker strings `SECRET-...` that tests plant to prove they are never repeated. No consumer logs a text, a phone hash, a tenant list or a token: log lines hold the message id, the outcome word, the class name, and for a receipt the provider id, the status and the provider's error code (the error code in the log is asserted in `test_delivery_tracker.py`; the absence of the text, phone hash and tenant from reasons is asserted in the unit tests). Dead-letter reasons are fixed texts that name a field and never a value (asserted in the unit tests).

## Tenant isolation
**Tenant-scoped statements, keys, queues and messages this task adds.** `Q-PROCESSED-SEEN` is converted (`tenantId: $tenant`, a scenario run by the generated two-tenant test). The processed-marker key is the existing composite one. The reply idempotency key is `sms-reply:<tenant>:<provider id>` (built in `reply_key` from the bound tenant, no tenant is an error). The consumers read `inbound.replies` and `inbound.receipts` messages that carry `tenantId`.
**Where the tenant comes from.** The `tenantId` application property of the message (a producer sets it from a verified source: I07 from the number called and the account after the signature check; the outbox relay from the tenant it read the row under), and only if `ActiveTenants` lists it. Never from the payload.
**Two-tenant tests.** `test_reply_processor.py::test_two_tenants_with_the_same_sender_are_each_handled_in_their_own` (same phone hash in A and B: each reaches the use case under its own tenant, key and unit-of-work scope; each has its own marker; neither is the other's duplicate) and `test_inbound_two_tenants.py` (the same sender and the same provider and bus id in both tenants, replies and receipts, on a contracted container). `test_idempotency_store.py::test_seen_asks_only_in_the_bound_tenant`. `test_delivery_tracker.py::test_two_tenants_each_have_their_own_marker_for_their_receipts`.
**Predicate-removal mutant.** Removing `tenantId: $tenant` from `Q-PROCESSED-SEEN` is refused when the statement is registered (the registry's own check). Removing the tenant binding, the directory check and the tenant from the reply key each fail a named test (table above).
**Tenant-pending statements (transitional rule), and the one test that does not pass.** `Q-COMM-BY-PROVIDER` and `Q-COMM-SET-STATUS` match by provider id alone and no Communication carries `tenantId`; the whole repository is TEN-015's. So "another tenant's message id reads as not found and is dropped" is **not yet true**: `test_delivery_tracker.py::test_another_tenants_message_id_reads_as_not_found_and_is_dropped` is written and marked `xfail(strict=True)`; today it fails because tenant A's receipt changes tenant B's Communication, and it will fail the suite as an unexpected pass when TEN-015 converts the statements, until the marker is removed. Only a callback signed with a tenant's own auth token and carrying another tenant's message id could do this (Twilio message ids are unique across accounts). Also unconverted and used through the use case: `Q-PERSON-PHONE-FIND` and the service and capacity statements (TEN-010), `Q-IDEM-*` (TEN-011); the reply test therefore proves the binding, key and scope with a recording use case and not the data (known issues).
**Cross-scope reads this task would need under DEC-132.** None.

## Decisions and assumptions

Departures from the prompt, each in it: the reply processor is not an I04 handler (item 3: the use case opens its own units); the idempotency key carries the tenant (item 5); a Conflict is a retry (item 6); `set_delivery_status` is now monotonic and returns True only when it moved (item 8); the error code is logged and not stored (item 7). No Sonnet consult was made.
