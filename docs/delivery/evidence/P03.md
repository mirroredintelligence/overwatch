## Summary
People are in the graph. The phone lookup returns the active reporter roles a phone holds, minus those covered out of at `now`, plus those it covers until after `now`, sorted by service name, then service id, then role id. An ambiguous phone lookup is a Conflict. A naive `now` is refused before any query.

## Other staff-text and identifier checks: ASCII-only review (step 3)
- **Postcode (`_POSTCODE`)**: now applied to `unicodedata.normalize("NFKC", value)`. NFKC maps fullwidth Latin letters and digits, and fullwidth space, to their ASCII forms, so `ＳＷ１Ａ １ＡＡ` becomes `SW1A 1AA` and is refused (test `test_every_unicode_digit_counts_towards_the_nine_digit_limit[fullwidth-postcode]`). The pattern itself keeps `[A-Z]`, `[0-9]` and `re.IGNORECASE`, which is correct once the text is normalised.
- **NHS-number pattern**: removed in round 5. The digit count (below) covers NHS-number forms, so no NHS pattern remains to be made Unicode-aware.
- **Digit count**: now `sum(1 for character in value if character.isdecimal())`, which counts every Unicode decimal digit (category Nd). The earlier `[0-9]` count missed other scripts. No regex character class is used for the count.
- **Phone hash (`_PHONE_HASH`, `[0-9a-f]{64}`) and email domain (`_EMAIL_DOMAIN`, `[a-z0-9-]+...`)**: ASCII-only by design. A fullwidth or Arabic-Indic character does not match, so the value is refused, and no normalisation is applied. Normalising here would make a non-ASCII hash or domain look valid, which is the opposite of what these checks are for. Neither is staff text, so this is not the gap the verifier named. No test was added for these, because the round-2 tests already refuse non-hex and non-ASCII input in the same way.
