## Summary
Protected contacts (phone numbers and role emails), PIN credentials and the device registry are stored in Neo4j, so a restart keeps them. The text-code store is an in-memory fake (Redis in production, I13). PIN attempts read the credential under its write lock, so concurrent wrong PINs cannot all be allowed. Round 2 adds a unique key on protected contacts (a racing first write now stores nothing), and makes a same-practitioner racing device registration a no-op.

## Verifier findings, and what changed
1. **Red-commit discipline (fixed).** The four guard tests were first in Green 1 (`9240563`). They are now committed in Red 2 (`38ad50c`) against Green 1, where they fail (table above). Green 2 adds each guard back. The round-1 evidence claimed this was done; it was not, and this file says so.
2. **Credential race (measured, not fixed, DEC-073 item 3).** Sixteen racing `set_pin` calls for one practitioner and device left exactly one `Credential` node in three runs out of three, so the race did not reproduce. The reason recorded in DEC-073 is that the MERGE creates a relationship from the practitioner node, and the engine serialises on that node. The test `test_racing_set_pin_for_one_device_leaves_one_credential` is a regression guard. The reasoning does not rest on the ProtectedContact acceptance. ProtectedContact did reproduce (sixteen nodes) and is fixed with a unique key (DEC-073 item 1, superseding DEC-071 item 1 in part).
3. **Same-practitioner register race (fixed, DEC-073 item 2).** The prompt is silent on re-registration. DEC-071 item 4 chose a no-op; the race now gives the same result. The register path locks the practitioner first (`Q-DEVICE-LOCK`). Test: `test_racing_register_by_the_same_practitioner_succeeds_and_leaves_one_device`.
4. **Disclosure and lesson.** Finding 2 is disclosed here and in DEC-073. The lesson is L91, an update to L90 (L90 is append-only, so it was not edited). L91 records the measurements.
