## Summary
The protected contact store (phone numbers and role emails), the PIN credential store and the device registry now store their state in Neo4j, so a restart keeps them. The text-code store is an in-memory fake (Redis in production, I13). PIN attempts are read under the credential's write lock, so concurrent wrong PINs cannot all be allowed.

## Decisions and assumptions
- DEC-071 (storage shape): contacts keyed by `roleId` property, not linked to the role; `lockedUntil` not stored (the domain has no lock time); device linked by `HAS_DEVICE`, no `practitionerId` property; UTC times written by the database; code expiry matches `code_attempt`; ports follow the prompt, not `contracts.md` line 123; `DEFAULT_FACTORIES` not registered (P06 not delivered).
- DEC-072 (PIN lock and protected store): PIN reads take the write lock; U32 must read and save in one unit of work; the done-when scan excludes only the one `ProtectedContact.value` property.
- Assumption: `set_pin` on an existing device resets the state fresh, because a new PIN follows a verified text code (DEC-044 item 2). U32 decides who may call it.
- Assumption: `clear_all` for an unknown practitioner is a no-op, not an error.
- Three tests (naive registration time, naive code issue time, racing registrations) were added after the first green run and before the green commit, to reach 100% branch coverage. Each passes on the code as written, so none was seen failing. The racing test is the only one that reaches the `ConstraintError` to `Conflict` mapping in `Neo4jDeviceRegistry.register`.
