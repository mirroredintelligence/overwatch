# Evidence: W05 Wall board page

Builder: build-W05 · Branch: `task/W05-wall-board` · Prompt: `docs/plan/prompts/W05.md`

## Summary
`/screen` now shows the call-centre wall board for the signed-in wall (or advisor, lead, exec) session: a header, a three-column grid of tiles in the order the back end sends them (accepting, limited, not accepting, not updated; over capacity and out of hours safely, W07 refines them), a legend and the footer line. It reads `$board` through `GET /api/bff/board` code (`lib/board/read.ts`), which also serves the browser. It takes no input from the address: the session's back-end token is the only thing that says whose board it is (DEC-151).

## Tenant isolation
- **Statements, keys, channels, queues, messages this task adds:** none. The page and the BFF route only call the back end's `GET /fhir/HealthcareService/$board`. No cache key, localStorage, cookie or telemetry attribute holds organisation data. The statements the back end runs for `$board` are listed as tenant-pending in `docs/delivery/evidence/R05.md`.
- **Where the tenant comes from:** the sealed BFF session's back-end token (W02, DEC-125). `WallScreenPage` has no props and the route handler reads no query string, header or body.
- **Two-organisation tests:** `app/(wall)/screen/page.test.tsx` (screen paired to A never renders B's names or ids, and the reverse; a query string and route params carrying B change nothing; the request carries A's bearer token and no query string), `app/api/bff/board/route.test.ts` (a `?tenant=` query and `X-Tenant-Id`, `X-Organisation` and `Authorization` request headers are ignored; the request to the back end has no query and no tenant-like header), `lib/board/read.test.ts`, and `e2e/board.spec.ts` in a real browser. The MSW back end and the browser-test back end answer by bearer token alone, as the real one does.
- **Predicate-removal mutant:** n/a, no statement added. The equivalent here is M10 (a scope added to the back-end request) and M16 (a constant organisation name), both killed.
- **Tenant-pending statements:** none added.
- **Cross-scope reads this page would need under DEC-132 (not built):** (1) `GET $board?scope=network`, a read-only use case bound to the network scope, returning member tenants' projected capacity with the owning organisation on each entry, after a membership and grant check; (2) the tenant display name on `$board` (the `organisation` part, DEC-151 item 3), a read of the bound tenant's own node; (3) the screen's choice of tenant board or network board, which is a read of the paired screen's setting (W08 pairing record); (4) a per-entry owning organisation and a "may act on this service" flag so other organisations' tiles can be labelled and made view-only (no Request booking, I phoned or They declined); (5) a scope label and organisation name on each row of the network variant.
