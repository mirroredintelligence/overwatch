# Evidence: W09 Staff sign-in with Entra ID and role guard

Builder: build-W09 · Branch: `task/W09-staff-signin` · Prompt: `docs/plan/prompts/W09.md`

## Summary
Staff (advisor, clinical advisor, shift lead, criteria owner, exec, support) can sign in through the Entra ID authorisation code flow with PKCE, and the BFF turns a verified ID token into its own session (the W02 cookie) and an HS256 back-end token. `proxy.ts` guards each staff page prefix by the role in that session. **Entra itself is not reached: this build has no Entra credential, so everything is built and proven against a recording fake of the Entra endpoints (`frontend/test/oidc/fake-entra.ts`).** The fake checks PKCE, state/nonce plumbing, the one-time code, the client secret and the redirect address, and signs ID tokens with a key of its own; it is not evidence that Microsoft behaves the same way. See "Not done" for what a real tenant must supply.

## Tenant isolation
**Tenant-scoped statements, keys, channels, queues and messages this task adds:** none. The task adds no Cypher, Redis key, channel, queue or message (front end only). **Where the tenant comes from:** the Entra directory of the *verified* ID token (`tid`, which must agree with the issuer), looked up in the directory-to-tenant bindings (`DIUCS_ENTRA_BINDINGS`), and from nothing in the request: the start route reads only `next`; the callback reads `code` and `state`; a tenant, directory, hint or role in a body, query string or header is never read. The tenant is minted into the back-end token's `tid` and the sealed session is the only copy; the browser never holds it. **Two-tenant test:** `app/api/bff/auth/entra/routes.test.ts::tenant: it comes from the verified directory and from nothing else`: two directories bound to `trust-a` and `trust-b`; the same object id signing into each gets `tid` `trust-a` and `trust-b` respectively and different tokens; six names (`tenant`, `tid`, `tenantId`, `directory`, `organization`, `x-tenant-id`) set to B's value on the start body and the callback query leave A's person in A; a tenant header and a B host on the callback change nothing; a token signed for directory A that names directory B's issuer gets no session. `oidc.test.ts` adds: a verified token from a directory bound to no tenant is refused (`unbound-directory`, answered `/forbidden`), and with one directory bound a token from any other directory is refused. Browser: `e2e/sign-in.spec.ts` signs in as a person from the unbound directory and from a customer directory holding the support role (no session in both). **Predicate-removal mutants:** the equivalents here are the two decisive lines of the tenant rule: replacing the lookup with "first binding" (killed by 2 tests) and reading the tenant from the query string (killed by 1 test); also the single-directory check removed (killed by 1). **Tenant-pending statements:** none (no statements). **Cross-scope reads this task would need under DEC-132:** none. **Open design points for tenancy:** the directory-to-tenant table is configuration until the back end exposes `Tenant.entraDirectoryId` (`TenantDirectory.by_entra_directory`, TEN-007) through the token exchange (TEN-043) or TEN-A01; two tenants sharing one directory are refused at load; the back end does not yet require or read `tid` (TEN-018), so until then the claim is minted and ignored: tenant isolation of data behind the token is the back end's task and is not claimed here.
