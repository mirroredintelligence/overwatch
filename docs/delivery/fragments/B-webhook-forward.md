# B-webhook-forward: the Twilio webhook forward in `web` (front end)

Bundle WB16, branch `task/build-WB16` off `integration/build`. Builds DEC-1302 (the allow-list of two paths, forwarded by `web` to the internal `api`). No decision number block was given, so the decisions below are numbered WBF-1 to WBF-8 for the orchestrator to number. Hazards H-850 to H-855 (all six used).

## Decisions

### WBF-1 Two routes at the public paths, a closed catch-all, one shared function
`app/webhooks/sms/twilio/route.ts` (replies) and `app/webhooks/sms/twilio/status/route.ts` (delivery receipts), outside `/api/bff` because Twilio calls them by their public path. Both only call `forwardTwilioWebhook(request, 'reply' | 'status')` in `lib/webhooks/forward.ts`, which is the one tested function. `app/webhooks/[[...rest]]/route.ts` (the optional form, so `/webhooks` itself is covered) answers every method of every other path under `/webhooks` with the same empty 404; the two specific routes win over it. Each file exports POST (the catch-all too: a 404) and the six other methods as the one `notFound`, because Next's own answer to an unexported method is 405, not the 404 the brief wants. Each says `dynamic = 'force-dynamic'`, because a GET that reads nothing would otherwise be prerendered at build.

### WBF-2 The forward sends the exact bytes and two headers, and nothing else
The path is picked from a two-entry table in code (`WEBHOOK_PATHS`: the back end's `REPLY_PATH` and `STATUS_PATH`), never built from the request; the query string is dropped (the back end refuses one). The body is read once as bytes and sent as the same bytes: never parsed, decoded or re-encoded (the signature is over the exact fields), proved with a body that has `+`, `%2B`, `&`, raw unicode, an emoji, an invalid escape, a trailing newline and a body that is not UTF-8 at all. The request headers sent are `Content-Type` as received and `X-Twilio-Signature` as received (left off if Twilio sent none, for the back end to refuse), and nothing of the caller's: no cookie, Authorization, `X-Forwarded-*`, `Forwarded`, `X-Real-IP`, tenant or edge header. The edge secret (`X-Edge-Auth`, DEC-1303) is NOT sent: this call needs no tenant from the host, and the back end binds the tenant from the number called and the signature. The host is the back end's own (global `fetch` sends the host of the URL it was given, and sets no other).

### WBF-3 What is refused before the back end is called
No `Content-Type`: 400, empty. A declared `Content-Length` over 64 KiB (65,536), or one that is not digits: 413, empty. A body over 64 KiB that declared less or nothing (chunked): 413, empty, and the read stops at the first chunk that crosses the line (a stream that never ends is cancelled, not drained; the brief said `arrayBuffer()`, this reads the same bytes once with the limit applied as they arrive, so a hostile caller cannot make `web` hold more than 64 KiB plus one chunk). A form of exactly 64 KiB is forwarded. A back end address that is not set: 500, empty, nothing called (a fault of this app's set-up, told apart in the log from an outage by its status).

### WBF-4 What comes back
The back end's status, body and `Content-Type` as received, plus `Cache-Control: no-store`; no other header of the back end is passed on (no `Set-Cookie`, `Location`, `Cache-Control`). The back end's own 200 (empty TwiML), 403 (fixed `Forbidden` body) and 500 (a failed queue send) pass through unchanged, so a 500 stays a 500 and Twilio's retry is not taken for a replay. A status that cannot carry a body (204, 205) is sent with none. `redirect: 'manual'`: any 3xx from the back end is a failure, answered 502 with an empty body, and the `Location` is neither followed nor passed on. An answer over 64 KiB is a failure: 502, empty. Unreachable, reset, or no answer in 10 seconds (the timer covers the wait for the answer and the read of its body): 502, empty. 502 and 5xx make Twilio retry; the 4xx the forward itself makes (400, 413) it does not.

### WBF-5 Logging
One `console.warn` line per answer that is not 2xx, of the form `twilio webhook forward: path=/webhooks/sms/twilio status=403`, and nothing for a good answer. Never the body, the signature, a number, a text or the back end's address (tests push every failure path and check every console method against the secrets and against the exact line shape). The back end's own log says why it refused (`sms webhook refused: reason=...`); the status here is the pointer to it.

### WBF-6 No session, no CSRF, no cookie: the signature is the authentication, and the back end checks it
These are pre-session routes of a kind of their own ("webhook"), not `withBff` routes and not the phone's pre-session routes. CSRF protects a browser's cookie from a page that did not ask for the call; here there is no browser and no cookie, so there is nothing for a token to protect and the check does not apply. `web` does not verify the signature either, and must not: it holds no Twilio auth token (those are per tenant, in the vault, read by the back end) and finding the tenant is the back end's job. So the forward is deliberately an unauthenticated public door whose only duty is to hand the exact bytes to the one place that authenticates (H-850).

### WBF-7 How the suites classify it
`test/guards/bff-routes.test.ts` gets a `webhook` kind and a `closed` kind with their own table (`WEBHOOK_ROUTES`) over `app/webhooks/**`: every route on disk is named and every name is on disk; the only routes outside `/api/bff` are these; a webhook file uses no session, cookie, CSRF, header or tenant wrapper; it exports the seven methods and `dynamic = 'force-dynamic'` only; a call with no session is forwarded (never a 401, 403 or redirect of its own); a staff session, an operator session, a tenant's host and a tenant header change nothing and the back end sees none of them; a tenant/scope/network in the query is dropped; every answer is no-store; every method but the forward's POST is an empty 404. The leak canary (`test/leak-canary.ts`) has four new rules for the call from `web` to the back end (`webhook-path`, `webhook-query`, `webhook-header`, `webhook-host`): a call under `/webhooks` that is not a POST to one of the two paths, a query string, an Authorization, cookie, forwarding, edge, CSRF or tenant header, and a Host that is not the back end's own are leaks, and the two paths are not a `no-token` call. `proxy.test.ts` shows both paths (and every path under `/webhooks`) pass the proxy with no session, a bad session cookie or an operator cookie, without the session secret, and without a redirect or a rewrite; the proxy's matcher covers them, so the security headers are on the answer. The fetch allow-list in `test/guards/scan.ts` names `lib/webhooks/forward.ts` with its reason; the ESLint server-only list (`eslint.config.mjs`, with a case in `eslint-rules.test.ts`) forbids a component importing `@/lib/webhooks/*`; `lib/fhir/hostCall.ts` gets `backendOrigin()` so the one place that reads `DIUCS_FHIR_BASE_URL` stays `lib/fhir`.

### WBF-8 Global `fetch`, not `node:http`
The repo's `node:http` rule exists to send a `Host` header, which `fetch` ignores. This call must not set one, so `fetch` is right and the `node-http` scan rule is left alone (L171: MSW intercepts `node:http` only through the default import, and the global `fetch` it always intercepts).

## Hazards

- **H-850** (HIGH) The forward is an unauthenticated public door: anyone on the internet can POST to the two paths, and `web` forwards it. Controls: only two paths and one method, chosen in code; 64 KiB and 10 s limits; the caller's credentials never reach the API and no credential of ours is sent (no edge secret, no bearer, no host); the API verifies the signature with the tenant's token and answers one fixed 403 for every failure, so a caller learns nothing about which numbers or tenants exist; no database is touched before the signature verifies. Residual: unauthenticated traffic costs one call to `api` and one directory lookup each; `web` has no rate limit on these paths (known issue).
- **H-851** (MEDIUM) Memory or time exhaustion by an oversized or never-ending body, or a never-ending answer. Controls: declared length checked first; the stream is cut at the first chunk over 64 KiB (tested with an endless stream); the answer is capped at 64 KiB; one 10-second timer covers the wait and the read.
- **H-852** (MEDIUM) Retries: Twilio retries on a 5xx or a timeout, so the same message can arrive twice, or a retry can be taken for a replay and lost. Controls: the back end's 500 (failed queue send, replay marker removed) passes through unchanged; an unreachable back end is 502 so Twilio retries; the back end's `MessageSid` replay marker (24 h) drops a duplicate that was already queued and answers it with the same empty TwiML; the forward's own 10 s is shorter than Twilio's webhook wait (15 s by default), so `web` answers first with a 502 and Twilio retries a reply that may in fact have been queued (the marker makes that safe).
- **H-853** (HIGH, to configure) The signature fails because the URL Twilio signed differs from the one the API checks. Twilio signs the URL it called exactly: scheme, host, port if explicit, path, and the query. The API checks `DIUCS_BASE_URL` plus the path. Any difference (`http`, another host, a trailing slash on the path, a port, a path prefix in front of `web`) fails every request with the fixed 403, which looks like an attack and is a mis-set URL. Controls: the forward keeps the path as it is and does not rewrite or forward a host; `DIUCS_BASE_URL` on `api` AND on the workers (the status callback URL given to Twilio per message is built from it) must be exactly `https://overwatch.mirroredintelligence.com`; the Twilio console URL must have no trailing slash (Next answers `/webhooks/sms/twilio/` with a 308 to the slashless path, which Twilio may not follow). Detection: `twilio webhook forward: path=... status=403` in `web` together with `sms webhook refused: reason=signature-bad` in `api`.
- **H-854** (MEDIUM) The forward leaks through its answers, logs or a cache. Controls: nothing of the body, signature or number is logged (tests on every failing path); no header of the back end is passed on but `Content-Type`; every answer is `Cache-Control: no-store`, and the route and the catch-all are `force-dynamic`; the forward's own refusals are empty (400, 404, 413, 502) or fixed (500 empty) and say nothing about tenants.
- **H-855** (MEDIUM) The allow-list drifts: a later route under `/webhooks`, a guard in the proxy or a changed forward that sends more. Controls: the catch-all 404s everything but the two paths; the `bff-routes` webhook section fails on an unnamed route or a route that appears outside `/api/bff` and `/webhooks`; the canary fails any call to the back end under `/webhooks` that is not the two paths with the two headers; the proxy test fails if the paths are redirected to sign-in.

## Known issues (with triggers)

- No rate limit on the two paths in `web`. Trigger: a flood of unauthenticated POSTs shows as load on `api` or its directory (watch the 403 rate in `web`'s log line).
- The visitor's address is not passed to the API (no `X-Forwarded-For`, no `CF-Connecting-IP`: the brief forbids them), so the API cannot rate-limit or log by Twilio's source address. Trigger: an IP allow-list for Twilio's ranges, or a per-source limit on the webhook, is wanted.
- Next's patched `fetch` adds `pragma: no-cache` and `cache-control: no-cache` to the outgoing request (seen on a real `next start` against a stub back end; the stub saw exactly `Content-Type`, `X-Twilio-Signature`, those two and the client's own `accept`, `accept-encoding`, `accept-language`, `sec-fetch-mode`, `user-agent`, `content-length`, `host` of the stub). They are not credentials and the back end ignores them; the vitest runs do not show them (MSW sits above that layer). Trigger: the back end or the ingress starts acting on a request `Cache-Control`; then call with `node:http` instead (and extend the `node-http` scan rule's allow-list).
- A cold or restarting `api` can take more than 10 s to answer, so Twilio sees a 502 and retries (safe: H-852). Trigger: a run of 502 lines in `web`'s log after a deploy or a scale-from-zero; raise `TIMEOUT_MS` (it must stay under Twilio's wait) or keep one `api` replica warm.
- The forward's own 400 (no type) and 413 (too large) differ from the back end's uniform 403, so a caller can tell a malformed request from a bad signature. They say nothing about tenants or numbers. Trigger: a requirement that every refusal on these paths be indistinguishable.
- The ingress or Cloudflare in front of `web` may challenge or block Twilio's servers (bot rules, WAF). Not seen here: no ingress. Trigger: Twilio's debugger shows 403 or a challenge page with no matching line in `web`'s log; add a skip rule for `/webhooks/sms/twilio*`.
- Not run: a real call from Twilio, the pilot ingress, Playwright (none needed: no page). What was run: the whole vitest suite, typecheck, lint, `pnpm build` (both routes and the catch-all are listed as dynamic), and a hand check against a built `next start` and a stub back end (byte-for-byte body with a raw non-ASCII byte, the headers the stub saw, 404 for GET, HEAD and PUT, 404 for `/webhooks` and for other paths, 308 for a trailing slash, 413 for 70,000 bytes).

## The Twilio console, exactly (per tenant subaccount; DEC-131: one subaccount per tenant)

Prerequisite on the API and the workers: `DIUCS_BASE_URL=https://overwatch.mirroredintelligence.com` (no trailing slash, no path; to become `OVERWATCH_BASE_URL`). On `web`: `DIUCS_FHIR_BASE_URL=https://api.internal.<env-domain>/fhir` (the forward calls `<that origin>/webhooks/sms/twilio[/status]`).

1. Phone Numbers, Manage, Active numbers, the tenant's number (in that tenant's subaccount), Messaging Configuration:
   - Configure with: **Webhook, TwiML Bin, Function, Studio Flow, Proxy Service** (not a Messaging Service)
   - A message comes in: **Webhook**
   - URL: `https://overwatch.mirroredintelligence.com/webhooks/sms/twilio`
   - HTTP method: **HTTP POST**
   - Primary handler fails: leave empty (a fallback URL that answers differently would hide a failure).
2. Delivery receipts need no console setting: each outbound message carries `StatusCallback=https://overwatch.mirroredintelligence.com/webhooks/sms/twilio/status` (built by the workers from `DIUCS_BASE_URL`). Do not set a status callback on a Messaging Service for these numbers; if one is ever used it must be exactly that URL, POST.
3. Do not set a webhook-signing override: the signature is made with the subaccount's own auth token, which is the secret `twilio/<tenant>/auth-token` the back end reads for that line. HTTP authentication in the URL (`user:pass@`) must not be used: it would change the URL the signature covers.
4. Check: send a text from a registered phone to the number; `web`'s log has no line (a good answer is silent), the message appears on the inbound queue. A text from an unregistered phone also answers 200 with the empty TwiML (the API says nothing about who is on its list). A 403 line in `web`'s log: see H-853.

## Contracts

- Routes (public, POST only, no session): `POST /webhooks/sms/twilio`, `POST /webhooks/sms/twilio/status`. Request: the Twilio form as sent, at most 65,536 bytes, with a `Content-Type`; `X-Twilio-Signature`. Answers: 200 empty TwiML (`text/xml`) or 403 `Forbidden` (`text/plain`) or 500 from the back end, as it answered; 400 (no type), 413 (over 64 KiB), 500 (back end address not set), 502 (unreachable, over 10 s, a redirect, an answer over 64 KiB), all with an empty body; `Cache-Control: no-store` on all. Every other method on them, and every method on every other path under `/webhooks`: 404, empty body.
- `@/lib/webhooks/forward` (server only): `forwardTwilioWebhook(request, target)`, `notFound()`, `WEBHOOK_PATHS`, `MAX_FORM_BYTES`, `MAX_ANSWER_BYTES`, `TIMEOUT_MS`, type `WebhookTarget`.
- `@/lib/fhir/hostCall`: new `backendOrigin()` (the back end's origin from `DIUCS_FHIR_BASE_URL`; throws when it is not set).
- Test support: leak canary rules `webhook-path`, `webhook-query`, `webhook-header`, `webhook-host`.

## Tenant pending

None: the front end holds no graph statement, and the forward is deliberately tenant-blind. The tenant is bound at the back end from the number called and a verified signature (DEC-131, I07), never from the host, a header or a query.
