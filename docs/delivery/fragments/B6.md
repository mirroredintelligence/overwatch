# B6: advisor and clinical (case, options, advice, summary, replay) (clinical-safety work)

Bundle WB6 (= bundle B6 of `docs/delivery/gap-triage.md` section 2.2). Branch `task/build-WB6`. Back end and front end. Number blocks: DEC-1170 to DEC-1189 (used 1170 to 1182), H-820 to H-839 (used 820 to 829), migrations 0210 to 0214 (none used: every change is to a property, an extension or a statement, never to the schema). Provisional answers applied: DEC-1100 Q5 (the service contact supplies the phone), Q7 (a wrong score is corrected by a new recorded score with a reason, the original kept in the audit), Q8, Q10, Q13, Q19, Q20 (no part of this bundle touches them; nothing here stores a postcode on a closed case, DEC-067).

## Decisions

### DEC-1170 The Pathways Dx shape is `[A-Za-z0-9]{2,12}` and a code is accepted only when it is on the list (KI-247, KI-625, KI-816, H-85)
Status: accepted (under DEC-133) [ASSUMED shape]. The triage said `[A-Z0-9]{2,10}`; the codes of the list begin "Dx" (the pilot's own sample is `DxSAMPLE01`), so an upper-case-only shape refused every one of them. The shape only keeps stray text out; what makes a code acceptable is that it is on the list (`Terminology.pathways_dx_listed`, exact, case counts, nothing trimmed; an empty or missing list refuses every code rather than accepting any). The list file is refused at load when it holds a code of another shape. The picker (`lib/advisor/scores.ts PATHWAYS_CODE`) uses the same shape and drops a result of another shape, so a code the advisor chooses is a code the back end will record: it was how a score could be lost on a call.

### DEC-1171 A recorded score is changed only as a correction with a reason; the first value is kept in the audit (Q7, KI-815)
Status: accepted. A write's scores are merged by method: a method not yet recorded is added (no reason), a recorded method given another value is a correction, a recorded method not mentioned stays as it is, and two scores of one method in one write are refused. A correction needs a reason from a closed set (`typing-error`, `referrer-corrected`, `rescored`; codes, never free text, because a reason can reach the audit which must hold nothing a person typed), sent as the extension `score-correction-reason`; a reason with nothing corrected is refused. The audit entry holds the score as it was, the score now and the reason; the case holds how many times the scores were corrected (`score-corrections` extension, on the answer only when above zero). A score is never removed: the screen offers no "Not given" and no way to clear a recorded method once one is recorded. The labels of the three reasons are [ASSUMED] wording.

### DEC-1172 The case has a version; a save at another version is 412; the open is one unit of work (H-192, KI-400)
Status: accepted. The ETag of a ServiceRequest is its stored version (`W/"n"`); a PUT must send the ETag it read as If-Match and a case at another version is a 412 (`conflict`) and nothing is written, so two advisors editing one open case cannot silently overwrite each other (replaces DEC-398's unchecked If-Match and DEC-397's two units). `$close` takes an optional If-Match and checks it when given. The open with details is one unit: a refusal leaves no case with no details. The screen says "Someone changed this case since you opened it. Nothing of yours was saved." and offers "Read the case again", which reads the latest and starts the form afresh; the save is disabled while the message stands.

### DEC-1173 The phoned report checks its case in the report's own unit of work (KI-354, KI-400)
Status: accepted. A case named with "I phoned" must exist in the bound tenant and be open, checked in the same unit as the capacity report, so a case closed between the check and the report is refused (DEC-292); another tenant's id is the one not found.

### DEC-1174 A lapsed clinical lock is released in the store; the advice is the Task's output; the request records the service under consideration (KI-233, KI-232, KI-473, KI-768)
Status: accepted. What a list drops or shows as released is released in the store too, so a lapsed lock does not stay `taken`. The advice is also `Task.output` (one typed output per part under the `task-output` code system: `advice-choice`, `advice-reason`, `advice-note`, `advised-at`), so a FHIR read of the Task shows it; the extensions stay beside the outputs until the screens read the outputs. The request takes an optional `service` input (the service id the advisor was asking about, when asked from one service's card); the Task answers the service's NAME (never the id) under the same input name, and the clinician's "Go ahead" reads "Go ahead with UCR West". The presence lives for 120 seconds and then reads as not available (tested by expiry). With no service the label stays "Go ahead with the service".

### DEC-1175 Visiting services are drawn as a circle; travel legs, the service phone and the patient point are sent; the straight-line fallback never fails the list; the TravelTime switch is wired (KI-626, 627, 801, 814, 791, 200, 202, 203, 350)
Status: accepted. A visiting service has no site, so its circle is the mean of the centres of the districts it covers and the distance to the farthest, rounded up to whole kilometres and never under one (`domain/rules/coverage.py`; a picture of where it goes, never a boundary). `$filter-options` options gain `phone` (the work phone of the service profile, Q5), `coverageRadiusKm` (with `lat`/`lon` as the circle's centre), and one `leg` part per travel leg after the range. The travel estimate is awaited after the unit of work has closed (KI-350). A cache that cannot be read answers the straight-line estimate at once (the routing engine is not asked while the cache is down, so a Redis fault is not a burst of route requests) and one that cannot be written only loses the keeping of an answer (KI-202). The cache key no longer repeats the tenant (the cache qualifies every name, TEN-019, KI-203). The container selects the routing provider by its setting and the straight-line one otherwise (KI-200).

### DEC-1176 Network options are view only, from the projection, labelled by organisation (KI-349, KI-181, KI-794)
Status: accepted. `$filter-options` with a `network` part answers the other organisations' services of that network as options carrying `organisation` (its name from the registry, never a tenant id) and `organisationSource`; a row is an option only when the organisation shares its directory, capacity and criteria (a service whose criteria are not shared cannot be filtered, so it is not offered: fail closed), its status can take a case and its current criteria cover the case. The case is read first and closed; the network read takes no parameter from it, so no case value reaches the network scope. The audit is a separate use case (`FilterNetworkOptions`), so the own display that the clinician is shown ("what the advisor saw", DEC-1030) is never replaced by a network one. The BFF reads at most three networks per display, appends their rows after the own services, and drops any network row that names no organisation, so no row can be taken for the viewer's own service. If the network read fails the own services are answered and the answer says `network: "unavailable"`; the screen says "The other organisations' services could not be read, so only your own are shown. Phone to check if you need them." Never an empty list for a failure.

### DEC-1177 The replay shows names as shown and the "+n" figure; planning orders by the position shown; declines are read by use case (KI-474, 475, 476, 477, 352, H-190, H-193)
Status: accepted. A display snapshot keeps the name the advisor saw, `over_by` and the position the option was shown at; the replay shows the name as shown (a display written before that shows the current name and says so), "+n" for how far over capacity (never the used count), and the options in the order shown. Planning's best fit is the option shown first, which is the nearest by travel [ASSUMED, DEC-393]; a display written before positions were kept has no order, so its best fit is the first option listed (board order, which may not be the nearest): the analysis cannot do better for it. The planning window and the decline listing read by use case and window, not every audit record of the tenant.

### DEC-1178 The advisor work phone has a writer (W44, DEC-1034)
Status: accepted. `PUT /tenant/staff/{practitioner id}/work-phone` `{phone}` (tenant administrator only) stores the number under `work-<practitioner id>` (the existing protected contact store; no new store of numbers, DEC-856 item 4) for an active person of the tenant. A number that is not a full UK number is refused and never echoed; another tenant's person, an unknown one and one who has left are the same not found; the audit entry names the person and the kind, never the number.

### DEC-1179 The clinical advice form is not offered when "what the advisor saw" cannot be read (tightens DEC-1036)
Status: accepted. DEC-1036 let the form stand when that read failed. A clinician who cannot see what the advisor saw can advise on the wrong services (H-700), and the same failure on a busy shift is the case this control is for. Now a request whose read of what the advisor saw failed (no answer, or `unreadable`) shows the case, says "What the advisor saw could not be read, so no advice can be given from here. Phone the advisor to ask, or read it again.", offers the call to the advisor, "Read it again" (re-reads the page) and the way back to the queue, and no advice form. A request with no display recorded (`none`) is a read that worked ("No options display is recorded for this request") and still allows advice: that is a fact about the record, not a failure to read it.

### DEC-1180 The summary to copy is built by the back end, with the destination, booking and data age of the service chosen (H-322)
Status: accepted. The BFF route no longer builds the summary from the case read; it calls `GET $summary` so the text that is pasted is the text the back end holds. The finish screen reads it again naming the service chosen as the destination on the outcome form (`?destination=<service id>`), so the copied referral says where the patient went, how it was booked and how old the figure was. Until a destination is chosen the three rows read "No destination chosen yet"; a destination with no holding booking reads "Not booked"; a re-read that fails removes the summary rather than leaving one without the destination. A closed case has no summary (409 `closed`). "Not recorded in this view" is now "Not recorded".

### DEC-1181 The outcome form offers the viewer's own services only
Status: accepted. A destination is a service of the viewer's organisation, and the back end refuses another's. The form asks the BFF for `?only=own` and filters out any row that names an organisation.

### DEC-1182 Every card shows the service phone as a link, or says none is held
Status: accepted. The number is read only when it is shaped like one (digits, spaces, brackets, dashes, an optional leading plus, five to twenty-five characters); anything else is not offered, so nothing odd reaches a `tel:` link. A card with none says "No phone number is held for this service. Find it in your service directory."; a number is never made up. A network card has no booking, "I phoned", "They declined" or Criteria (its criteria are another organisation's, which the own-criteria read would not find): the one thing to do with it is to phone it.
