# B8: Key Vault secret store, back end (bundle WB14)

Bundle WB14 (= bundle B8). Branch `task/build-WB14`. Back end and infra files only. Spec: DEC-1304 and its addendum (they override the task text). Number blocks: none was given for decisions, so the decisions below are numbered B8-D1 and up for the orchestrator to number; H-830 to H-839 (used 830 to 835); migrations none (no graph change).

## Decisions (beyond DEC-1304)

### B8-D1 The vault name function lives in the domain and the file store uses it too
Status: accepted. `domain/rules/secret_names.py: vault_secret_name` (pure, never raises) is the one mapping; `adapters/outbound/keyvault_secrets` re-exports it, so the adapters stay independent (import-linter) and a name that works in a file on a laptop works in the vault. A refused name is `NotFound` with the fixed text "secret name is not a valid reference" (the refused text is never echoed: it could hold anything).

### B8-D2 An unreadable secret is `SecretStoreUnavailable`, not a `DomainError` and not `NotFound`
Status: accepted. It is defined beside the port (`application/ports/outbound/tokens.py`). Every caller of `SecretStore.get` was read: each catches `NotFound` and nothing else (the exchange, the pre-session resolver, the identity routes' `_check_secrets`, `TenantSenderResolver._secret_text`, the SMS webhook's token read, `configured_push_sender`, `edge_for`, `secret_is_configured`, `TenantKeyedSecrets`, the phone hasher, the link-token service), so an outage passes through each of them and the request is a 500 or the queue message is retried and dead-lettered by the runner, never "no secret, carry on" and never a 4xx. `test_callers_fail_closed.py` pins seven of those callers. No `except Exception` or `except DomainError` sits between a secret read and the edge (grep, 2026-10-31); a later one that swallowed it would turn an outage into a silent skip, and H-831 says where to look.

### B8-D3 The stale window is checked before the retry pause
Status: accepted. While serving a stale value the vault is asked again at most every 30 s (`STALE_RETRY_SECONDS`), but a value older than the TTL plus the stale seconds is never served, pause or not: past the window the store asks the vault once and, if that fails, fails closed. A failed read inside the window logs a WARNING with the secret name and the failure's TYPE only (the provider's text can hold a request id or URL). The raised exception does not chain the provider's (`from None`).

### B8-D4 The Azure client is built with short timeouts
Status: accepted. `SecretClient(connection_timeout=3, read_timeout=5, retry_total=2)` (`bootstrap/secret_store.py`). The library's defaults (300 s to connect or read, more retries) would freeze the event loop for minutes on a cold read when the vault cannot be reached. Worst case now is about 25 to 30 seconds for one read, and then the value held is served or the read fails. [ASSUMED values; measure on the pilot.]

### B8-D5 The three secret settings, and the address key, are read once at start-up; plain values beside a vault stop the process
Status: accepted (DEC-1304 item 8, with the lead's addition). `neo4j_password`, `redis_url`, `servicebus_connection` come from `neo4j-password`, `redis-url`, `servicebus-connection` (required: missing, empty, not text or unreadable stops the process, naming each secret and no value) and `os_places_api_key` from `os-places-api-key` (optional: absent is the existing "no address lookup" warning; an unreadable one stops). A plain `DIUCS_NEO4J_PASSWORD`, `DIUCS_REDIS_URL`, `DIUCS_SERVICEBUS_CONNECTION` or `DIUCS_OS_PLACES_API_KEY` beside `DIUCS_KEY_VAULT_URL` stops the process before the vault is asked for anything, naming the variable and the vault secret that replaces it. Detected from `os.environ` (any letter case: the settings read it that way) and from the settings given directly (`model_fields_set`), so a default is never mistaken for a value. The workers and the relay read the three but not the address key. The relay closes the vault after reading them. `redis_url` is out of the settings' repr (the pilot's URL holds the access key).

### B8-D6 The start-up check is the prefetch
Status: accepted. `check_secrets` (api) and `check_worker_secrets` (workers) read each required name at start-up, which warms the cache. The api's optional names are read when the lifespan starts (warnings). There is no separate `prefetch` call in the wiring; `KeyVaultSecretStore.prefetch(names)` exists for a caller that needs one. The per-tenant Twilio tokens are not listed anywhere (they depend on the tenants) and are read cold at the first send for each tenant (H-832).

### B8-D7 The workers' list is what their wiring reads, pinned by a test
Status: accepted. `WORKER_REQUIRED_SECRETS = ("link-token",)`: `AesGcmContentSealer` (every sealed message, all sender runners, the alert notifier) and `LinkTokenService` (scheduled work) read only that platform name (derived per tenant by `TenantKeyedSecrets`, DEC-350). `WORKER_OPTIONAL_SECRETS = ("webpush-vapid-private-key",)`: `configured_push_sender`; without it the push runner is not started (warning). Nothing else: no `phone-hash`, `code-hmac`, `bff-jwt`. A test records the names `AesGcmContentSealer.seal` and `configured_push_sender` ask for and requires them to equal the two lists, so a new secret read in a worker path makes that test fail until the list is updated. DEC-1304 item 5's "secrets the consumers already read" is therefore `link-token` plus the per-tenant references.

### B8-D8 The workers refuse to run in the production profile with no store
Status: accepted. With no vault and no directory the workers keep running outside production as before (every secret not found, a warning), and stop in production with a message naming `DIUCS_KEY_VAULT_URL`. The api already refused with no store.

### B8-D9 `REQUIRED_SECRETS` gains `telemetry-markers` and starts with `bff-jwt`
Status: accepted. The api reads `telemetry-markers` (browser insight) and the start-up check did not list it. `bff-jwt` is first so an outage at start-up is reported against the signing key. `edge-origin` stays optional (DEC-1303 item 3); its absence is a warning.

### B8-D10 The development file store
Status: accepted (the lead's addendum). `FileSecretStore` (`adapters/outbound/file_secrets`), chosen by `load_secret_store` when `DIUCS_SECRETS_DIR` is set and the vault URL is not. Refused: in the production profile (`DIUCS_SECRETS_DIR ... refused when DIUCS_PROFILE is production`), beside a vault URL (names both settings), a directory that does not exist or is not a directory, a directory with any permission bit for group or others (mode `& 0o077`), and, when a secret is read, a file that is not a regular file private to its owner, a symbolic link (`O_NOFOLLOW`) or a file over 64 KiB (`SecretStoreUnavailable` naming the secret). Names map as in the vault (`/` to `--`); a refused name opens no file. Trailing CR/LF is stripped, an empty file is NotFound, nothing is cached. It logs one WARNING at start-up that it is the development store. When it is in use, `DIUCS_NEO4J_PASSWORD`, `DIUCS_REDIS_URL` and `DIUCS_SERVICEBUS_CONNECTION` work from the environment (no vault, so no refusal), and the address key is read from the file `os-places-api-key` when the environment does not give one. The relay ignores the directory (it reads no secret).

### B8-D11 `scripts/make_local_secrets.py <directory>`
Status: accepted. Python, as the repo's other scripts (thin entry over `diucs/bootstrap/local_secrets.py`). Writes one file for each name in `REQUIRED_SECRETS` (the ten the api requires, which include the one the workers read): 48 random bytes as base64 text, directory 700 (created, or an existing one must already be private: otherwise it refuses and writes nothing), files 600 created with `O_EXCL`. An existing file is kept, so a second run adds what is missing and never rotates. It prints the names written and kept and no value.

### B8-D12 Infra: the script already matched DEC-1304; SETUP.md names each app's secrets
Status: accepted. `create-pilot.sh` gave api, web and workers `Key Vault Secrets User` on the vault and the collector and Redis none, and passed no secret as an environment value: unchanged apart from a comment on the container-apps line. `SETUP.md` section 5a is new: the settings each app gets (the vault URL and its identity's client id, never a secret; Neo4j URI and user for api and workers), a container-app example that puts `--env-vars` values on their own lines, a ban on `AZURE_CLIENT_SECRET`, and the secrets of the api, the workers and the web app by name. `tests/unit/test_azure_infra.py` reads both files and the code's lists, so the document and the code cannot drift. The Service Bus role (Data Owner for api and workers) is unchanged: see KI-1304.

## How to run the API and the workers locally

From the repository root and `backend/` (nothing here uses a vault or a real credential):

```bash
docker compose -f infra/docker-compose.yml up -d --wait neo4j redis servicebus-sql servicebus-emulator servicebus-ready
cd backend
uv run python scripts/make_local_secrets.py ~/.diucs/secrets      # once; prints names, no value
export DIUCS_SECRETS_DIR=~/.diucs/secrets
export DIUCS_EDGE=none                                            # no Cloudflare in front locally
export DIUCS_SERVICEBUS_CONNECTION='Endpoint=sb://localhost;SharedAccessKeyName=RootManageSharedAccessKey;SharedAccessKey=SAS_KEY_VALUE;UseDevelopmentEmulator=true'
# The compose Neo4j password is the settings default (diucs-test-password) and Redis is redis://localhost:6379/0,
# so DIUCS_NEO4J_PASSWORD and DIUCS_REDIS_URL need not be set; setting them is fine because no vault is configured.
uv run python -m diucs.bootstrap.api_main          # the API on DIUCS_API_PORT (8000)
uv run python -m diucs.bootstrap.workers_main      # in another terminal
uv run python -m diucs.bootstrap.outbox_relay_main # and the relay, if the outbox is used
```

Every sign-in is refused locally (no Entra verifier is built: `RefusingIdentityVerifier`, unchanged). `DIUCS_PROFILE=production` with `DIUCS_SECRETS_DIR` stops with a message naming the setting. The compose Service Bus connection is the emulator's public development string (also in `tests/support/servicebus.py`).

## Known issues

| KI-1306 | A cold or expired read is synchronous and blocks the calling thread for one vault round trip. The start-up check warms every platform name; a tenant's Twilio and SMTP secrets are cold at first use and again every ten minutes of use. Prefetch is not done for them because the list depends on the tenants. | if p99 latency of a send or an SMS webhook shows ten-minute spikes, or the vault has an outage that is not recovered in a minute: move the read to `asyncio.to_thread` with a refresh ahead of expiry (the store is already thread-safe) |
