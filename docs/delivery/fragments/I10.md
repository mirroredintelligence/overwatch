# I10 fragment

## Decision

I10: outbound senders take the tenant from the message and send through that tenant's sender.

1. The outbox payload is the one U03 writes: `communication_id`, `message_id` (catalogue id),
   `channel`, `recipient_role_id` and `sealed_content`. The text, subject and html are sealed
   (DEC-116), so the sender opens them with `ContentSealer.unseal`, under the outbox message id,
   the bound tenant and the recipient role. The prompt's plain `text`, `subject`, `html` fields do
   not exist in the payload and are not added.
2. The sender is chosen per tenant at send time through a `SenderResolver` port (DEC-131 item 1),
   not injected once. `SmsMessageSender` and `EmailMessageSender` therefore take
   `(senders, sealer)`, not `(sms)`. A tenant with no sender for the channel is recorded as failed
   with `no-channel` and nothing is sent (fail closed, H-T03).
3. The recipient comes from `uow.contacts` inside the unit of work. No number or address is
   recorded as failed with `no-contact` and the message completes (permanent).
4. The send outcome is written to the Communication in the same unit of work by a new port method,
   `CommunicationRepository.record_send_outcome`: `sent` with the provider id, or `failed` with the
   reason (`refused`, `send-failed`, `no-contact`, `no-channel`) kept as the `errorCode` property.
   Only a queued communication with no provider id moves. The write takes the record's lock first
   (lesson L73).
5. A communication with a provider id, or one that has left `queued`, is never sent again
   (`is_handled`). A `SendFailedError` (an answer that is neither accepted nor a listed refusal)
   is recorded as `failed` with `send-failed` and completes; it is not retried.
6. Consumer names `sender-sms` and `sender-email` (as the prompt). Subscriptions keep the names in
   the Service Bus config: `text-sender`, `email-sender`, `push-sender` (the F04 prompt names them,
   the prompt for I10 says `sms`, `email`, `push`; the config is the thing that runs).
7. `infra/servicebus-config.json` gets one SQL rule per sender subscription (`channel = 'text'`,
   `channel = 'email'`, `channel = 'push'`). `channel` is an application property (the adapter sets
   it), so the filter sees it.

## Contracts

- `SenderResolver` (port, `application/ports/outbound/sender_resolver.py`): `sms_for(tenant_id)`, `email_for(tenant_id)`, each `-> SmsSender | None`.
- `CommunicationRepository.record_send_outcome(communication_id, *, status, provider_message_id, error_code) -> bool` (port in `application/ports/outbound/messaging.py`; Neo4j in `communication_repository.py`, query `Q-COMM-RECORD-OUTCOME` with a scenario).
- `OutboundMessage`, `parse_outbound(payload, *, message_id, tenant_id, sealer)`, `is_handled(communication)` (`adapters/inbound/workers/message_senders.py`).
- `SmsMessageSender(senders, sealer)`, `EmailMessageSender(senders, sealer)`, `sender_runners(client, uow_factory, tenants, senders, sealer, observe)`.
- Constants: `MESSAGES_TOPIC`, `SEND_MESSAGE_EVENT`, `CONSUMER_SMS`, `CONSUMER_EMAIL`, `SMS_SUBSCRIPTION`, `EMAIL_SUBSCRIPTION`, `PUSH_SUBSCRIPTION`, and the refusal texts and reason codes `NO_CONTACT`, `NO_CHANNEL`, `REFUSED`, `SEND_FAILED`.
- `FixedSenderResolver(sms=, email=)` (test fake, `adapters/testing/recording_senders.py`).
- Config: subscriptions `text-sender`, `email-sender`, `push-sender` on `messages.outbound` carry SQL rules.

## Tenant pending

- The `SenderResolver` in production returns None for every tenant until TEN-007 channels exist (no sender is ever used in production; fail closed).
- The `Communication` statements (`Q-COMM-RECORD-OUTCOME`) are tenant-scoped (`tenantId: $tenant`) and have a scenario, so the generated two-tenant test covers them in verification.
- Sender identity (`senderLabel`, `fromAddress`) per tenant is not used yet: the text comes from U03's rendered message, which TEN-022 makes tenant-aware.

## Assumed

- Reason codes stored on a failed Communication: `no-contact`, `no-channel`, `refused`, `send-failed` (the spec gives only `no-contact`).
- A `SendFailedError` is recorded as failed and completes rather than dead-lettering: a dead letter would leave the Communication queued forever.
- Subscription names kept from the config (`text-sender`, `email-sender`, `push-sender`).
