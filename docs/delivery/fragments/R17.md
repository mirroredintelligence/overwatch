# Fragment R17: acknowledgement of a withdrawn booking

Route: `POST /fhir/Task/{id}/$acknowledge` in routes_bookings.py (built in the R09 implement commit,
c69a890). Decisions 6 and 8 of R09.md cover the route's behaviour.

## Fix in U21 (AcknowledgeWithdrawal, withdraw_booking.py)
A repeat acknowledgement with a new Idempotency-Key used to write a second AcknowledgeWithdrawal
audit entry. The fix: before the audit append, `_already_acknowledged` reads the booking's audit
records (`uow.audit.records_for`) and writes nothing when an AcknowledgeWithdrawal record exists.
The repeat still answers 200 with `cancelled_escalation` false, and nothing is cancelled twice.
Red commit: 085545e (the U21 integration test
`test_a_second_acknowledgement_with_a_new_key_writes_no_second_audit_entry` and the R17 route test
without its xfail). The fix commit follows it. Both run only on the orchestrator's merged-tree
integration run (not run here, per the wave addendum).

Why the audit log, not the cancelled escalation: `cancel_work` is also called from suspend_service,
so a cancelled escalation does not prove an acknowledgement happened.
