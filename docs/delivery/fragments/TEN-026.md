## Decisions

### DEC-271 Tenant configuration records: scope, versions, approvals, retention defaults and what is left to others (TEN-026)

Status: accepted (build wave 2, under DEC-133; no owner gate). Affects: DEC-134 item 14, DEC-136 item
10, the tenancy plan rows TEN-026, TEN-028, TEN-042, TEN-043, audit F section 2.3. Assumed values are
marked [ASSUMED].

1. **Tenant scope, registry untouched.** Every record is a node in the tenant's own scope with
   `tenantId`, written and read by registered `NamedQuery` statements with a scenario each (17
   statements, `CONFIG_QUERY_IDS`). The registry (`Tenant`, `TenantNumber`, no `tenantId`) is read
   only by global statements (DEC-163) and is not written here, so the registry's
   `currentConfigVersion` and `entraDirectoryId` are not maintained by this task. The version in
   force is the tenant's version with status `current`, never a pointer.
2. **Seven records and their keys** (composite, migration 0055 `0055_tenant_config_records` in the new
   area module `migrations_tenant_config.py`, lesson L157, one schema statement each, expand only,
   no label existed before so nothing is superseded): `TenantConfigVersion (tenantId, version)`,
   `TenantSetting (tenantId, configVersion, key)` joined by `HAS_SETTING`, `TenantContact (tenantId,
   kind)`, `TenantChannel (tenantId, id)`, `TenantRetention (tenantId, dataClass)`,
   `TenantEntraBinding (tenantId, directoryId)`, `TenantRoleMapping (tenantId, groupObjectId)`. A
   setting is a typed row with one column (`intValue`, `textValue`, `boolValue`, `timeValue`,
   `codeValues` a list of text) and its unit, never JSON (DEC-001). The migration is in its own
   module and not in `migrations_tenant.py` (the files list named that one) so the existing
   `TENANT_IDS` pin is untouched; the assembled list and its count test include it.
3. **Versions are immutable snapshots.** A version holds the whole set of overrides; `plan_draft`
   builds the next one from the version in force (`based_on` must equal it, else `Conflict`, so a
   retry of a lost reply cannot make a second draft), applies the changes and removals, validates
   every value (bounds, allowed codes, cross-field rules), and refuses a draft that changes
   nothing. Setting a key back to its default is a change. The only statement that changes a
   version's node (`Q-TCFG-MOVE`) sets its status, approvers and effective time, matches by key,
   locks the node with a self-set and reads the status after the lock (lessons L73, L99), so two
   approvers at once move it once. A settings row is written once with its version.
4. **Approvals (the DEC-032 pattern).** An operational change needs one approver, who may be its
   author. A change that touches a clinical setting needs two different people, neither the author;
   the first version of a tenant always does (it sets clinical values). The approvers needed are
   judged against the version in force at approval, from the values alone. Only the latest version
   can be approved, so a draft written against an older version can never revert a newer one. The
   approval that completes a change moves it draft to pending to current and the old version to
   `superseded` in one unit of work (each a guarded move, a lost race is `Conflict`).
5. **Who may change it: nobody yet.** `CONFIGURATION_ROLES` is empty and every use case takes the
   roles as a constructor argument, so every actor is refused until the composition root passes
   `frozenset({Role.TENANT_ADMIN})` (TEN-018 adds the role, DEC-134 item 4). A role off the list is
   refused before any unit of work opens. The unit of work must be bound to a tenant; a network
   scope or none is `TenantNotBound`.
6. **Retention defaults [ASSUMED]**, one rule per class, set by an explicit act (activation needs the
   rules stored): capacity reports 730 days summarised; bookings 730 days deleted; case audit 2555
   days deleted (the postcode and needs of a case are cleared at close by the rule book whatever this
   row says); communications 730 days; raw telemetry 90 days; telemetry aggregates 730 days; audit
   chain and safety concerns kept until purge. Only those two classes may be `keep`, and they may be
   nothing else. The longest period is 3650 days.
7. **Channels.** A text channel holds a Twilio account SID and the reference of its token, an email
   channel a sender address and optionally the reference of its SMTP secret; no field can hold a
   token or a password (DEC-131 item 4). The secret reference must be the bound tenant's own
   (`check_secret_ref`), so a channel can never name another tenant's token. A channel is retired by
   recording it again with its id and status `retired`; it stays as history. The sender label and
   display name go through the privacy guard (D17).
8. **Directory binding and roles.** A tenant administrator binds a directory as `pending`; binding
   another revokes the one in force; binding the same one again changes nothing. Verification is the
   platform operator's (TEN-043, TEN-028) through `put_binding`, so a `verified` record names when
   and by whom. A group maps to a staff role only (advisor, clinical, lead, owner, exec, audit): not
   `support` (a platform role from the operator directory), nor wall, reporter or anonymous link.
9. **The read port.** `ReadTenantConfig` gives the policy in force (the default policy when no version
   is in force, which equals the behaviour before tenancy), the wording (None unless all three words
   are set), the contacts and the readiness facts (`ConfigurationFacts`). Each call opens its own
   unit of work, so a caller must not hold one open (lesson L173). It does not cache.
10. **Not built here, with the reason.** No domain event (`TenantConfigChanged` has no consumer yet); no
    idempotency key (the `based_on` and status guards make a retry a `Conflict` or a no-op); no
    discard of a draft (the move table has no such step); no container or settings wiring (the
    composition root is shared and TEN-028, TEN-042 and TEN-043 wire what they use); no write of the
    `TenantNumber` or the registry's host and directory (a tenant unit cannot write a registry
    node, DEC-163).

11. **Mutants run by hand** (22, over the four unit files of this task): the author approving a clinical
    change, one approver for a clinical change, a draft not checked against the version in force, a
    draft that changes nothing, any role configuring (and the default role set not empty), a
    directory bound twice, another tenant's secret, an approver approving twice, a setting written
    without the registry check, duplicate setting rows, the lock of the move removed or the status
    read before it, a kept class deleted, a `support` group mapping, a verified binding with no
    verifier, a channel with the wrong provider, a string read as a list of approvers, the count
    dropped from the latest statement, a draft built from nothing, clinical keys not counted, and a
    supersede that keeps its status. All killed; two first survived (the repeated-approver message
    and a string read as a list) and their tests were tightened. The use cases' own flow
    (`execute`) is covered by the integration tests only, which are not run here.
