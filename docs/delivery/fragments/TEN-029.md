## Decisions

### DEC-272 The cross-tenant reference matrix tests the entry points as they are; the placeholder behaviour is not changed (TEN-029)

Status: accepted (build wave 2, under DEC-133; no owner gate). Affects: DEC-053 item 8, DEC-130
item 1, audit F section 3.4 items 1 and 3, `ResourceStore`, TEN-032.

1. **The audit asked for two things and this task does one.** Audit F 3.4 recommends (item 1) that in
   tenant mode the resource store refuses to create placeholders, and (item 3) a generated matrix
   test over every relationship. The matrix is built. The store is not changed: placeholder creation
   is the design of DEC-053 item 8, `test_resource_store.py` asserts it, several callers rely on it
   (a scope entry for a service not yet held, a booking whose owner is written in the same
   transaction), and a change to it cannot be verified without Neo4j, which this build does not
   run. Changing it blind would be a decision about behaviour that nothing here can show is safe.
2. **What the placeholder does with a foreign id.** The store looks the id up in the bound tenant,
   so an id that exists only in another tenant is unknown, and the placeholder is the bound
   tenant's own node with its own `tenantId`. Nothing links across, and the other tenant's node is
   neither read nor changed. A foreign id therefore cannot create a cross-tenant relationship or
   leak that it exists (the collision the audit feared, `Resource.id` clashing across tenants, is
   gone because the key is `(tenantId, id)`, TEN-005). What remains is the audit's lesser point:
   the bound tenant's entry point accepts the id instead of refusing it. See the known issue.
3. **The matrix** (`tests/support/relationship_matrix.py`) classifies the 39 relationship types the
   graph store names in its Cypher by what the entry point does with a foreign target: `CHECKED`
   (9 types, 9 cases: refused with `NotFound`, before any write), `PLACEHOLDER` (2: `ENTRY`,
   `OWNER`), `TENANT_LOCAL` (every node of the statement is on `tenantId: $tenant`, proved for each
   registered statement by the generated two-tenant test), `SHARED` (7 Concept-valued types,
   DEC-130 item 5) and `REGISTRY` (`HAS_NUMBER`). `written_types()` reads the Cypher text of the
   store, so a new relationship type that is not classified fails
   `test_every_relationship_type_the_store_writes_is_classified`.
4. **"The same body as a missing target"** is tested by `shape()`, which takes the ids the caller
   named out of the message, and compares the refusal for a foreign id with the refusal for an id
   that exists nowhere. **"Zero writes"** is tested by catching the refusal inside the transaction
   and committing it, then comparing the SHA-256 digest of both tenants' subgraphs
   (`tenant_seed.digest`) before and after. A refusal that propagates would roll back and hide a
   write made before it, so it is not used.
5. **What the nine cases are**: `capacity.add.service` (FOCUS), `person.save_role.practitioner`
   (PRACTITIONER), `person.save_role.service` (HEALTHCARE_SERVICE), `person.save_role.cover`
   (COVERED_BY), `flag.add_report_flag.report` (ON), `flag.set_service_flag.service` (SUBJECT),
   `push.save.practitioner` (USED_BY), `move.add.service` (FOR), `move.add.practitioner` (FROM).
   Each also runs once with the tenant's own record, which must not be refused as missing, so a
   case cannot pass by refusing everything.
