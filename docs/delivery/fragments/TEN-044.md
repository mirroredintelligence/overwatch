## Decisions

DEC-600 The BFF session carries the tenant and the host it was made on, and is read only on that host (TEN-044, refines DEC-125 items 2 and 9, DEC-130 item 3 and DEC-134 item 3, reworks W02)

Status: accepted (build wave 6, bundle W6A, under DEC-133; no owner gate). Affects: `frontend/lib/auth/session.ts`, `lib/auth/host.ts` (new), `lib/auth/ids.ts` (new), `lib/auth/tokenClaims.ts` (new), `app/api/bff/telemetry/route.ts`, `lib/telemetry/schema.ts`, `proxy.ts` (unchanged, reads the same function), `e2e/support/session.ts`.

1. **`Session` gains `tenantId` and `host`.** The tenant is the one the back end issued the token for, read from the `tenant` claim of the token the back end returned at sign-in (`readIssuedToken`), never from a request. A claim that is missing, a network id (`net-...`) or not a tenant id is refused. The browser never receives it (the session answer is `{role, services, csrfToken}`; `sub` is dropped too).
2. **Unseal fails closed.** A sealed session with no or an invalid `tenantId` or `host` is `null`, so a session cookie from before this change is a signed-out visitor (one sign-in), never a session with a guessed tenant.
3. **A session is for the host it was made on.** `sessionFromRequest` and `getSession` return the session only when the request's Host (`requestHost`: the Host header, or the address of a request built without one; never `X-Forwarded-Host`, `Forwarded` or a tenant header) equals the sealed `host`. The cookie is already host-only (no `Domain`), so this closes the case of a cookie set from a sibling sub-domain (a tenant B script setting a valid tenant B session on tenant A's host). The host is compared in lower case with its port. A proxy in front of the app must pass the original Host on, as the back end already requires (DEC-167 item 1).
4. **`tenant-admin` and `network-admin` join `ROLES`** (DEC-134 item 4); `STAFF_ROLES` names the eight roles a staff sign-in can give. `platform-operator` is not a session role: the operator door is a separate audience and a separate exchange (TEN-043 `/auth/operator-token`) and has no BFF door yet (known issue).
5. **Not done: a `__Host-` cookie prefix.** It would stop cookie tossing at the browser, but it needs Secure and so breaks local development over http, and it renames the cookie every e2e and proxy test reads. The host binding covers the same case in the sealed value. Revisit with the first production deployment.

DEC-601 Staff sign-in is the back end's token exchange; the front end holds no signing secret, no directory list and no role mapping (TEN-044, TEN-043, supersedes DEC-210 items 4 to 7 where they differ: the directory-to-tenant table, the role map and the token mint; DEC-134 item 2, reworks W09)

Status: accepted (build wave 6, bundle W6A). Affects: `lib/auth/exchange.ts` (new), `lib/auth/flow.ts`, `lib/auth/oidc.ts`, `lib/auth/staff.ts`, `lib/fhir/hostCall.ts` (new), `lib/links/server.ts`, `e2e/support/*`, `test/oidc/*`.

1. **What the BFF still does:** the OpenID code flow with PKCE against Entra, state, nonce, and the signature, audience, issuer and nonce checks of the identity token (defence in depth; the back end verifies it again). **What it no longer does:** map an app role to a DIUCS role (`mapRoles`), mint a token (`mintBackendToken`, `BACKEND_JWT_SECRET`), hold the directory-to-tenant list (`DIUCS_ENTRA_BINDINGS`) or give the support role from a directory. `staff.ts` exports `safeNext` only (a test holds that).
2. **The exchange (`exchangeStaffToken`)** posts `{"idToken"}` to `POST /auth/token` with the browser's host as the Host header and nothing else (no tenant, role, audience or directory), and keeps the answer only when it is the shape TEN-043 promised: a staff role (one of `STAFF_ROLES`), a token for the staff audience that names a tenant, a role equal to the answer's, and an expiry equal (to 2 seconds) to the stated `expiresAt` and still ahead. Failure is one of four words (`refused` for 403, `not-found` for 404, `unavailable`, `bad-answer`) and carries no token, host or tenant. The sign-in page shows the access message only for `refused`; every other failure is "could not sign you in". A directory the tenant has not bound, a group with no role and a person of another tenant's directory are one answer (the back end's one 403), so the page does not say which.
3. **The token is not verified here.** The front end has no secret. `readIssuedToken` reads the claims of a token the back end has just handed this server over the server-to-server call, to record the tenant; the back end checks every later use of the token (signature, audience, tenant, epoch).
4. **One redirect address per tenant host.** `DIUCS_PUBLIC_URL` is gone: the address Entra returns the browser to is the callback on the host of the request (`callbackAddress`), https in production whatever scheme the request URL shows, and the request's own scheme and port elsewhere. Each tenant host must be registered as a redirect address of the one app registration (deployment). The sealed sign-in transaction carries the host it began on, and the callback refuses to finish on another (a transaction is for one host). The shared `organizations` endpoint is always asked.
5. **The host-forwarding transport moved to `lib/fhir/hostCall.ts`** (`callBackend`, `BackendCallError`, `backendRoot`), beside `client.ts`; `lib/links/server.ts` keeps `callLinkApi`, `LinkApiError`, `hostOf` and `backendRoot` as before on top of it. Node's `fetch` ignores a Host header, so it uses `node:http` with the default import (lesson L171). It never sends an Authorization or tenant header.

DEC-602 The BFF handler: private and never stored, no tenant input, one 404 for an id, the back end's 401 ends the session (TEN-044, supersedes DEC-125 item 8, refines DEC-130 item 7 and DEC-132, reworks W02 and W01)

Status: accepted (build wave 6, bundle W6A). Affects: `lib/bff/handler.ts`, `lib/bff/inputGuard.ts` (new), `lib/bff/errors.ts`, `app/api/bff/session/route.ts`, `test/cookies.ts`, `test/requests.ts` (new), `test/tenants.ts` (new), `test/backendToken.ts` (new), `test/msw/handlers/auth.ts` (new).

1. **Every answer of `withBff` is `Cache-Control: private, no-store` and `Vary: Cookie, Host`,** success, refusal, error and 204 alike. The handler's own directives are kept except the ones that let a cache keep or share (`public`, `max-age`, `s-maxage`, `stale-*`, `immutable`, `must-revalidate`), so a stream keeps its `no-transform`. The response is rebuilt, so one with immutable headers (from `fetch` or `Response.redirect`) works; one that cannot be rebuilt is a bare 500.
2. **Inputs that name a tenant, a scope or a network are a 400 `{code: "invalid"}` before the handler runs,** after the session, role and CSRF checks (an unauthenticated caller always learns 401). The check is on key names only, compared without case, dashes, underscores, dots or brackets: a query key, a header (`tenant*`, `x-tenant*`, `x-scope*`, `x-network*`, `x-source-tenant*`) and a key of a JSON or form body at any depth up to 12 (deeper, more than 5000 objects or a body over 128 KiB is refused as unverifiable). A value such as `?q=network` is data. Other bodies (text, binary) are not read. The scope of a request is the route family, never a parameter (audit D 3.3).
3. **`idScoped: true` makes every back-end 403 and 404 the one 404** (`{code: "not-found", message: "We could not find that."}`), so an id in another tenant cannot be told from an id that is nowhere. A 404 has one code whatever the back end called it, on every route.
4. **A 401 from the back end ends the session here:** the session and CSRF cookies are cleared and the answer is 401 `{code: "session-ended"}`. A 400, 403, 404, 409, 5xx leaves it. (The back end refuses a token whose epoch moved, a suspended tenant or a changed role; the BFF no longer keeps a dead session.)
5. **The session route** answers display fields only: `{role, services, csrfToken}`.

## Contracts

- `lib/auth/session.ts`: `Session {role, tenantId, host, services, sub, device?, backendToken, expiresAt}`; `ROLES` adds `tenant-admin`, `network-admin`; `STAFF_ROLES`; `sessionFromRequest` and `getSession` read a session only on its host.
- `lib/auth/host.ts`: `normaliseHost`, `requestHost`. `lib/auth/ids.ts`: `isTenantId`, `isGuid`. `lib/auth/tokenClaims.ts`: `readIssuedToken`, `STAFF_AUDIENCE`.
- `lib/auth/exchange.ts`: `exchangeStaffToken(idToken, host, now?) -> StaffGrant`, `ExchangeFailed(reason)`.
- `lib/auth/oidc.ts`: `EntraConfig {clientId, clientSecret, authorityHost}`, `callbackAddress(request)`, `newTransaction(next, host)`, `authorizeUrl(config, transaction, redirectUri)`, `exchangeCode(config, code, transaction, redirectUri)`, `verifyIdToken` returns `{oid, directoryId}`. Settings read: `ENTRA_CLIENT_ID`, `ENTRA_CLIENT_SECRET`, `ENTRA_AUTHORITY_HOST`, `SESSION_SECRET`, `DIUCS_FHIR_BASE_URL`. Removed: `DIUCS_PUBLIC_URL`, `DIUCS_ENTRA_BINDINGS`, `BACKEND_JWT_SECRET`.
- `lib/fhir/hostCall.ts`: `callBackend`, `BackendCallError`, `backendRoot`.
- `lib/bff/handler.ts`: `withBff(handler, {roles?, csrf?, idScoped?})`; `lib/bff/inputGuard.ts`: `refusesTenantInput`, `namesTenantInput`; `lib/bff/errors.ts`: `toBffError(error, {idScoped?})`.
- BFF endpoints: `GET /api/bff/session` -> `{role, services, csrfToken}`; `DELETE /api/bff/session` -> 204; back-end call `POST /auth/token` (TEN-043).
- Test support: `test/tenants.ts` (`TENANTS`), `test/backendToken.ts` (`fakeBackendToken`, `claimsOf`), `test/requests.ts` (`requestAs`, `sessionFor`), `test/cookies.ts` (jar, `headersMock`, `setRequestHost`, `seedCookies`), `test/msw/handlers/auth.ts` (the exchange stand-in).
