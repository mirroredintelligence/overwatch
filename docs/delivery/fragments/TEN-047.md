## Decisions

DEC-607 The front-end tenancy harness: overlapping fixtures, a leak canary on every back-end call, and a generated test over every BFF route (TEN-047, refines DEC-130 item 7, audit D 7)

Status: accepted (build wave 6, bundle W6A, under DEC-133; no owner gate). Affects: `frontend/test/tenants.ts`, `test/leak-canary.ts` (new), `test/setup.ts`, `test/msw/handlers/*` (`tenantData.ts` new, `links.ts`, `index.ts`), `test/requests.ts`, `test/guards/bff-routes.test.ts` (new), `test/import-meta-glob.d.ts` (new), `vitest.config.ts`.

1. **The fixture is built to make a mistake visible.** `TENANTS.A`, `.B` and `.C` (hosts `tenant-a|b|c.example.test`, distinct fictional names and ids), `NETWORK` (`net-sample`, members A and B; C is not a member), `GRANTS` (one active, one ended, one pending), and `recordsFor(tenantId)`: tenants A and B hold the SAME service id `s1`, case reference `4821`, phone ending and registration id with DIFFERENT content (so a handler that forgets the tenant returns the wrong record, not a 404, and the wrong record is not mistaken for the right one), one id (`a-only-1`, case `4822`) exists in A only. No person, phone number, postcode or NHS number (a test scans the fixture).
2. **The leak canary watches every call to the back end, in every test.** `test/setup.ts` installs it on the MSW server (`request:start`, so it also sees a call no handler answers) and asserts it after every test; a test that made a call that could cross a tenant fails there, whatever it was checking. Rules: `tenant-mismatch` (the token's tenant is not one the test signed in as: `sessionFor` and `requestAs` call `canary.expect`), `tenant-header` (any `X-Tenant*`, `X-Scope*`, `X-Network*`, `X-Source-Tenant*` header), `tenant-query` (a query key naming a tenant, scope or network), `link-bearer` (a link call with an Authorization header), `network-non-member` (a network route called with a token of a tenant that is not a member of `net-sample`), `no-token` (a tenant-API call with no token; `/auth/`, `/public/` and `/links/` have none by design) and `bad-audience` (an operator token at the tenant API). A token the canary cannot read (the opaque tokens of the older tests) is judged on the other rules only. The message names the rule, method and path, never a token, cookie or host. Only calls to the back end origin are looked at.
3. **A tenant-aware back end stand-in** (`tenantDataHandlers`: `GET /fhir/HealthcareService/{id}` and `GET /fhir/ServiceRequest/{reference}`): the tenant is the token's `tenant` claim and nothing else; a record in another tenant is the same 404 as a record nowhere; a token it cannot read is a 401. The sample link handlers now answer a request addressed to another tenant's host as they do a link that exists nowhere (410 `expired`), like the real back end (DEC-167 item 1).
4. **The generated route test** (`test/guards/bff-routes.test.ts`) finds every `app/api/bff/**/route.ts` on disk, requires each to be in a table that classifies it (`session`, `link`, `sign-in`, `beacon`), so a new route file that is not classified fails the build, and checks each kind: exports only HTTP methods and no `revalidate` or `fetchCache`; **session** routes answer 401 with no session, answer a session of tenant A sent to tenant B's host byte-for-byte as no session, refuse (400) a request naming a tenant, scope or network (query or header) before any work, and are `no-store`; **link** routes answer a link that exists only in tenant A, asked on tenant B's host, exactly as a link that exists nowhere (never a 403), answer the same with a staff session in the browser and write no staff cookie, and are `no-store` (plus a non-vacuity control: the same link on A's own host is a different answer); sign-in and beacon routes are `no-store` and take no tenant from the request. The audit asked for "tenant B holding an id that exists only in tenant A gets 404": the invariant tested is the stronger "indistinguishable from an id that exists nowhere", which is the same 404 for the routes that answer one and the 410 of a link for the link pages. Verified by mutation: a link route that ignores the request host fails it.
5. **The suite's own timeout is 20 seconds** (`testTimeout`, `hookTimeout`): the axe checks render a whole page in jsdom and ran past the default 5 seconds on a busy machine (five failures on one full run that passed alone).
