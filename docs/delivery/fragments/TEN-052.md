## Decisions

### DEC-270 One allowlist module, one digest, and the choices the prompt leaves open (TEN-052)

Status: accepted (build wave 2, under DEC-133; no owner gate). Affects: DEC-132 items 4 and 7,
DEC-134 items 6 to 8, DEC-136 items 3, 4 and 14, D17 (`privacy_guard.py`), TEN-053 to TEN-057 and
TEN-062, which read this module and write nothing of their own.

1. **One definition, two layers.** `domain/rules/projection.py` is the only place that names what
   may leave a tenant: `PROJECTION_ALLOWLIST_VERSION` (1), `FieldSpec`, `ALLOWLIST` (five labels,
   each field with its stored property and its source), `SYSTEM_PROPERTIES`, `NETWORK_RELATIONSHIPS`
   (empty), `NEVER_SHARED` (18 categories), `allowlist_digest()`, the five DTOs and the three
   builders. `application/projection.py` holds the translation (`to_rows`, `to_body`, `from_body`,
   `body_keys`, `format_window`, `parse_window`) and the statement check. A grep of `src/` finds
   `"sourceServiceId"` in `domain/rules/projection.py` only (a test holds that). The digest is the
   SHA-256 of the version and every label, DTO field, stored property and source, in order, pinned
   in `tests/unit/application/test_projection_allowlist.py`
   (`6ed747fd9ea7b4d753811d2f8bcea92b6a5524ba2710ef1972857f56095fdf97` for version 1). It does not
   cover `SYSTEM_PROPERTIES`, which statements stamp and TEN-053 may extend. Changing the
   allowlist needs a version bump, a new pin, a decision and, for a widening, a new agreement
   version (TEN-036 `revise_grant`).
2. **Names.** The service name is `service_name` (stored `serviceName`) and the place name is
   `location_name`, because `name` is a forbidden key (D17 `FORBIDDEN_FIELDS`, TEN-038's body
   floor).
3. **The street address is not shared.** A location holds a name, a postal district (the outward
   code, from `normalise_postcode` then `postcode_district`, or a bare district), a city and a
   coordinate pair (both or neither). A value that is neither a postcode nor a district gives
   `None` and is never copied. The street lines are not an input at all, the postcode input is
   reduced to its district by the builder, and the full postcode appears nowhere.
4. **Source versions.** A service projection orders by the producer's `source_version` (the
   HealthcareService version); a capacity projection by milliseconds since 1970 UTC at which the
   producer read the source (a monotonic per-source sequence, named `source_version` so every DTO
   orders the same way); criteria by `Basic.version`. `supersedes(stored, incoming)` is true for
   the first write and for an equal version (a replay is idempotent), false for an older one
   (hazard H-N06). It refuses a version that is not a whole number of at least 1.
5. **Contact.** `contact_label` is plain text of at most 60 characters and `contact_phone` matches
   `\+?[0-9][0-9 ]{6,15}[0-9]` and passes `find_patient_data`. That a number is a role or
   switchboard number and not a person's cannot be enforced by shape: it is a point for the person
   who registers the service (the registration form wording is TEN-051/W-series work, not here).
6. **Opening hours** travel in the flat body as window strings `"<days csv>|HH:MM:SS|HH:MM:SS"` or
   `"<days csv>|all-day"`, days ascending and distinct, times whole seconds. `from_body` accepts a
   tuple or a list of them (a body that went through JSON has lists).
7. **`valid_until`** is supplied by the producer (TEN-056 computes it); `None` means no known
   boundary and the read relies on the heartbeat. **`NETWORK_RELATIONSHIPS`** is empty until
   TEN-053 adds what it needs, with a test each. **`NetworkServiceInput.row_ref`** is an opaque
   reference supplied by the read use case (TEN-057), never the source tenant id.
8. **Text and identifier checks.** Every `str` DTO field is checked in `__post_init__`: exact
   `str`, within its cap, characters from `[\w &'()./,:+·-]`, no control character, no `<`, `>` or
   `@`, and `find_patient_data == []`. Ids match `[A-Za-z0-9][A-Za-z0-9_.:-]{0,63}`. Numbers are
   range-checked, enums by exact type (lesson L3), datetimes must be timezone-aware and are held in
   UTC, lists become sorted tuples, a bare string is refused as a list (lesson L51).
9. **Privacy guard.** `normalise_key`, `FORBIDDEN_KEY_FORMS`, `find_forbidden_keys` and
   `scan_value` are added; `find_patient_data` and `FORBIDDEN_FIELDS` are unchanged. A value nested
   deeper than 16 levels, which includes a value that contains itself, is refused.
10. **Statement check** (`check_network_write_statement`, `assert_network_write_statement`): a
    tokenising parse (comments removed and string literals masked first), fail closed
    (`unparseable`). Codes as in the prompt, plus `multiple-labels`, `unlabelled-node` and
    `unlabelled-variable` (a write through a variable whose pattern gave no label). A statement
    with no write clause has no problems. `ON CREATE SET` and `ON MATCH SET` need no case of their
    own (they read as an empty CREATE or MATCH followed by the SET). The relationship list is read
    at call time, so TEN-053's additions take effect.
11. **Network board.** An `admitted` listing with both the `directory` and `capacity` scopes
    becomes a figure row; a `suspended` listing is a name-only row whatever the scopes (TEN-036
    gives a suspended listing no scopes); `pending`, `declined` and `withdrawn` are left out; a
    shown listing missing a scope is left out (fail closed). Order is category declaration order,
    organisation, service name (case-folded), then `row_ref`; status never affects it. Pressure
    counts shown rows only, through TEN-021's functions with the thresholds passed in.
12. **Departures from the prompt text, each with a test.**
    a. `tenantId` is a stamped system property and also a forbidden key form (D17 forbids
       `tenant_id`, TEN-022). The prompt's test 3 says no `SYSTEM_PROPERTIES` entry may be a
       forbidden form; the test instead pins that the scope stamp `tenantId` is the only exception.
       No DTO has a tenant field and no row or body carries one.
    b. A service projection with `active == False` is left out of the board (the prompt is silent;
       a deactivated service must not look like a live tile).
    c. A report dated after the read instant (clock skew between member and platform) reads Not
       updated with no figures, instead of raising from `assess_freshness` and taking the whole
       board down.
    d. A capacity projection that has no report reads as `compute_status` reads it (Not updated in
       hours, Out of hours outside them), so the network row and the tenant row agree; the prompt
       says "no report: not-updated" and that holds in hours.
    e. `format_window` and `parse_window` take and return an `OpeningHourProjection` (and the
       position), not four loose values.
    f. `ProjectionValue` is defined in `application/projection.py` as
       `str | int | float | bool | None | tuple[str, ...]` because TEN-038's events are not on this
       branch; TEN-038 may alias it.
    g. `build_capacity_projection` refuses a report of another service or measure with
       `ValidationFailed` (not the `ValueError` of `compute_status`), and a policy that is not
       exactly a `TenantPolicy` with `ValidationFailed` (not `TypeError`).
13. **Disagreements in the sources, and the choice.** Audit A stores a computed status in
    `ProjectedCapacity`; DEC-134 item 6 (later) stores the inputs, so DEC-134 wins. Audit F copies
    `comment`, a `listingStatus` and an `endorsement`; DEC-132 and DEC-136 do not, so they are not
    copied. Audit A keys capacity by report id, audit F keeps a series, audit B and DEC-134 want the
    current inputs: the DTO carries `report_id` so TEN-053 can key either way.

14. **Mutants run by hand** (`mutate.py` over the six test files, about 6 seconds a run): 50 named
    mutants, every one killed by a named test. Builders: copy `comment` (M01), copy a
    `change_reason` or `performer_role_id` (M02, M03), a field in `ALLOWLIST` without the DTO (M04),
    in the DTO without the allowlist (M05), a stored property named `phone` (M06), `to_rows` with an
    extra key (M07), a `postcode` copied raw (M33, M34), `build_criteria_projection` accepting
    `pending-approval` (M20). Body and guard: `from_body` without the extra-key or missing-key
    check (M08, M56), the text check without the guard (M09), `scan_value` without list or key
    reads (M17, M18), `normalise_key` not normalising (M19), a deleted `NEVER_SHARED` entry (M28),
    a digest that ignores sources (M30). Statement check: `+=`, a parameter map, a tenant label, a
    CALL or `apoc`, backticks, a comment that hides the rest, `keys(`, DELETE, an unlisted
    relationship, relationship properties, an unknown or unlabelled variable, a property or label
    assignment, a dynamic set, an unread statement answered `[]`, the shape check removed (M10,
    M12, M13, M14b to M16, M40 to M55). Board: `confirmed_since` dropped (M21), the default reply
    window (M22), `suspended` ignored (M23), `supersedes` with `>` or `<` (M24), status order (M25),
    a `pending` field (M26), scopes ignored (M27), an inactive service shown (M31), a figure on a
    suspended listing (M32). Three mutants first survived (M11 the `ON CREATE SET` case, M14 the
    CALL clause case, M29 a repeated scope check): each was an equivalent mutant (another line did
    the same work), so the redundant code was removed, not tested around. Coverage of the four
    modules is 100 percent line and branch (`uv run --with coverage python -m coverage`).

## Tenant pending

None. Pure code: no statement is registered, no key, channel or queue is added, and nothing reads a
tenant. No DTO has a tenant field (the source tenant id is an argument the producer takes from its
verified binding, TEN-054). Cross-scope reads this task would need: none (the member-scope reads
and the network write are TEN-054, the network board read is TEN-057). The layer-2 proof against a
real network scope (every property of every node, label and relationship) is TEN-062.
