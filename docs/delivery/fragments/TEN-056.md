# TEN-056: leave and grant-end semantics, boundary projection, reconciliation (W9A)

Back end: `domain/rules/projection_validity.py` (`next_status_change`), `domain/rules/opening_hours.py` (`next_hours_change`), `application/use_cases/network_leave.py` (`EndProjections`), `projection_reconcile.py` (`ReconcileProjection`), `projection_boundaries.py` (`RunProjectionHeartbeat`, `ensure_projection_schedule`), `network_governance.py` (`NetworkGovernance`), `adapters/inbound/workers/network_governance_consumer.py`, `project_network.py` (`valid_until`), `apply_projection.py` (the reopen rule), `bootstrap/workers_main.py` (wiring), `application/work.py` (`WorkKind.PROJECTION_HEARTBEAT`).

## Decisions

- DEC-962 The producer writes `valid_until`, and the heartbeat is one chain of scheduled work for each tenant that shares. `next_status_change(profile, last_report, now, policy, zone)` is the next instant after `now` at which the status the member's own board computes from the same inputs could change with no new report: the hours change (`next_hours_change`: a window's edge, the join of two windows is no edge), the reply-by of the current and the next due time (unless a report at or after that due time exists, or the service is already overdue: it stays so until a report, which is an event), and the figure's age passing the stale limit; a suspended service has none (rule 1 of `compute_status`). Its oracle in the tests is `compute_status` itself over a three-day sweep. `ProjectNetwork` reads the tenant's zone from a `TenantZones` source before the unit opens and fills `valid_until` on every capacity projection; `ProjectionRun.next_boundary` is the earliest, not part of equality. `WorkKind.PROJECTION_HEARTBEAT` (about the tenant): each run backfills every kind (the capacity version is the instant read, so each run moves it forward: that is the heartbeat; directory and criteria are ordered by their own versions, so a repeat is a no-op), runs the revoked-grant leak check for every network the tenant is an active member of or left within 24 hours, carries out due supersessions, and in the unit that marks the work schedules the next run at the earlier of the next boundary and 5 minutes, never sooner than a minute. The projection and reconciliation run before the marker (they open their own units, never nested in it); a repeated delivery projects again (the apply step is idempotent) and schedules once. The chain ends when the tenant has no approved grant in a network it belongs to and left none within a day; a `GrantEffective` starts it again (`ensure_projection_schedule`, work id derived from the tenant and the minute so two starters make one chain). [ASSUMED] interval 5 minutes, minimum gap 1 minute, reconciliation after a leave 24 hours. The board is still computed at the time of the read from the stored inputs (DEC-546): nothing reads `valid_until` to degrade a status, so it is the heartbeat's schedule and a statement to a later reader, not a second source of truth.
- DEC-963 The network projector's subscription of `network.events` has its runner. `NetworkGovernanceConsumer` (inside `TenantBoundConsumer`, subscription `network-projector`, no sessions: the second subscription of the topic, beside the board's, so neither holds the other back) hands the event to `NetworkGovernance`. It acts on three events: `GrantEffective` (in the GRANTOR's scope, bound for the call: start the heartbeat chain and backfill that kind), `GrantEnded` (end the source of that member and kind, dated by the event), `MemberRemoved` (end every source of the member); the others are acknowledged. The message is never the authority: the grant or network is read from the registry, the event must agree with it (grantor, scope, network), and the verified sender must be a party (the grantor or the owner of the network for a grant; the member or the owner for a membership); a tenant that is not active is skipped. Refusals are permanent (`message-invalid`, `not-found`, `sender-mismatch`), anything else is a retry that names only the class of the error. The handler is in the list of modules that may bind a tenant (architecture test), with its reason: it binds the grantor, which may not be the sender. Wired in `workers_main.serve` with the heartbeat handler and the supersession.
- DEC-964 Ending a source (`EndProjections`) is repeatable and dated by the decision. `end_grant(network, member, scope, reason, at)` and `end_member(network, member, at)` ask the registry first and leave alone a member that still shares the scope in that network (a newer grant) or whose membership is active again, because a handler that runs late must not end what is now valid; a supersession ends nothing (the successor carries on); the end is dated by the event or the registry's own date, never by the moment it is handled; one network unit does the end and one audit entry (`EndProjection`, ids, reason, kinds and counts) is written only when something changed, so a second run changes and audits nothing. The reason is `left` for a lapse of a member who is not active, otherwise `grant-ended`. The reopen rule of `ApplyProjection` is refined: an ended source is reopened by a grant that began after the end, where "began" is the later of its last approval and its start (`_in_force_from`), because a grant approved before an end but starting after it is a new grant for the source; an in-flight message of an older grant still cannot reopen it (its grant is no longer effective at the gate in any case). `ReconcileProjection.member(network, member)` is the leak check: it reads the member's active sources and live rows in a read-only network unit, then ends (through `EndProjections`, after the read unit has closed) every kind the registry no longer allows, and a live row under an ended source is marked; a network that is not active reconciles nothing.
