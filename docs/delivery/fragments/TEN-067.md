# TEN-067: wall screen board scope setting (back end)

Bundle W9B. Branch `task/build-W9B`. Tests: unit (domain, `NetworkAccess` for a wall, the role and status tables), integration on the shared Neo4j and Redis (`test_wall_board_scope.py`, 56 cases, run green; the pairing, registry and route files that the change touched, 113 cases, run green). Not run: Playwright (no front end here).

## Decisions

### DEC-980 A wall screen's board is a setting on its own record, decided on the server from that record on every read (TEN-067, refines DEC-132 item 5, DEC-548 item 3, audit C 13.5)
Status: accepted (build wave 9, bundle W9B; under DEC-133). Affects: `domain/model/device.py` (`Device.network_id`, `Device.scope_version`), `credential_store.py` (`Q-SCREEN-PEEK`, `Q-SCREEN-LIST`, the two screen statements carry `networkId` and `boardScopeVersion`), `application/network_access.py` (`ScreenReader`, `require_tenant_member`, `screen_network`, `require_wall`, `networks_of_tenant`), `application/use_cases/wall_board_scope.py` (new), `network_board_projector.py` (`get_wall_board`), `routes_screens.py`, `routes_network_events.py` (`open_wall_network_events`).

1. **Where it lives.** On the `:Device` node in the paired tenant's scope: `boardScope` (`tenant`, the default, or `network`), `networkId` (set only for `network`; the domain refuses a network screen with none and a tenant screen with one) and `boardScopeVersion` (1 when paired, plus one for every change; a screen stored before this task reads as version 1 and the tenant board). It is not in the wall token. The token still carries `tenant`, role `wall` and `sub` = the device id and no `networks` claim, so an administrator changes the board without pairing again and a stolen token cannot widen its own view.
2. **A wall asks for no network.** The audit's sketch (`$network-board?network=<id>` accepted for a wall only when the id equals the stored one) is replaced by routes with nothing to ask for: `GET /screens/me/board-scope`, `GET /screens/me/network-board`, `GET /screens/me/network-events`. The network is the screen record's, read on every call (`Q-SCREEN-PEEK`, a read with no write lock: a screen refreshes often and decides nothing single-use), and the registry then confirms the tenant is an active member of an active network (`NetworkAccess.require_wall`). `/network/{id}/...` stays closed to a wall (DEC-548 item 3 stands: the role is not in `NETWORK_VIEW_ROLES`), so a wall cannot read a network by naming it. A screen set to its own board, a revoked or unclaimed one, another tenant's screen with the same id, a missing screen and a tenant that left are all the one 404.
3. **Pairing is the tenant board only.** `POST /screens` takes `boardScope` `tenant` only (a network at pairing is a 400 and stores nothing) and `ConfirmPairing` refuses a network board; the design's confirm step says the new screen "will show our organisation's capacity only". The network is chosen afterwards. This changes what R15 accepted (a `network` value with no network id, which meant nothing).
4. **Who may list and change it.** `GET /screens` and `PUT /screens/{deviceId}/board-scope`: the shift lead and the tenant administrator. The audit and the design name the administrator only; the lead already pairs screens, may read every network board, and the tenant administrator cannot sign in through the exchange yet (known issue TEN-043), so a rule of administrator-only would leave the setting unusable. Every other role is the one 404.
5. **The change.** Body `{"boardScope": "tenant" | "network", "networkId"?: "net-..."}` with `If-Match: W/"<scopeVersion>"` (none: 428; stale: 412) and an `Idempotency-Key` (the fast guard, and a durable record in the tenant's idempotency store so a replay after the cache entry is gone returns the first answer; the same key for another command is 409). It runs in the tenant's unit of work after the registry has confirmed the tenant's active membership of an active network (read first: a unit holds one scope). A network the tenant is not an active member of, one it left, an unknown one, an unknown or revoked screen and every other refusal are one 404 with one body, so a network id and who belongs to it are not discoverable. Setting what is already set changes nothing, writes nothing and keeps the version. A change writes one audit entry in the tenant's chain (`wall-screen-board-set`: the board, the network id and the new version; the administrator's role, no person). The audit's "at least one active grant in the network" is not required: a network with nothing shared yet has the designed empty board.
6. **The choice list is the server's.** `GET /screens` returns the tenant's screens and the networks it may choose (the registry's active memberships): the page never sends an id the server did not offer.
7. **Fallback with a flag, never blank and never silent.** A screen set to a network it can no longer read (its tenant left, the network is suspended or closed) reads `{"boardScope": "tenant", "fallback": true, "fallbackReason": "network-unavailable", "scopeVersion": n}` from `/screens/me/board-scope` and a 404 from `/screens/me/network-board`: the page shows its own board with the banner. The stored setting is kept, so the screen resumes the network if the tenant joins it again (hazard H-652).
8. **The stream.** `/screens/me/network-events` relays the network's own channel as `/network/{id}/events` does. The screen's record is read before the subscription opens and every 30 seconds; a screen whose setting changed, was revoked or whose tenant left is sent `scope-ended` and the stream closes. This replaces the audit's `scope.control` message: the re-check already closes the stream within 30 seconds, with no new message and no new channel.
9. **Not built here:** unpairing and re-pairing (no use case exists), a "last seen" time (no source), and the page. The list has no `lastSeen`.
