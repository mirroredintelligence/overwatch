## Decisions

### DEC-1190 `networkId` is the one allowed network input, on seven named read routes only (TEN-068; refines DEC-1100 Q11, TEN-044's guard)
Status: accepted (bundle WB10, under DEC-133). Affects: `lib/bff/inputGuard.ts`, `lib/bff/handler.ts` (`allowNetworkId`), `test/guards/bff-routes.test.ts`.
1. The input guard still refuses every field whose name starts with `tenant`, `scope`, `network` or `source`, in the query, the headers and a body. A route that needs to know which network a page is looking at says `allowNetworkId: true`; then ONLY the query key written exactly `networkId`, once, holding a network id of the back end's pattern, is let through. A header, a body key, a second `networkId`, `networkIds`, `network`, `network_id`, a value that is not a network id: all 400 before any work.
2. The seven routes are `board`, `directory`, `criteria`, `events`, `phones`, `system-now`, `week` under `/api/bff/network/`. The list route (`GET /api/bff/network`) takes none: it offers the networks. The generated test holds the list of seven and fails when a route outside it says `allowNetworkId` or one inside stops.
3. Why a query key and not a path or a session value: a viewer in more than one network chooses between them in the page, and a page has no other way to say which. The session cannot hold it (it would need a refresh path that does not exist: KI-585). The id is the opaque `net-...` the server offered; it appears in no address, cookie or storage of a page.

### DEC-1191 The availability check is made on every call and never kept; every refusal is the one 404 (TEN-068; DEC-134, audit D risk 6)
Status: accepted. Affects: `lib/network/availability.ts`, `lib/network/server.ts`, the seven routes.
1. Every data route first calls `GET /networks` with the session's token (the registry's answer: `networks_of`, not the token's `networks` claim, which only routes) and goes on only for a network in the answer. A tenant that is not a member, a member that left, an unknown id and an id never offered are one `FhirError(404)`; for each the network's own routes are NOT called, so no call carries a token to a network it cannot read (the leak canary's `network-non-member` rule stays clean). The answer is not cached: a member that leaves between two calls is refused on the second.
2. The routes say `idScoped: true`, so a 403 of the back end is the same 404. A malformed id or value is a 400 (it names nothing). A back end that fails is 503; a body that cannot be read is 502 with nothing of the body in the answer.
3. The stream route (`events`) asks the registry BEFORE it opens the upstream stream, relays only `network-board` (cut to `{changedAt}`, a UTC time) and `scope-ended` (cut to `{}`), never the tenant board's events on this stream nor the network's on the tenant's, forwards back end comments as the one fixed keep-alive, and closes the upstream when the browser goes away. The back end checks the registry again every 30 seconds while it is open.
4. One extra call per read is the price (`GET /networks`); a registry read is cheap and the board is cached per network at the back end.

### DEC-1192 The network pages are for five roles; the BFF takes the network's data through one parser that reads two shapes (TEN-068)
Status: accepted. `lib/auth/access.ts` guards the prefix `network` for advisor, clinical, lead, owner and exec (the back end's `NETWORK_VIEW_ROLES`); a wall has no network page (its network board is the screens' own route, TEN-067/072). `lib/network/parse.ts` is one strict parser per answer, used on the back end's JSON (snake_case, by the BFF) and on the BFF's (camelCase, by the page). It builds a new object from the fields it knows: a field it does not know never passes, a value it does not know is an error naming the field and never a value. `/network-admin` is NOT guarded by this prefix (TEN-080 gives it its own).
