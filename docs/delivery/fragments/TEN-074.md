# TEN-074: tenant offboarding, export and purge (W9A)

Back end: `application/use_cases/tenant_offboard.py` (`OffboardTenant`, `ExportTenant`, `CompleteOffboarding`), `tenant_purge.py` (`PurgeTenant`), `domain/rules/tenant_export.py`, `application/ports/outbound/tenant_export.py`, `adapters/outbound/graph_store/tenant_purge.py` (`Neo4jTenantData`), `adapters/outbound/export_files/file_storage.py`, `adapters/testing/memory_export_storage.py`, `purge_scope` on `RedisCache` and `InMemoryCache`, `bootstrap/lifecycle_operations.py`, `scripts/tenant_lifecycle.py`, `membership.py` (`LeaveAllNetworks`). No migration: no schema changed.

## Decisions

- DEC-968 Starting an offboarding leaves the networks first, then moves the record, and owns nothing. `OffboardTenant` ends every live membership of the tenant as a leave (an invitation is removed) through the same steps as `LeaveNetwork` (`LeaveAllNetworks`: the registry, the network scope, the records and `MemberRemoved`), **before** the record moves to `offboarding` (TEN-075's `StartTenantOffboarding`: compare and set, the edge told, the typed tenant id, its audit entry; `OffboardTenant` is what the operator's route and the script both run, `bootstrap/lifecycle_operations.py: build_offboard`, wired into `PlatformServices.offboard`): while the tenant is still active its outbox is relayed, so the network hears; a start that stopped is run again (what ended is not met twice; a record already `offboarding` only finishes what is left). A tenant that owns a network is refused with nothing changed (the owner cannot leave its own network: transfer or close it first). Once the record moves, the edge refuses the tenant's people and the workers skip it (a tenant that is not active has no sign-in, no prompts and no relay), so the tenant's administrator reads nothing while offboarding; the plan's "read-only mode with export enabled" is met by the operator's export being the tenant's way to its data, the stricter reading (the tenant-admin's read-only access during notice is TEN-075's, if wanted).
- DEC-969 The export package is every class of the tenant's data, or nothing. `ExportTenant` (an offboarding or offboarded tenant) reads the tenant's scope in pages (1000, [ASSUMED]) through the `TenantDataReader` port and writes, through the `ExportStorage` port, one file for each label set grouped by class (`<class>/<labels>.jsonl`, keys sorted, one JSON object a line, no `tenantId`), `relationships.jsonl`, and `manifest.json` (rows and SHA-256 of each file, the storage's own hash, a mismatch is an error; what was held back or left out by label set and count; the head of the audit chain; canonical JSON so the same package has the same manifest hash). The classes are `ExportClass` (directory and criteria, capacity reports, registrations, communications, cases and requests, people, alerts and flags, configuration, telemetry, support, audit chain). **Held back unless the tenant asked** (`include_protected`): the protected contacts and the text of safety concerns. **Never exported**: credentials, device and link-token hashes, sessions, support codes, idempotency and processed markers, the outbox and scheduled work. A label set that no class names (`UnclassifiedData`) refuses the whole export; a backbone element's label (`<Resource>_<Element>`) is classified by its resource; and a unit test keeps the table equal to the labels the registered statements name, so a new label cannot be added without a decision. The writer is the filesystem (`FileExportStorage`: atomic writes, names checked) until the tenant's chosen object store is a human decision. The audit entry names the package, the manifest hash and counts, never a value.
- DEC-970 A purge is guarded as the one irreversible act, and its audit is kept until the purge (DEC-271 item 6). Two different named platform operators, the tenant's id typed again, an offboarded tenant whose retention hold has passed (`purge_blockers`), and a dry run that counts by label set and changes nothing. The order is the safety: (1) the **tombstone** (both operators' references, the head of the tenant's audit chain (last hash and sequence), the export's manifest hash, the counts by label set) is appended to the platform's chain, and if that cannot be written nothing is deleted; (2) the record becomes `purged` by compare and set (nothing reopens it; a lost race deletes nothing); (3) the data is deleted in batches of 1000 by `tenantId` (`Q-TENANT-PURGE-DATA`: every node that is not the audit chain, `DETACH DELETE`); (4) the cache names of the scope are removed (`purge_scope`); (5) the audit chain is deleted last (`Q-TENANT-PURGE-AUDIT`, which deletes nothing while any other node of the tenant is left: the guard is in the statement); (6) nothing may be left; (7) a completion entry. A purge that stopped is finished by the same command on the `purged` tenant (two operators and the id again). The deletion is by `tenantId` and nothing else: another tenant, the network scope and the registry (the tenant's record, numbers, memberships and grants carry no `tenantId`) are out of its reach, shown on a real graph with two tenants. The tombstone and the completion entry go to the platform's hash chain (`container.platform_audit`, TEN-075), which the script and the purge use case share. Backups expire by their schedule (information governance to accept, H-T29): nothing here reaches them.
- DEC-971 Completing an offboarding quarantines the numbers. `CompleteOffboarding` needs the export delivered (the manifest hash of a package of **this** tenant in the storage) or the tenant's written waiver of it, and the 30-day notice over or the tenant's written waiver of the rest (`complete_offboarding`); the record becomes `offboarded` first by compare and set, then every active number becomes `quarantined` until the offboarding date plus 90 days (`number_quarantine_until`), so it cannot be given to another tenant; a repeat finishes the numbers that are still active. Closing the Twilio subaccount is a human step. The operator's commands are `scripts/tenant_lifecycle.py` (`network-create`, `offboard`, `export`, `complete-offboarding`, `purge`); it prints fixed words, ids and counts, never a value; a purge has no `--yes`, it needs `--second` and `--type-id`.

## Known issues

| id | what | where | trigger |
|---|---|---|---|
| TEN-074 | The export's `ExportStorage` is the file system; the object store the agreement names is not built, and the manifest hash must reach the tenant by another route | `file_storage.py` | the first real offboarding |
| TEN-074 | The graph reader pages by `elementId`, which is stable inside one export only if nothing writes to the tenant meanwhile: an offboarding tenant is blocked at the edge, but a workers' message in flight could write | `tenant_purge.py` | an export that runs while a message of the tenant is being processed |
| TEN-074 | The export writes whole files in memory (a label set's rows); a very large tenant needs streaming | `tenant_offboard.py` | a tenant of millions of nodes |
| TEN-074 | The network's projections of a purged tenant stay (marked with the date it left): organisational records kept by the network's retention, which information governance has not set | `network scope` | the network's retention schedule |
| TEN-074 | Purge does not remove the tenant's Redis keys of other families than the scope's own (`diucs:<tenant>:*`); it removes that prefix only | `redis_cache.py` | a key written under another prefix by a later task |
| TEN-074 | `purge` cannot be undone and has no restore path in the application; a mistaken purge is a restore from backup by two operators (a runbook step, not a tested one) | `docs/delivery/runbooks/tenant-offboarding.md` | a purge of the wrong tenant |
