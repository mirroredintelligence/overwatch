# TEN-075: operator and tenant-administrator API routes, the operator session, the support-access ticket flow and the platform audit adapter (bundle W9C)

Bundle W9C, branch `task/build-W9C`, back end only. Number blocks used: decisions DEC-1000 to DEC-1012, hazards H-670 to H-678, migration 0190 (of 0190 to 0194). The screens that follow (TEN-076 tenant administration, TEN-083 operator console, the support request and approval screens) read `docs/delivery/fragments/W9C-routes.md` for the exact paths and shapes.

U40 and U41 were read for the ticket request and approval the brief asked about. Neither specifies one: U40 is the clinical advice request and U41 the safety concern and problem report. The only earlier ticket is R18's in-tenant one (DEC-206 item 2, DEC-335 item 8: support asks on a session, a lead approves). This bundle builds the cross-tenant ticket instead (DEC-1003) and leaves R18's routes as they were (known issue W9C-K3).

## Decisions

## DEC-1000 The operator door: an operator token is for `/platform` only, and an operator-only route binds the tenant its path names after the token and the role are checked (TEN-075, TEN-043, DEC-134 items 4 and 5, refines DEC-130 item 6 for the operator)
Status: accepted (W9C, under DEC-133).

1. `current_operator` decodes a bearer token of the audience `diucs-ops` (`decode_operator_token`) and is a 401 for every other: a tenant token, a token with no audience or another, one that carries a tenant, epoch, service or device claim, a role no operator has, no subject, no or a text expiry, another secret, algorithm `none`. `require_operator(*roles)` adds the role: another operator role is the non-revealing 404. The tenant door (`current_actor`) already refuses an operator token (audience), so an operator token is a 401 on every `/tenant`, `/fhir` and other tenant route.
2. The operator's token names no tenant, so an operator route that acts on a tenant takes the tenant from the PATH (`/platform/tenants/{id}/...`) and `operator_in_tenant` binds it for that request alone, after the token and the role are checked (the role is `platform-operator` only). The tenant is the target of the act, never a source of authority: the operator has no data access (what its use cases touch in a tenant is the tenant's structure and its audit chain), a path that is not a tenant id is the 404 of a route that is not there (never a 400 that says what an id looks like), and a tenant the registry does not know is refused by the use case before it writes. `auth.py` was already a binding module (`BINDING_MODULES`).
3. A support person names the tenant of a ticket in the path too, but no scope is bound in the route: `CrossTenantGuard`, the one binder of a tenant a platform principal names, checks the principal and the directory before it binds anything (DEC-528 item 7).
4. No body names a tenant (`extra="forbid"` on every body). The tenant of a tenant route is the signed claim and nothing else.
5. Tests: `test_routes_platform.py` (13 tenant roles are 401 on every platform route; the 11 roles no operator has, forged into an operator-audience token, are 401; the two operator roles against every route with a tripwire that shows a refused role never reaches a service and a permitted one does; 17 claim negatives), `test_routes_tenant.py` (13 roles against every tenant route; operator tokens 401), `test_edge_binding.py` (every platform route is on the operator door and not the tenant door; the binder is on exactly the routes that act on one tenant as the operator; every tenant route takes the actor).

## DEC-1001 The platform's own records are a platform scope with their own labels, three more statement groups on the digest-pinned list, one migration (TEN-075, TEN-028, DEC-163, refines DEC-529)
Status: accepted (W9C).

1. Three labels carry no `tenantId`, like the registry: `PlatformAuditHead`, `PlatformAuditEntry`, `SupportAccessTicket` (`PLATFORM_RECORD_LABELS`, added to `REGISTRY_LABELS` so the start-up invariant check does not count them as nodes that lost their tenant). Only a platform statement may name them (a global statement may not: they are not on `GLOBAL_STATEMENT_LABELS`; a test proves it).
2. Twelve platform statements are added to `PLATFORM_QUERY_IDS` with a reason and a SHA-256 pin each (`PLATFORM_STATEMENTS`), reviewed like the seven registry ones: `Q-TENANT-REG-LIST`, `Q-TENANT-REG-GET` (reads), `Q-PLATFORM-AUDIT-LOCK`, `-APPEND`, `-ENTRIES`, `-HEAD`, and `Q-SUPPORT-TICKET-ADD`, `-OF-TENANT`, `-OF-PRINCIPAL`, `Q-SUPPORT-TICKETS-OF-TENANT`, `-OF-PRINCIPAL`, `Q-SUPPORT-TICKET-MOVE`. Fixed text, no `$tenant`, no delete or call, run only through `run_platform_query`, only from `platform_audit.py`, `support_ticket_store.py` and `tenant_registry.py` (the architecture lists name them), built only by the composition root. `test_platform_statements.py` pins every text.
3. Migration `0190_platform_records` (expand only, one idempotent statement per key): unique `PlatformAuditHead.id`, unique `PlatformAuditEntry.seq`, unique `SupportAccessTicket.id`, indexes on `(forTenant, requestedAt)` and `(requestedBy, requestedAt)`. `migrations_platform.py` is assembled after the contract migration (a network-like expand step on labels that did not exist).
4. Why the platform scope and not a tenant's for tickets: a ticket is read from two sides (the support person lists their own across tenants; the administrator lists what names their tenant), so one record with one state moved by compare and set avoids a copy that falls out of step, and a tenant scope cannot be listed across tenants. The tenant side always passes the BOUND tenant to the statement (`forTenant`), the person side the principal's reference, and a move matches the tenant and the state read, so another tenant's ticket is never matched. The tenant's own chain also holds every step (DEC-1004).
5. `Q-TENANT-REG-GET` has its own text (it also returns `t.id`) because the recording test connection finds a statement by its text and `Q-TENANT-GET` already has the plain one.
6. Tests: `test_platform_statements.py`, `test_platform_records.py` (unit, recording connection), `test_migrations_platform.py`, the updated migration, contract and tenant migration pins, `tests/integration/graph_store/test_platform_records.py` (run, private container).

## DEC-1002 The platform audit chain is a hash chain in the platform scope, written by the guard, the lifecycle routes and the operator sign-in (TEN-075, TEN-084, DEC-529, audit F 2.4)
Status: accepted (W9C); the graph adapter DEC-529 deferred is built.

1. `Neo4jPlatformAudit` implements `PlatformAudit` and `PlatformAuditReader`: the same link as a tenant's (`sha256(previous_hash + canonical entry)`), one `PlatformAuditHead` and the `PlatformAuditEntry` nodes after it, from a genesis of its own (`genesis_hash_for("platform")`, a scope id no tenant can have, so a tenant's chain cannot be grafted on). An append is one write transaction: the lock statement writes the head (creating it on first use) and reads where the chain stands, the append statement adds the link only when the head is still at that sequence and moves it. A failed append raises. `verify` walks the chain, recomputes every hash and compares the denormalised properties with the hashed text and the head with the last link.
2. `PlatformAuditEntry.tenant_id` may now be `None`: an entry about the platform itself (an operator signing in) names no tenant. `PlatformAuditRecord` and `PlatformAuditReader` are new; `PlatformAuditLog` is both ports as the container holds them.
3. What is written: every step of a support ticket and access (the guard, both chains, DEC-528 item 5), the operator's lifecycle steps (`tenant-created`, `-host-set`, `-number-recorded`, `-number-tested`, `-references-recorded`, `-directory-verified`, `-admin-invited`, `-activated`, `-suspended`, `-resumed`, `-offboarding-started`, each with a small snapshot: a status, an epoch, a mode and reason word, never a number, host, mobile or reference value), and every operator sign-in (`operator-signed-in`, the account reference and the role).
4. A lifecycle step is recorded AFTER it is done: the lifecycle use cases write in two places that cannot share a transaction (the registry and the tenant's scope), and a platform chain that is down cannot undo them. The tenant's own chain already holds the step (the use cases write it). The answer carries `recorded: true|false`, and a failure is logged by class and never silent (H-670). A sign-in is the opposite: it is recorded BEFORE the token is returned, and one that cannot be recorded gets no token (a fixed 503, `Retry-After`), because the chain is the operator's record of who was let in.
5. Read by the operator only: `GET /platform/audit` (a page after a sequence, oldest first) and `GET /platform/audit/verification`.

## DEC-1003 The support-access ticket: a request, a decision and the guard's code, with no standing access (TEN-075, TEN-084, DEC-134 item 5, DEC-136 item 6, audit F 4.2)
Status: accepted (W9C).

1. The flow: a support person (an operator token of role `support`) requests access to ONE active tenant with a reason (`POST /platform/tenants/{id}/support-tickets`); the tenant's administrator approves or refuses; an approval issues the guard's one-time code (`issue_code`); the support person opens with the code (`POST /platform/support-tickets/{id}/access`), the guard opens ONE access for ONE tenant and an hour; they end it, or the administrator revokes it, or it lapses. The ticket is not access: it is the request and the record of the decision.
2. The states and their times (`domain/rules/support_ticket.py`): `pending` (lapses after 24 hours, [ASSUMED]) to `approved` (the code's four hours), `refused`, `cancelled` (by the requester, only while pending); `approved` to `opened` (the access's hour), `revoked`; `opened` to `ended`, `revoked`. A live ticket whose time has come READS as `expired` whatever was stored (`effective_state`), so nothing has to run for an expiry to take effect, and an expired ticket moves nowhere. A finished ticket moves nowhere.
3. The reason is a fixed code (`security-incident`, `clinical-safety`, `service-fault`, `configuration`, `user-request`, `other`) and a plain sentence of 10 to 200 characters: letters, digits and `. , ' & ( ) + -` only, at most six digits (the patient-data guard finds a postcode, an NHS number and a titled name but not a phone number), nothing the guard recognises. The optional reference is the requester's help-desk number (letters, digits, hyphens, 32). The reason text is in the ticket and in NEITHER audit chain (the chains name the reason code).
4. The code is returned ONCE, in the answer to the administrator's approval, and is never stored or cached: the administrator gives it to the support person (spoken or typed, as O06's code). The ticket keeps the keyed hash the grant is held under (`IssuedCode.code_hash`), which is what lets a refusal, a revocation and a failed approval take the code back (`CrossTenantGuard.withdraw_code`) and what lets the opening check the code is THIS ticket's (a code issued for another ticket opens nothing under it, the access is ended at once). The code opens only for the person who requested the ticket (their ticket, their principal). A lost approval answer is handled by revoking and asking again (H-671): a second approval would be a second code. The approval is not replay-cached (a repeat is a 409).
5. One live ticket per person and tenant (a second request is a 409 until the first is finished or has lapsed); another tenant or person may ask. The support person lists only their own tickets; the administrator only the tickets that name their tenant; another tenant's ticket and another person's read as not found; every refusal the support person sees is the guard's one `CrossTenantDenied` (the 404 of a route that is not there). A tenant that is not ACTIVE (suspended, provisioning, offboarding, unknown) cannot be asked.
6. The guard gains, additively: `IssuedCode.code_hash` (never in its repr), `withdraw_code`, `note_ticket` (a support person's step to both chains, platform first, the tenant checked against the directory) and `note_decision` (the administrator's step to both chains). The use cases bind nothing themselves: the guard stays the one binder (`BINDING_MODULES` is unchanged). `UseTicketAccess` (`guard.authorise` for a ticket that is open) is built and tested for the support routes that will read a tenant's data; no HTTP route calls it yet (known issue W9C-K3).
7. Tests: `test_support_ticket.py`, `test_cross_tenant_tickets.py` (56 cases, real guard, mutants killed: the grant-hash check, the withdrawal on a lost race, the revocation's withdrawal, the approved-state check, the live-ticket check, the tenant filter), the new cases of `test_cross_tenant_guard.py`, `test_platform_tenant_stack.py` (real graph, real guard, real chains).

## DEC-1004 Order of effects and compensation in the ticket flow (TEN-075, TEN-084)
Status: accepted (W9C).

What gives access is done last and undone first, and a chain that cannot be written never leaves access standing. A request adds the ticket then writes both chains, and withdraws the ticket if they cannot be written. An approval issues the code, moves the ticket by compare and set, writes both chains; a lost race or a failure withdraws the code, and a failure at the last step also revokes the ticket. An opening is the guard's own (it writes both chains and removes the access when it cannot) and the ticket moves after it; a ticket that cannot take the access ends it. A revocation, an end, a refusal and a cancellation take the access (or the code) away FIRST and record after. A revocation of an open access whose cache key is already gone (ended, lost) still marks the ticket revoked.

## DEC-1005 The operator console's session is the operator token, read at `GET /platform/session` (TEN-075, TEN-043)
Status: accepted (W9C).

1. The session answers `{role, accountRef, expiresAt, permissions}`: who is signed in (the opaque account reference derived from the operator directory, never a name), the role, when the token ends, and what the role may do (`tenants:list`, `tenants:read`, `tenants:provision`, `tenants:lifecycle`, `audit:read` for the operator; `tenants:list`, `support:request` for support), so the console draws only what it can use. It reads the token and asks no service. It holds no secret, no tenant and not the token.
2. The token is the session: nothing is held at the back end, so signing out is the console dropping it, and a new session is a new exchange (`/auth/operator-token`, one hour, `OPERATOR_TOKEN_LIFETIME`). There is no refresh and no server-side revocation (known issue W9C-K5); a suspended operator account is stopped by the operator directory at the next exchange.
3. The exchange records the sign-in in the platform chain (DEC-1002 item 4) when `ExchangeDeps.platform_audit` is set; `IssuedToken` gains `account_ref`.

## DEC-1006 Starting an offboarding is built; the rest of offboarding is TEN-074 (TEN-075, TEN-074, DEC-136 item 10)
Status: accepted (W9C).

`StartTenantOffboarding` moves an ACTIVE or SUSPENDED tenant to `offboarding` (`start_offboarding`: the 30-day notice begins, a suspension's fields are cleared) by compare and set on the epoch and status read, tells the serving process (`on_changed`), and writes the step with the notice end to the tenant's chain. The operator must type the tenant's own id (`confirmTenantId`). Export, the end of network memberships, the number quarantine, the completion of the notice and the two-operator purge are TEN-074's and are not started. Until TEN-074 gives the administrator a read-only door for the export, an offboarding tenant is closed at the edge for every role (`_status_allows`), so starting one ends the tenant's sign-in (known issue W9C-K2, H-675). The epoch is not raised (the domain function does not): the edge refuses on the status. `scripts/provision_tenant.py` gains `offboard TENANT --confirm TENANT`.

## DEC-1007 The tenant administrator's API (TEN-075, TEN-026, TEN-065, DEC-134 item 4, DEC-136 item 10)
Status: accepted (W9C).

1. Reads: the overview (the record with its time zone, the host, the configuration in force, contacts, channels, retention, the directory binding, the role mappings), the setting registry (key, kind, unit, bounds, default, safety class, scope, whether activation needs it), the versions newest first with their diff, the access log.
2. Changes are the TEN-026 use cases behind the administrator role (`CONFIGURATION_ROLES = {tenant-admin}` is passed by the composition root): drafts from the version in force (`basedOn`, a stale one is a 409) and one approval at a time, two people who are not the author for a clinical key; contacts, retention (defaults or one rule per class), the directory (pending until the operator verifies it), role mappings. A setting is on the wire as JSON (a time as `HH:MM`, a set of codes as a list), made the exact type the row demands, and the use case still checks the bounds.
3. A channel is shown without the reference of its secret (`hasSecret`). The TEXT channel is the platform operator's (the number, the Twilio account and the token reference are the platform's business with Twilio, DEC-131 item 4): `POST/PUT /tenant/channels` refuse `kind: sms` (400, "set by the platform operator"). The administrator manages the email channel and its sender label; a secret reference must be the tenant's own (`check_secret_ref`).
4. A directory group maps to a staff role, never to `tenant-admin` (`ENTRA_MAPPABLE_ROLES`): an administrator comes from the first-administrator invitation. A tenant suspended read-only lets its administrator read and refuses every write at the edge.
5. Every write needs an `Idempotency-Key` and is replayed from the 24-hour cache.

## DEC-1008 The operator access log is read from the tenant's own chain (TEN-075, audit F 4.2)
Status: accepted (W9C).

`GET /tenant/access-log` answers what the platform's own people did in this tenant: the entries of the operator's lifecycle use cases (`CreateTenant` to `StartTenantOffboarding`, `InviteTenantAdmin`) and of the support guard and ticket (`OpenCrossTenantAccess`, `UseCrossTenantAccess`, `EndCrossTenantAccess`, `RevokeCrossTenantAccess`, `SupportAccessTicket`) whose actor role is `platform-operator` or `support`, newest first: time, use case, action, role, the actor's opaque reference, the entity ids and the small snapshot. Default 90 days, at most 400, at most 200 entries. It reads the tenant's real chain (`records_between`), so the tenant reads what was written and cannot change it. The administrator's own steps on a ticket are in the chain but are not this log.

## DEC-1009 A support person lists tenants by id, name and status; the operator by more (TEN-075)
Status: accepted (W9C).

`GET /platform/tenants` is the registry's list, whatever the status. A support person needs to name the tenant of a ticket and gets `{id, displayName, status}` and nothing else; the operator also gets the type, the host and the activation date; the detail (`GET /platform/tenants/{id}`: the record with its references, host, directory, numbers and what activation waits for) is the operator's. A number is shown (the tenant's business line and Twilio account, never a person's) without the reference of its auth token.

## DEC-1010 Wiring: the container carries the guard; a serving process installs the routes' services (TEN-075, TEN-084)
Status: accepted (W9C).

`Container` gains `platform_audit` (`Neo4jPlatformAudit`), `support_tickets` (`Neo4jSupportTickets`) and `cross_tenant_guard` (built on the container's units of work, cache, clock, ids, directory and platform chain, with the TENANT-KEYED secret store so the support-code key is derived for each tenant), in `build()` and `build_for_tests()`. `bootstrap/platform_services.py` builds `PlatformServices` and `TenantAdminServices` (`application/platform_services.py`) on a container, reusing the provisioning script's use cases (`build_provisioning` takes `on_changed` and builds `offboard`), and `install_platform_routes(app, container)` sets `app.state.platform_services` and `app.state.tenant_admin_services` with the edge's `forget_tenant` passed to suspend, resume and offboard so they take effect at the edge of this process at once. With no services set every route fails closed with a 500. No serving main exists yet (known issue W9C-K1): it must call `install_platform_routes` after `create_app`, set `app.state.secrets` (`bff-jwt`, `account-ref`, `support-code`), `app.state.cache` and `app.state.token_exchange` with `platform_audit=container.platform_audit`.

## DEC-1011 Idempotency on the new routes (TEN-075, DEC-105)
Status: accepted (W9C).

An `Idempotency-Key` is required on every write. An operator write and a tenant administrator write are replayed from the 24-hour tenant-qualified cache (a different body under the key is a 422). A support person's write is validated for a key but not cached: there is no tenant to qualify the key with, and the ticket's own state makes a repeat harmless (a second request is a 409, a second cancellation an invalid move, a second opening a refused code). The approval of a ticket is not cached because its answer holds the code. A POST or PUT with no body must still say `Content-Type: application/json` (the body-type check runs before routing; send `{}`).

## DEC-1012 Architecture and test-support changes this bundle makes (TEN-075)
Status: accepted (W9C).

`test_tenant_registry_access.py`: the platform runners are `tenant_registry.py`, `platform_audit.py` and `support_ticket_store.py`, each binds nothing and runs only platform statements and is built only by the composition root; the operator use cases that name `TenantRegistry` include `tenant_offboarding.py` and `platform_tenants.py`. `test_single_execution_point.py`: `support_ticket_store` may take a tenant id (it reads and moves by the tenant a ticket names and sends no tenant to a statement). `test_edge_binding.py`: a route on the operator door is judged by its own tests, not exempted. `tests/support/tenant_seed.py` (`UNSTAMPED_OK`) and the registry label tests list the three platform labels; `tests/support/registry_connection.py` finds the platform statements.
