# TEN-079: network and grant administration API (W9A)

Back end: `adapters/inbound/fhir_rest/routes_network_admin.py`, mounted in `app.py`. The paths, bodies and answers are in `W9A-routes.md`.

## Decisions

- DEC-967 The API is a thin layer: roles at the edge, the tenant from the token, one use case a route. Twenty-three routes at the root under `/network-admin` (not FHIR), JSON, `Cache-Control: no-store`. A role that may not use a route is the API's one 404 (`require_role`), the platform operator a 401 (no data access), and a record that is not the caller's the same 404 as a missing one (tests compare the bodies). Bodies are closed models (`extra=forbid`, strict types): a body, query, header or cookie that names a tenant, a network claim or an account is refused or ignored, never read. The `networks` claim of the token is **not** used (it routes the read routes of TEN-059 only): the registry is asked on every call, so a member that left reads nothing though its token lists the network. There is no `Idempotency-Key`: each command is repeatable by its state (an approval by the same person, an end of an ended grant, an invitation already accepted), so a client retries; a POST still needs `Content-Type: application/json` as every POST of the API. Services are on `app.state.network_admin` (a dataclass `NetworkAdminServices`); with none the routes fail closed with a 500. No body names a tenant, an account reference, a person or an agreement's content: organisations are named, handles are the registry's ids.
