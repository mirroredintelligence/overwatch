# TEN-080: network administration screens, and how a network administrator signs in (bundle WB12)

Back end and front end. Number blocks used: decisions DEC-1260 to DEC-1266, hazards H-900 to H-909, no migration (0225 to 0229 unused). The exact routes and shapes are in `WB12-routes.md`. Screens: `/network-admin` (members, the agreement, health), `/network-admin/grants`, `/network-admin/listings`, `/network-admin/history`. The design is `docs/design/network-ui.md` sections 7 and 15.

## Decisions

## DEC-1260 A network administrator is a role of the network owner's own directory, given only to a tenant that owns an active network (TEN-080, TEN-043, DEC-132 item 2, DEC-134 item 4, DEC-136 item 6, refines DEC-523 item 3)
Status: accepted (WB12, under DEC-133).

The staff token exchange gave `network-admin` no session (W9D: "network-admin still gets none"), so nobody could sign in to run a network. The network owner is a lead organisation, a tenant, so its administrators are in its own directory like its other staff.

1. `ENTRA_MAPPABLE_ROLES` gains `network-admin` (and only that): a group of a tenant's directory may be mapped to it. The tenant administrator stays unmappable (DEC-1007 item 4: it comes from the first administrator's invitation).
2. The role is given only while the HOST's tenant owns an active network. `staff_role(mappings, groups, owns_network=...)` counts `network-admin` only when `owns_network is True` (a damaged value is not ownership); a person whose other groups give another role falls to that role, otherwise the exchange's one refusal. The exchange asks the registry (`NetworkOwnership.owns_active_network`, `RegistryNetworkOwnership` over `memberships_of` and `get_network`: an active `owner` row in a network whose `owner_tenant_id` is the tenant and whose status is active) and only when the groups would give `network-admin` if the tenant owned a network, so no other sign-in depends on the registry. A registry that fails is a fault (an exception, no token, nothing audited), not a refusal. A process with no registry wired never gives the role (`ExchangeDeps.ownership`, `build_network_ownership`).
3. The token names no network. Every route of `/network-admin` asks the registry and `require_owner_of` compares the network's owner with the token's tenant, so a network administrator of network A reads and changes nothing of network B (the same 404 as a missing network), and a member's `network-admin` mapping is stored but gives nothing.
4. How the first mapping is made. The tenant administrator who could make one through `PUT /tenant/role-mappings` cannot sign in yet (known issue KI-532, W9C), so the platform operator names the owner's first group: `scripts/tenant_lifecycle.py --operator NAME network-admin-group OWNER-TENANT GROUP-GUID` (use case `MapNetworkAdminGroup`: operator only, bound to the one tenant, which must own an active network or it is the one `NotFound`, a group that already gives another role is a `Conflict`, a repeat changes nothing, one audit entry with the role and never the group). Later ones are the owner's tenant administrator's, through the ordinary route.
5. Front end. `STAFF_ROLES` gains `network-admin` (the exchange accepts it, `NO_PAGES_YET` is gone); `/network-admin` is guarded for that role alone in `lib/auth/access.ts` (home `/network-admin`), and the network pages (`/network`) are not for it.

Tests (a negative for every claim): `backend/tests/unit/application/use_cases/test_exchange_token.py` (owner gets it for its own host, the registry asked about the host's tenant only, another owner's tenant gives nothing, a tenant with no network the one refusal with no audit, a person with another group falls to it, no registry never, the registry not asked for anyone else, a failing registry no token, a retired mapping, an app role the identity claims is never read, the other directory, a blocked owner), `test_network_admin_sign_in.py` (ownership, the operator's mapping), `tests/unit/domain/rules/test_token_exchange_rules.py`, `test_tenant_records.py`, `tests/unit/adapters/inbound/fhir_rest/test_routes_auth.py`; on a real graph `tests/integration/application/test_network_admin_sign_in.py` (the role not before the network exists, a member and an outsider the one refusal, the issued token administers its own network and not another owner's, read and write, the same 404 body; the mapping in the owner's scope only); front end `lib/auth/exchange.test.ts`, `access.test.ts`, `access.network.test.ts`, `proxy.test.ts`.

## DEC-1261 The BFF routes of the network administration: the registry chooses the network, the browser may name an offered one as `networkId`, and the guard's list is extended on purpose (TEN-080, TEN-044, TEN-068)
Status: accepted (WB12).

1. Every route is `withBff` with `roles: ['network-admin']`, calls the root `/network-admin/...` with the person's own token, rebuilds each answer field by field (`lib/networkAdmin/views.ts`: no tenant id, no account reference, nothing the back end adds later, a shape that is not the one expected a fixed 502) and answers `private, no-store`.
2. The network is never taken from the browser as an authority. Each route first asks the registry (`GET /network-admin/networks`) and goes on for a network that organisation OWNS and is active in (`ownedNetworks`); the id reaches the back end only in the path of the call after that. The browser may name one of the networks the server offered as the query key `networkId` (`GET /api/bff/network-admin/networks` lists them), on the routes that need a network: with none named and exactly one owned, that one; several, a 400; one not offered or not owned, the one 404 (the same as a stranger's) with no network route called. The routes of a grant (`grants/[id]/approve|decline`) name no network (the grant's own handle; the back end checks the owner) and refuse the key.
3. The input guard's named list is extended deliberately: `TAKES_NETWORK_ID` in `test/guards/bff-routes.test.ts` names the ten routes that say `allowNetworkId` (and, for TEN-081, three more); the test fails if another route says it or one stops. Any other key naming a tenant, a scope or a network, any header and any body key stays a 400 before any work.
4. Ids: a record id is shape-checked (`RECORD_ID`) before a path is built, a bad one is the one 404; a membership, grant or listing is named by the registry's own handle.
5. Bodies are whitelisted field by field (`lib/networkAdmin/bodies.ts`): an unknown field is a 400; a reason is one of the seven codes; the agreement is a reference (`[A-Za-z0-9][A-Za-z0-9._/-]{0,63}`) and a whole version, never its content; an action that takes nothing refuses a body.

## DEC-1262 What the owner's screens show, and where they depart from the design (TEN-080, design N1, DEC-136 items 3, 4 and 14)
Status: accepted (WB12).

1. Members: all rows (closed ones too), status in words, joined and left dates, the version accepted and, when behind, `Agreement version {n} is available`. Invite by `Organisation code`, end a membership (an invited or active member, never the owner's own row), the agreement (reference and version only), a History link.
2. Ending a membership is one administrator's act, as the back end built it (TEN-077). The design (and audit F section 4.5) ask for a second administrator's confirmation; the dialog does not say so, because the line would be untrue (known issue WB12-K1).
3. Health shows, for each organisation, `Sharing`, `Not sharing` or `Ended on {date}` for each kind: states and dates, never a row (the projection status read). `Last update received`, `Delay` and `Updates refused` are not shown: the registry holds none of them and nothing is invented (known issue WB12-K2).
4. Grants: the owner approves or declines a grant that still waits for it; it never ends a member's grant. The `Approval` words are the design's plus three for states it does not name (`Waiting for the organisation and the network owner`, `Approved, starts on {date}`, `Replaced by a newer version`). A 409 on an approval says that the same person cannot give both approvals. A decline asks first.
5. Listings: `Admit`/`Decline` for a waiting one, `Pause` for an admitted one, `Reinstate` for a paused one. `Decline` and `Pause` ask for a reason from the fixed list (a select, never free text) and for confirmation. A listing carries no service name, so `Service` is the organisation's own reference for it (known issue WB12-K3).
6. There is no per-version criteria endorsement screen: DEC-136 item 4 says the owner's approval of the grant covers the scope.
7. A `NetworkAdminHistory` page (`/network-admin/history`) lists, read only, the members that left or were removed and the grants that ended, lapsed, were replaced or were declined, with their dates.
8. The page says what the owner does not see (the design's one line). No tenant id, handle or person's reference is in the DOM (a test searches it).
