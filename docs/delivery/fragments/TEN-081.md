# TEN-081: grant approval and sharing transparency screens, for the member's administrator (bundle WB12)

Back end (the sharing read) and front end. Number blocks used: decisions DEC-1263 to DEC-1266, hazards H-910 to H-916, no migration, no new graph statement (the read reuses the registered `Q-PROJ-SOURCE-GET` through `NetworkView.source`). The exact routes and shapes are in `WB12-routes.md`. Screen: `/admin/sharing`. The design is `docs/design/network-ui.md` sections 8 and 15.

## Decisions

## DEC-1263 `GET /network-admin/sharing`: what the organisation shares with each network, and the exact keys that may leave a tenant (TEN-081, DEC-132 items 3, 4 and 6, DEC-134 item 6)
Status: accepted (WB12, under DEC-133).

The screen needs "what is shared with whom" and the fields that leave. Neither existed as a read for a member (the owner's projection status is for the owner).

1. The tenant administrator only (the role matrix of `test_network_admin_routes.py` gains the route: every other role gets the API's one 404, the platform operator a 401). The organisation is the token's: a body, query or header naming a tenant is ignored (tested).
2. `QueryMemberSharing` (`application/use_cases/member_sharing.py`): for every membership of the actor's tenant (any status) the network, the membership (status, joined, left, the agreement and the version accepted, whether it is behind), and, for an ACTIVE membership only, what the network scope holds of THIS organisation for each kind: open, or ended with the date and the reason, read in a read-only unit bound to that network with `network_view.source(actor.tenant_id, kind)`. The source tenant is the actor's own and no caller input; another member's sources are never read into the answer (two-tenant tests, on the fake registry and on a real graph). A member that left or an invitation not yet accepted has no live state. No new graph statement: `Q-PROJ-SOURCE-GET` is registered with its scenario.
3. The allowlist is the one the projection enforces: `allowlist_fields()` is `body_keys(kind)` for each kind, sorted, with `PROJECTION_ALLOWLIST_VERSION`, so the screen cannot list a field that does not travel or hide one that does. A test holds that no field name carries a reporter, pin, token, booking, case, audit, comment or reason.
4. Answer: `{ allowlist: { version, scopes: { capacity, directory, criteria: [field...] } }, networks: [{ id, name, membership_id, membership_status, joined_at, left_at, agreement_reference, agreement_version, accepted_agreement_version, agreement_behind, shared: [{ scope, status, ended_at, end_reason }] }] }`.

## DEC-1264 The organisation code is the organisation's own id, shown only to its own administrator (TEN-080, TEN-081, DEC-136 item 3, design N1 NetworkMemberAdd)
Status: accepted (WB12).

The design invites a member by an `Organisation code` "on the organisation's administration page", and no page showed one. The code is the organisation's tenant id (the back end's `tenant_id` of the invitation). `/admin/sharing` shows it under `Your organisation code`, with "Give this code to the network owner so that they can invite your organisation." The BFF answers it from the SESSION's tenant (the signed token's), only to the tenant administrator, only in the page body: never in an address, a header, a cookie, storage or telemetry. It identifies a legal entity that already has a public sub-domain (DEC-134 item 3), and the owner learns nothing of other organisations from it: an unknown, ineligible and already invited code are one answer.

## DEC-1265 The sharing screen: five states and one more, the field list fails closed, and nothing the browser holds chooses a network or a membership (TEN-081, design N2)
Status: accepted (WB12).

1. Each kind has a card with the design's states (`Sharing since {date}`, `Waiting for your approval`, `Waiting for the network owner`, `Not sharing`, `Ended on {date}`) and one more, `Approved. Sharing starts on {date}`, for an approved grant whose window has not started (`Sharing since` would be untrue). What needs the organisation comes first: a newer version waiting for approval shows over the one in force, which is still said. A declined grant reads `Not sharing`. `lib/networkAdmin/sharing.ts` works the state out from the organisation's own grants and what the network holds; it is pure and tested for every status.
2. The cards say whether the network is getting the kind (`The network is receiving this.`, `The network stopped receiving this on {date}.`, `Nothing has arrived on the network yet.`) from the projection source, never from the grant alone.
3. `AllowlistFields` renders the labels of the design's table from the back end's allowlist (`lib/networkAdmin/fieldLabels.ts`; the internal references have no label and are never listed; no field's own name is printed). A field the back end sends with no sentence cannot be described: nothing is listed, the card says "We could not list the fields that are shared. Do not approve this until it is fixed.", and Approve and Propose are not offered for that kind (Decline and End still are). `fieldLabels.test.ts` fails when a field of the back end's list has no label or a label has no field, using the list the back end's converter wrote into the fixture.
4. Approve, decline, end, propose, leave and accept an agreement version call the BFF (`/api/bff/sharing/...`). A grant is named by its own handle; the network is the registry's answer for the organisation (the page passes the id it was offered as `networkId`); an agreement is accepted by the NETWORK the server finds waiting for it (an invitation, or a newer version), never by a membership handle the browser holds. Decline and end ask first (dialogs, focus returned). A 409 on an approval says that the same person cannot give both approvals. The owner of a network is not offered `Leave network` (it cannot leave its own).
5. The browser's key for the kind to propose is `kind`: the input guard refuses every key that names a scope (a scope is a tenant's or a network's), so the back end's `scope` cannot be a browser key.
6. History is a section of the same page (`#history`, link `SHARE-HISTORY-LINK`): one line for each grant in force or ended, `{Kind}: Shared with {Network} since {date}` and `. Ended on {date}`; `Nothing here yet.` when nothing was shared.
7. The page opens with the design's sentence (sharing is read only, other organisations see only the fields listed, no patient information is ever shared) and the never-shared sentence, once.

## DEC-1266 TEN-081 is reachable by a real sign-in only when the first administrator's invitation is consumed (KI-532), and nothing here changes that (TEN-081, TEN-076, DEC-505, DEC-1007 item 4)
Status: accepted (WB12).

The tenant administrator comes from the first administrator's invitation, which no code consumes yet (the sign-in tasks' and the gap-triage bundle B3's, item 5). The screen is built for the tenant administrator's session as `/admin` is (TEN-076); this bundle neither widens `ENTRA_MAPPABLE_ROLES` to the tenant administrator (DEC-1007 item 4) nor builds the consumption (it is another bundle's), and records the dependency as WB12-K6 (in `TEN-080.md`).
