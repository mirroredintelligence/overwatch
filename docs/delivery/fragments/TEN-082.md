## Decisions

### DEC-982 The network pressure alert is a state read from the network board; no task, no push, no write in any tenant (TEN-082, amends DEC-136 item 9 only as far as stated)
Status: accepted (build wave 9, bundle W9B; under DEC-133). Affects: `application/use_cases/network_lead_views.py` (`NetworkPressureAlert`), `routes_network_views.py`, the known issue U34 ("the network-pressure alert is not built (owner decision)").

1. The owner's instruction for this wave is to build the network pressure alert; DEC-136 item 9 says alerts are tenant-only and "not driven by network events for now", and the design (`network-ui.md` section 9) removes any network alert from the exec screens. The two are reconciled by what an alert is here: a state, not a delivery. `GET /network/{id}/system-now` carries `alert: {raised, level, limited_or_worse, watch_from, high_from}`. `raised` is true while the network board's pressure is HIGH. It is computed with the board at the time of the read (so a service that stops reporting does not count as limited and the alert clears or rises without an event), with the platform's default thresholds (`DEFAULT_POLICY`: watch from 3, high from 5 limited-or-worse services; DEC-546 item 3: a network's own thresholds are a later decision).
2. Nothing is delivered. No `Alert` task, no push and no message is made in any tenant, because that would write a network-derived record into each member's scope (two scopes in one piece of work) and drive a tenant alert from a network event, which DEC-136 item 9 rules out. A page shows the state as a banner for whoever reads the network view. If the owner later wants a push to the members' subscribers, it is a separate decision with its own consent and scope rules; nothing here blocks it.
3. The state names no organisation and no service: the count and the two thresholds only, so a page can say why.

### DEC-983 A network keeps hourly samples of what its board showed; the week summary is made from them (TEN-082, refines DEC-132 item 4, DEC-136 items 1 and 14, DEC-542 known issue "a capacity row is the current one only")
Status: accepted (build wave 9, bundle W9B; under DEC-133). Affects: `domain/rules/network_sample.py` (new), `application/ports/outbound/network_samples.py` (new), `graph_store/network_sample_repository.py` (new), `scope_labels.py` (`NetworkSample`), `migrations_network.py` (0185), `unit_of_work.py` (`network_samples`), `network_board_projector.py` (`SampleRecorder`), `use_cases/network_samples.py` and `network_week_summary.py` (new), `routes_network.py` (`NetworkServices.weeks`), `routes_network_views.py` (new).

1. **Why a new node.** A projection keeps the current row only, so a week of the network cannot be read from it. What a week can show is what the board showed, so each time the board is built its counts are filed under the hour that holds it, in the network scope: `(:NetworkSample {tenantId: <network>, hour, lastAt, accepting, limited, notAccepting, overCapacity, notUpdated, outOfHours, unavailable, organisations, peak})`, key (scope, hour) unique (migration 0185, expand only). A sample holds counts and a pressure level: no organisation, service, grant, source tenant or relationship, so no measure made from samples can be broken down by member (DEC-136 item 14). `NetworkSample` is a network-only label (`NETWORK_ONLY_LABELS`), so a tenant scope cannot run its statements and the generated isolation test covers both (`Q-NETSAMPLE-RECORD`, `Q-NETSAMPLE-RANGE`).
2. **When one is written.** By the board projector, after it has built a board that did not come from its cache: a rebuild after an event (`ProjectionApplied`, grant, member) and a read that found no cached board (at most one a minute for a network that is being looked at). Best effort: a failed write is logged by the class of the error and never fails the board. A later sample of an hour replaces its counts and the highest pressure of the hour is kept (`peak`); a sample older than the one the hour holds changes only the peak. Hours with no board built have no sample and the summary shows no data for them (it never carries a figure forward: a status is a statement about an instant).
3. **The measures** (`week_of_samples`, pure): `hours_sampled`; `on_time_pct`, the share of in-hours service readings that were not Not updated, which is the network's reading of "capacity updates on time" (a network has no prompts, so it cannot say a report came inside a reply window; the tenant summary's definition is not used); `status_share` for each of the six statuses; `pressure_hours`, the hours of the week at each level (the highest level of the hour); `pressure_over_time`, the level of each sampled hour. Bookings, cases and outcomes are not shared (DEC-136 item 1) and none appears.
4. **Small groups.** A count or a base under 10 is hidden (`value` null, `hidden` true), as the tenant summary does (domain-rules 10). A week in which no sample shows at least 3 organisations is withheld whole (`withheld` true, every measure hidden, no series): with fewer a share can be read as one member's own figure (DEC-136 item 14 asks for aggregates across at least three tenants).
5. **The week** is Monday to Sunday in London time (`london_week`, the same function as the tenant summary: the network's time zone setting allows nothing else yet, DEC-136 item 13), `weekStart` required and a Monday. Roles: the executive and the shift lead, as the tenant's own summary, and only as an active member of the network (`require_member`): another role, a tenant outside the network and an unknown network are the one 404.
6. **The numbers** `SMALL_GROUP = 10` and `MIN_ORGANISATIONS = 3` are named constants in `network_sample.py`.
