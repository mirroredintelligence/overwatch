# TEN-083: the operator console, the operator's session, and the support ticket screens (bundle W9D)

Front end, with no back-end change. Number blocks used: decisions DEC-1064 to DEC-1074, hazards H-738 to H-745. Built on `docs/delivery/fragments/W9C-routes.md` (the `/platform` door); shapes are `routes_platform.py`'s own, written out as fixtures in `frontend/test/fixtures/operator.ts`. The support ticket screens (a support person asks, sees the state, opens with the code and ends; the administrator's side is in TEN-076.md) are part of this fragment.

## Decisions

## DEC-1064 The operator's session is another KIND of session: its own cookie, key and CSRF, and no tenant (TEN-083, DEC-1000, DEC-1005, DEC-134 items 4 and 5)
Status: accepted (W9D, under DEC-133).

1. `lib/operator/session.ts`: the cookie `diucs_operator` is sealed (dir + A256GCM) with a key derived from the session secret for this one purpose (`diucs-operator-session`). A tenant's sealed session is not an operator's and the other way round, even with the cookie renamed (tests both ways). The claims are `kind: 'operator'`, the role (`platform-operator` or `support`), the host, the opaque account reference the back end derived, the back end's operator token and the end time. A payload that carries a tenant (`tenantId`, `tenant`, `epoch`, `services`), another kind or a tenant role is not a session even when it opens (tested with a payload sealed by hand with the operator key). Sealing a session with any other field throws.
2. It is read only on the host it was made on. `lib/auth/session.ts` is unchanged: `sessionFromRequest` and `getSession` still read the tenant cookie only and still require a tenant; no tenant-bound rule was weakened.
3. CSRF (`lib/operator/csrf.ts`): `<nonce>.<mac>` in the cookie `diucs_op_csrf`, made with a key and a material of its own and bound to the console host and the account reference. A tenant's token is not an operator's, even for the same subject and host.

## DEC-1065 The operator signs in with its own app registration, on its own host, and fails closed (TEN-083, TEN-043, DEC-1000)
Status: accepted (W9D).

`lib/operator/flow.ts` is the staff sign-in's authorisation code flow with PKCE against the operator's directory only. It reads `OPERATOR_ENTRA_CLIENT_ID`, `OPERATOR_ENTRA_CLIENT_SECRET`, `OPERATOR_ENTRA_DIRECTORY_ID` (required: there is no shared endpoint for the platform's own people) and `DIUCS_OPERATOR_PUBLIC_URL` (and the identity provider's address, `ENTRA_AUTHORITY_HOST`, shared); it falls back to none of the staff sign-in's settings. It serves only on the host of `DIUCS_OPERATOR_PUBLIC_URL`: a request on a tenant's host makes no transaction and no session. Its transaction cookie has its own name (`diucs_op_oidc`), path and sealing purpose, so one sign-in cannot complete the other. The ID token goes to `POST /auth/operator-token` (`lib/operator/exchange.ts`); the answer is kept only when the role is an operator's and the token is audience `diucs-ops` with no tenant, epoch, service or device claim, its role the answer's, not expired and not longer than twelve hours. `refused` (a 403) is the one access message; every other failure is the failed-sign-in message. Nothing logs more than a fixed word (`operator sign-in refused: <reason>`).

## DEC-1066 The console is `/operator`, guarded by the operator cookie; no tenant role opens it (TEN-083)
Status: accepted (W9D).

`lib/operator/access.ts`: `/operator` for both roles; `/operator/tenants/**` and `/operator/audit` for the operator; `/operator/support/**` for the support person; `/operator/sign-in` is public. `lib/auth/access.ts` answers `[]` for the `operator` prefix, so no TENANT role passes it and `canAccess` is false for a tenant role. `proxy.ts` decides the console first: no operator session sends to `/operator/sign-in?next=...`, a role that is not for the page gets `/forbidden`, and a tenant's person on a console page is sent to the console's sign-in (not shown forbidden). An operator's cookie opens no tenant page. The console sign-in page's content security policy names the identity provider as the staff sign-in page's does. A support person's home is `/operator/support`.

## DEC-1067 The console's BFF is `withOperatorBff`, routes `/api/bff/platform/**`, and its own guard kind (TEN-083, TEN-047)
Status: accepted (W9D).

`lib/operator/bff.ts` reads the operator session and nothing else (a tenant person of any of the 13 roles is a 401 identical to no session), checks the role (403), CSRF (403, before any call), refuses a request that names a tenant, scope or network in its query, headers or body (400), turns a back end 401 into `session-ended` and drops the session, answers privately and never stored. The tenant of an act is the PATH of the back-end call (`/platform/tenants/{id}/...`), checked by shape; no body names one. The generated route test (`test/guards/bff-routes.test.ts`) has two new kinds, `operator` and `operator-sign-in`, and a new check on every `session` route: a request that carries only an operator session is a 401. A route may not use both wrappers, and a route under `platform/` must use the operator one. The leak canary gains: a `/platform` call must carry audience `diucs-ops` (a tenant token there is `bad-audience`) and no tenant claim (`operator-names-tenant`); an operator token elsewhere is `bad-audience`. Answers are read field by field (no number's auth token reference, no epoch, no access id); a support person's tenant list is cut to id, name and status here even if the back end sent more.

## DEC-1068 The console tells the truth about a step the platform chain could not record (TEN-083, DEC-1002 item 4, H-670)
Status: accepted (W9D).

`recorded: false` on a provisioning or lifecycle answer means the step was done and the platform chain could not write it. The page says so as an alert ("The step was done, but the platform record could not be written. Do not repeat it. Tell the person who looks after the platform record."), shows what happened, and does not retry. A creation that comes back as created and not recorded shows only that alert and no form.

## DEC-1069 Starting to close a tenant is asked for with its consequence and its id (TEN-083, DEC-1006, W9C-K2)
Status: accepted (W9D).

The dialog says "Its people cannot sign in from now on. A notice period of 30 days starts. Exporting its data is not built yet, so nothing can be handed back to them.", needs the tenant's own id typed (the button is disabled until it matches, the BFF requires it to equal the path, and the back end checks it again as `confirmTenantId`). Suspension asks for a mode (read only or blocked, in words) and a reason; resume and activation ask first.

## DEC-1070 The support ticket screens (TEN-083, TEN-084, DEC-1003)
Status: accepted (W9D).

A support person lists their own requests (the tenant by name), asks for one active tenant (a reason code and a plain sentence: 10 to 200 characters of letters, digits and `. , ' & ( ) + -`, at most six digits, checked in the form, the BFF and the back end; the page says not to put in a name, number, postcode or anything about a patient), sees where it stands in words, cancels it while it waits, and opens the access with the code the administrator gave (`K7R4-92QX`, once, one tenant, one hour) or ends it. The code is typed, sent in one call and the field emptied whatever the answer; every refusal is the one message (the back end's one 404). The page says what the console does not do: it opens and ends the access and reads no tenant data yet (W9C-K3). The tenant's `?for=` on `/operator/support/new` counts only when it is the shape of a tenant id and an active tenant.

## DEC-1071 The console and the administration draw no inline style, and sign out their own way (TEN-083)
Status: accepted (W9D).

The content security policy allows styles by nonce only, so a style attribute is blocked: both areas use a CSS module (`components/admin/admin.module.css`, tokens only). The operator's sign-out (`signOutOperator`) ends the console session at `/api/bff/platform/session` with the console's own CSRF token, wipes the device whether or not that worked, and leaves by a hard navigation to `/operator/sign-in` only when the session did end.
