## Decision
Text codes: what makes a number known, the stored key, the send, and the audit (U25)
1. A number is known when a registered practitioner holds its hash (`find_by_phone_hash`, active only) or an invitation is open for it: a link token of purpose `invite` (U24's shape), unused and not expired at now. The open-invitation lookup is a new port method, `LinkTokenRepository.open_for_phone`, with one new converted statement `Q-LINK-OPEN-FOR-PHONE` (phoneHash, purpose, tenant; the latest to expire). The statement's scenario marks the token hash so it needs no shared constraint (the ratchet's table does not grow).
2. An unknown number gets the same answers as a known one: a code is generated and stored under the key, the same audit row is written, the same result is returned (`sent` true, 60 seconds). Only a known number is texted. A verify for a number with no stored code gets one refusal, known or unknown.
3. The store key is `code:<phone hash>:<purpose>`. The `CodeStore` port's first parameter is documented as the phone hash; it now receives this key, so a store that prefixes with the tenant (I13) keeps purposes apart. The Redis adapter and the fake take the key as given.
4. The send happens after the unit of work commits, so an audit row never exists for a code that was not stored.
5. A request is replayed by its key under a tenant-named key; the replay returns the first result and sends nothing again.
6. Every verify that finds a stored code writes one audit entry with the purpose and the outcome. The actor is anonymous (role anonymous-link, channel text-code). Neither the code, the number nor the hash is in the audit.
7. A correct code marks its state verified, so a second use is refused until the ten minutes end. A correct code for a number that is no longer known is refused (needs a new code).
8. `retry_after_seconds` is 60 after a send, and the remaining whole seconds (rounded up) during the cooldown.

## Assumed
- The actor of an unauthenticated request is anonymous (no practitioner), as above.
- The invitation purpose is `invite` (U24's purpose; U24 is not built on this branch, so the lookup is tested on a link seeded as U24 would write it).
- The K1 wording is rendered by the code sender adapter; this use case passes the code only.
