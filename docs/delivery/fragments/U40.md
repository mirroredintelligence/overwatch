# Fragment U40: clinical advice requests

## Decisions
- DEC-394: clinical advisors are the holders of an active clinical-lead role in effect now (PractitionerRoleCode.CLINICAL_LEAD). The model has no other clinical directory. Query: Q-PERSON-ACTIVE-ROLES (tenant, scenario); the role code and period are applied in Python.
- DEC-395: presence is a cache key `presence:clinical:<practitioner_id>` with a 120-second lifetime, refreshed by the client; an unknown or missing value is not available. Going away returns the taken, unadvised requests to the queue (audited). Advisors see only the count (AvailableClinicians returns an int). The clinician list comes from the directory, so no presence index is kept in the cache.
- DEC-396: the advice note goes to the protected text store (kind clinical-note, 280-character limit enforced again by the store); the request holds only its handle; the audit entry holds the choice, reason and snapshot ref, never the text. The K3 notice names urgency, age band and need only. Advice raises ClinicalAdviceGiven (alerts.events, request id, choice, time); the event carries no note. Advice cancels the clinical-return work.
- Queue: the queue is built from open requests (waiting and taken, Q-CLIN-OPEN), with idle locks released first (queue_now), then queue_order. Clinical advisors only.
- A request is accepted only for an open case (Conflict on a closed one); only advisors request; only clinicians take and advise.

## Hazards
- H-191: the clinical-advisor set is the set of clinical-lead roles. A clinician who is not holding that role is never notified and cannot take a request, even when present. Trigger: a clinician without a clinical-lead role on the staff directory. Owner to confirm the role model (W09 sign-in may supply the role).
- H-194: presence keys are tenant-prefixed only by the cache adapter (Redis, TEN-C06). The in-memory cache in tests does not prefix, so the presence isolation between tenants is not proved here. Trigger: a second tenant with the same practitioner id on the shared Redis.

## Known issues
- U40: the K3 notice is sealed; the test checks the count of outbox messages, and the notice wording is checked in a unit test only. Trigger: a change to the notice template.
- U40: the presence TTL is not tested by expiry (the test cache has a fixed clock).

## Contracts
- clinical_advice: presence_key(practitioner_id) -> str; parse_presence; validate_request; validate_advice; queue_now(records, now); advice_notice(urgency, age_band, need) -> (title, body); PRESENCE_TTL; ADVICE_CHOICES; ADVICE_REASONS; REQUEST_WHYS.
- Commands/results: RequestClinicalAdviceCommand(actor, case_id, urgency, why) -> RequestClinicalAdviceResult(request_id, notified); SetPresenceCommand(actor, presence); AvailableClinicians(uow_factory, cache, clock).execute() -> int; TakeClinicalRequestCommand(actor, request_id); ReturnIdleRequest(uow_factory, clock).execute(request_id); GiveClinicalAdviceCommand(actor, request_id, choice, reason, note) -> GiveClinicalAdviceResult; ListClinicalQueue(uow_factory, clock).execute(actor).
- PersonRepository.active_clinical_leads(now) -> list[PractitionerRole]; ClinicalRequestRepository.open_requests() -> list[ClinicalRequestRecord].
- domain/events: ClinicalAdviceGiven(request_id, choice, at), topic alerts.events; added to DomainEvent, the topic table and the decoder table.

## Tenant pending
- Q-CLIN-OPEN, Q-PERSON-ACTIVE-ROLES carry $tenant. The clinical queue is per tenant; a shared clinical pool across tenants is out of scope (DEC-130 item 8).
- Presence keys: tenant prefix from the Redis adapter (pending on TEN-C06); see H-194.

## Tenant isolation
- test_clinical_advice.py::test_tenant_b_request_id_is_not_found_to_tenant_a: tenant B's request id given to tenant A's take answers not found; tenant A's queue is empty.
