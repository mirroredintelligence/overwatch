# W13 fragment: options list

## Decision

DEC-636 The options are read once per case per page load. They are read again only after a saved answer (W14), never on focus or visibility change. The audit snapshot the back end writes for each `$filter-options` call is why.
1. The BFF generates a new `Idempotency-Key` for each read (a UUID), because the back end requires a key on the call.
2. The list holds a request guard, so a strict-mode remount does not read twice.

DEC-643 The options view is the back end's `$filter-options` Parameters read through `lib/advisor/options.ts`, which keeps only the named parts. Unknown parts are dropped, an unknown status is shown as Not updated (never as accepting), a stale figure (over 2 hrs) is flagged, and an option with no `serviceId` or name is dropped.
1. The order is the back end's; nothing is re-sorted or ranked.
2. A card has four actions for the viewer's own organisation: Request booking (W20), Criteria (W14), I phoned (W14), They declined (W14). A network card has only Criteria (DEC-648; network-ui.md section 9).

## Contracts

- Pages: `app/(advisor)/advisor/case/[ref]/options/page.tsx` (`CaseOptionsPage`).
- Components: `OptionsList` (props `caseId`; optional `onRequest`, `onCriteria`, `onPhoned`, `onDeclined`, `onAskClinical`), `ServiceCard` (props `option`; optional handlers; ids `ADV-OPT-REQUEST-BTN`, `ADV-OPT-CRITERIA-BTN`, `ADV-OPT-PHONED-BTN`, `ADV-OPT-DECLINED-BTN`, `ADV-OPT-NUMBER`), `NotSuitableList` (props `items`), `CaseSummary` (props `caseId`).
- Lib: `lib/advisor/options.ts` (`optionsFromParameters`, `OptionView`, `NotSuitableView`, `OptionsParts`, `NetworkTag`, `STALE_AFTER_SECONDS`).

- Back-end call: `POST /fhir/HealthcareService/$filter-options` with `case` as `valueReference` `ServiceRequest/<id>` and a fresh `Idempotency-Key`.
