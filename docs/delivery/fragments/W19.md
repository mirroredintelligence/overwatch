# W19 fragment: booking request page (build-W6H)

## Decision

Booking link pages follow the L02 back end as built (booking_links.py), not the W19 prompt where they differ (lesson L172).
1. Purposes are `booking-request` (the request) and `booking-change` (a confirmed booking's change link). The prompt's `booking` is read as either.
2. A booking 410 is `{state}` alone, as for every link. The page shows the same closed page for every closed state (expired, declined, cancelled, used), so it does not reveal which it was. The BFF answers `expired` for any closed booking on GET.
3. The confirm answer carries `bookingStatus` and `changeToken` only. The page shows "Booked" and the reference and service it already read; it shows no confirmation time, because the back end sends none.
4. The request view and the change view carry `coordinationPhone`, the SPOA's coordination-phone contact from the tenant's own configuration (`uow.tenant_config.contacts()`). It is never a constant or an environment variable (DEC-130 amendment, W19 prompt). A closed (410) answer has no phone, by the 410 rule (H-NEW-1).
5. The BFF forwards `reason` on a booking answer. A capacity answer never sends one, and the back end refuses a reason on a capacity link.
6. The need is shown exactly as the back end sends it (a code list joined with "and", e.g. "fall-no-injury and frailty"). No wording is invented for clinical needs (H-NEW-4).
7. A booking request reads its link twice: once on `/l/[token]` to learn the purpose and redirect, once on `/l/[token]/booking`. One booking view costs two of the tenant's 60 link requests a minute (DEC-167 item 8).
8. The redirect is kept in state and taken by its own effect, so a router that is a new object on each render does not re-read the link.

## Hazards

| id | hazard | source | control | tasks | verified by | status |
|---|---|---|---|---|---|---|
| H-NEW-1 | A service opens a booking after it has closed and sees "phone the SPOA" with no number, because the 410 carries no phone | L02 `booking_links.py`, 410 rule (L172) | the closed page says the SPOA's name and the words "phone the SPOA"; the number shows when the page already held it | W19, W22 | e2e (not run) | open, back-end follow-up |
| H-NEW-2 | A confirm pressed twice posts twice | W19 page | the button is busy while posting; the back end burns the link, so a second answer is 409 or 410 and the page shows that state | W19 | unit test: busy state | controlled |
| H-NEW-3 | The SPOA number on a closed page is a stale number | tenant configuration changes | the number comes from the link's own view, read when the page opens | W19, W22 | unit test | open |
| H-NEW-4 | A service reads a need code list ("fall-no-injury and frailty") and does not recognise it as the referral it was asked for | L02 `need_text` sends codes, not wording | shown as sent; the referral details follow in SystmOne | W19 | none | open, back-end wording |
| H-NEW-5 | A wave of booking links opened together spends the tenant's link budget (60 a minute), so answers are refused | DEC-167 item 8; a booking view costs two reads (decision 7) | the page reads once per view; a refused read shows the unavailable page, not the closed one | W19, W22 | none | open |

## Contracts

- `components/reporter/BookingDecision.tsx`: `BookingDecision({ token })` (client).
- `app/l/[token]/booking/page.tsx`: the booking request page (server shell).
- `lib/links/model.ts`: `BookingView`, `parseBookingView`, `parseOpenLink`, `OpenLink`.
- `lib/links/browser.ts`: `LinkRead` now has a `booking` kind; `BookingAnswer`, `BookingOutcome`, `sendBookingAnswer(token, csrf, answer)`.
- `lib/links/server.ts`: `readLink` returns `{ kind: 'open', link: OpenLink }`.
- BFF `GET`/`POST /api/bff/links/[token]`: serves booking views and forwards `reason`. No new route.
- Back end: `coordination_phone(contacts)`, `view_body(booking, service_name, case, phone)` in `booking_links.py`.
