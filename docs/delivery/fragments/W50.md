# W50 fragment: map view and travel details

## Decision

DEC-644 The map is a schematic: a picture drawn with SVG and a plain equirectangular projection, not a tile map. No tile provider is chosen and no third-party script is loaded. The patient's area is a dot at the postcode centre. Each fixed site is a labelled button over the picture; each visiting service is a dashed circle with its name beside it, and has no pin (it is reached from the list). Tiles are a later change.

DEC-649 The travel wording is the spec's. The range is for the area, not the door, and a visiting service is "Included in their response time". A wrong estimate is reported to `/help/problem?from=<the map path>`, with the path encoded.

DEC-647 The postcode-not-found state does not re-enter the postcode in place. "Change the postcode" goes to the needs form, where the postcode is edited and checked. The district chips are not built: the back end stores the postcode district only (DEC-398), and the BFF's save needs a full postcode, so a district choice has no save path yet.

DEC-643 (see W13) The options view gained `patientArea`, `notFound`, `outOfArea`, and per option `position`, `coverage` and `travel` (with `legs`), read from optional back-end parts: `patientLat`, `patientLon`, `notFound`, `outOfArea` at the top; `lat`, `lon`, `coverageRadiusKm`, `travelSource`, and `leg` sub-parts (label, low, high, how, source) per option. A coordinate outside the earth's range is not a position. This is the contract the back end must adopt; it sends none of these yet.
