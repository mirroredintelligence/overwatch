# W9F: the support console's insight tabs, on the back end and on the page

Tasks: W49 (the insight page, wired), O08 (the route and the read side it lacked), O02, O03 and O05 (the telemetry is now mounted, the web vital event exists, the route template check is fixed), O04 (two keys on the collector list). Back end built: `POST /telemetry/ui` and `GET /support/insight/{tab}` (root, not under `/fhir`), the counters they write and read, migrations 0195 and 0196. Front end built: the telemetry mount, the web vitals, the BFF forward of the events, the insight BFF route's device filter and the five tabs on the real answers. The exact shapes are in `W9F-routes.md`.

## Decisions

- DEC-1020 Where each figure comes from. Nothing reads Application Insights or Log Analytics (there is none, and the exporters stay configurable): the figures the insight page needs are counted from the browser's own `ui.*` events into tenant-scoped daily aggregate nodes in the graph, and no event is kept. The BFF already receives the events (O02); it now sends the allow-listed batch to the back end as well as to the collector (the collector path is unchanged and still optional). Figure by figure: funnels = `FunnelDaily` counted from page views (DEC-1024); paths = `RouteDaily` (sessions per route) and page-level friction (`FrictionDaily`, element `PAGE`, with its route); friction = `FrictionDaily` over `ElementUsageDaily` (clicks and submits); web vitals = `MeasureDaily` histograms from the new `ui.web_vital` event; slowest routes = LCP p95 per route from the same histograms; slowest queries = `QueryStatDaily` as O08 defined it (no writer yet, see known issues); release comparison = `ReleaseDaily` counters plus the histograms by release; pipeline = the tenant's own outbox read live (`OutboxMessage` pending and dead by topic). The O08 daily job and its `TelemetryQuery.daily_aggregates` stay as they were; a day it replaces takes the place of what was counted (documented in `aggregate_repository.py`).
- DEC-1021 The ingest. `POST /telemetry/ui` takes `{events: [{name, attributes}]}` (at most 50 events; `at` and any other key are ignored: the day is the server's UTC day). Any signed-in role but the platform operator (refused at the edge) may send; the tenant is the token's; the role counted is the token's `role`, never the browser's `user.role`. An event that breaks the schema is dropped and counted in `dropped`; the schema is the browser's (`lib/telemetry/schema.ts`) written again in `domain/rules/browser_insight.py` (enums, anchored id patterns, finite non-negative numbers, no free text). The route answers `{accepted, dropped}`; the BFF never passes that on. Without the marker secret (`telemetry-markers`, secret-store seam) the route answers 503 and nothing is counted: counting without the key would have to keep session ids. The ingest is not idempotent (a counter is added to): the BFF sends once and does not retry, and the browser sends one batch by beacon or by one fetch.
- DEC-1022 Counting sessions without storing them. A group's sessions are counted by a keyed marker per session, group and day (`TallySeen`: HMAC-SHA256 of tenant, day, family, group and session id, 32 hex characters, tenant-stamped), so the graph never holds a session id and a marker cannot be joined to the session id of a support code. A marker is created by `MERGE` on a composite key (a second batch waits and matches) and its `hits` says whether the session is new to the group. Markers older than yesterday are removed by each ingest (`Q-INSIGHT-PURGE-SEEN`, at most 5000). The floor is ten sessions (`is_suppressed`) as O08 set it. A count over a range is of session-days (a session on two days counts twice, as O08 recorded); a figure that spans groups (a vital over routes, a release over routes) uses a lower bound on distinct sessions (each day's largest group, added over the days), so a double count can never pass the floor. A floor on session-days does not mean ten people: in a small pilot one person on ten days passes it (H-690).
- DEC-1023 Web vitals. The browser measures the largest contentful paint, the slowest interaction and the layout shift with `PerformanceObserver` (`lib/telemetry/vitals.ts`) and sends one `ui.web_vital` event per measure when the page is hidden, with `metric` (`lcp`, `inp`, `cls`), `reading` (a number) and `rating` (`good`, `needs-improvement`, `poor`). The spec's keys `name` and `value` are refused by the collector (DEC-332), so these three are used; `metric` and `reading` are added to `infra/otel-allowlist.txt`, to the three `keep_keys` lists of `infra/otel-collector.yaml` and to the browser keys of the allow-list test; neither contains a denied word. A layout shift of zero is reported once the page has painted (otherwise the p75 would be of the pages that shifted); an interaction measure is reported only if there was one. The back end keeps a fixed histogram per day, measure, route, device and release (12 buckets; edges in `EDGES`), never a value. A p75 is the upper edge of the bucket that holds it, so it never reads better than the data; a budget (LCP 2500 ms, INP 200 ms, CLS 0.1, observability.md) is a bucket edge, so exactly on the budget is within it and anything past it is over. The overflow bucket reports the last edge, which is over every budget.
- DEC-1024 Funnels the browser can see. The spec's funnels (`FUNNELS`) have steps that are not screens (a text delivered, a booking confirmed); nothing stands in for them. The insight funnels are five (`BROWSER_FUNNELS`): reporter set-up, daily capacity update, advisor call, registration and criteria review, each a list of screens (route templates) in order, with the step names in `domain/rules/browser_insight.py`. A session is counted at the furthest step it reached (a screen shown, not a task finished): a step is the share of the sessions that reached the first step that reached it (no more than 100%), and a step under ten sessions, or any step of a funnel whose first step is under ten, has no number. The channel is `app` for the installed app and `browser` otherwise; the split is the share of first-step sessions by channel. The median time between steps and the exit element are not measured. The browser funnels are not the O08 `FUNNELS`; both stay.
- DEC-1025 Friction. Interactions are clicks and submits on tagged elements (a chip or a switch fires a click as well, so counting both would count one tap twice; typing is not an interaction). A friction event counts once however many clicks made it (`count` is the burst size). Friction of the page itself (element `PAGE`: u-turn, thrash, hesitation, scroll thrash) has no click rate: its row carries its route (`FrictionDaily` gains `route`, empty for a control; part of the key; `FrictionDailyRow.route` defaults to empty) and no rate. The review flag is the back end's: strictly over 5% (O08, DEC-334); the page shows it as sent. DEC-748 had the page flag a row "at or over 5%": a row at exactly 5% is no longer flagged, and the page does not work the rule out again. A group is left out when the element had fewer than ten sessions (for the page, or an element nobody clicked, when the friction was met in fewer than ten) and the answer counts how many were left out. Rows are ordered by rate then events; there is no per-person row and no advisor is named.
- DEC-1026 Release comparison. The newest release with at least ten sessions in the range against the one before it (versions compared as numbers, so 1.10.0 is newer than 1.9.0); none when fewer than two have ten. A measure is shown when both releases have ten sessions behind it: LCP, INP and CLS at p75 (the same bucket reading as the vitals), friction events per 100 interactions and errors shown per 100 page views (rounded to one place). The release gate of observability.md marks a measure `review`: a vital more than 10% slower at p75, or friction more than 2 points higher (a rise of exactly 2 is not held). The mark is advisory: nothing is held by it.
- DEC-1027 Pipeline. The pipeline table is the tenant's own outbox read now, by topic: waiting (`pending`), dead and the age of the oldest message waiting. It is not the Service Bus queue depth (there is no management client here); it is what the product has written and not yet relayed. A topic that is not a known name is added up as `other`, so a name can never carry more than a fixed word. The read is by status on a new index.
- DEC-1028 The tabs' route. `GET /support/insight/{tab}?range=24h|7d|30d[&device=phone|tablet|desktop]` is for the support role only (the role guard runs first; another role gets the non-revealing 404). The counters are daily (UTC), so a range is whole days ending today: `24h` is yesterday and today (the page says "Today and yesterday"), `7d` seven days, `30d` thirty. The friction rate is over the chosen range (the spec's seven days is the default). A device filter applies to every tab but the release comparison, which refuses one with 400. Two figures are not measured and are said as such, never as an empty list: `unused` (the controls nobody used need the list of every control, which the back end does not hold) is `null`, and `promptToBoard` is `null`. The page says "Not measured yet" for each. An unknown tab, range or device is 400, naming the field. A back end that cannot be asked is "This view could not be loaded"; the page no longer says "Insight is not available yet" for a 404.
- DEC-1029 The telemetry is mounted. Nothing called `initTelemetry`, `attachFriction` or `trackPageView`, so no `ui.*` event was ever recorded. The root layout now renders `Telemetry` (a server component, `app/Telemetry.tsx`) that reads the session and mounts `TelemetryMount` (a client component) for a signed-in person: it starts the telemetry with the session's role and this build's release, attaches the friction rules, starts the vitals and records each screen as a page view of its route template with the one it came from. A signed-out page measures nothing (the ingest needs a session). The route template check was wrong: `/^\/[a-z0-9\-/[\]]*$/` refused a template with a camel-case parameter (`/app/respond/[serviceId]`, `/criteria/[serviceId]`), so the browser would have dropped every event on those screens; it now allows a bracketed parameter name of letters and digits and still refuses a space, a dot or a capital outside a bracket.
