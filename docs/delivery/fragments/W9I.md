# W9I: wall screens administration for the lead (TEN-072, single-tenant part), back end and front end

Bundle W9I: the lead's list of the organisation's wall screens (name, place, status, paired, last seen) and the revoke (immediate; audited), the BFF routes, and `/lead/screens` linked from the lead home and the pairing form; the wall display that says "This screen was disconnected". Branch `task/build-W9I` off `integration/build` 178b50b. The network-scope half of TEN-072 (screens by scope, the which-board control, last-known keyed by scope) is another bundle's (W9B builds `GET /screens`' board fields and the board-scope route in parallel: see Known issues, "W9B overlap").

## Decisions

### DEC-1050 The lead's list and revoke of wall screens (TEN-072; refines DEC-160, DEC-761)
Status: accepted (bundle W9I, under DEC-133).
1. **Two routes in `routes_screens.py`, role `lead` alone** (the role matrix is tested for all 13 roles on both: another role is the non-revealing 404, the platform operator the edge's 401). `GET /screens` answers `{scope: "tenant", asOf, screens: [{deviceId, name, location, status, boardScope, pairedAt, lastSeenAt, revokedAt}]}`; `POST /screens/{deviceId}/revoke` (Idempotency-Key required, a JSON body required by the body-type middleware and never read) answers 200 `{deviceId, status: "revoked", revokedAt}`. The tenant is the lead's token's; no body, query or header names one. A screen the tenant does not hold (another tenant's included) is the one 404; a malformed id is a 400 before any read. Every answer is `no-store`.
2. **No secret in any answer.** The view (`ScreenSummary`) has no field for a token, a token hash or a pairing secret; the BFF keeps only the fields the page shows, so a field a back end added by mistake never reaches a browser.
3. **Status is the back end's word** (`domain/model/device.py: screen_state`): `online` (read within 3 minutes, `ONLINE_WITHIN` [ASSUMED]: the wall polls every minute), `offline`, `waiting` (connected by a lead, token not yet collected, inside the ten-minute pairing window), `never-connected` (the window ran out before the screen collected its token: it can only be paired again, and the lead can remove the row by revoking), `revoked`. A last-seen time in the future is not online.
4. **Order and retention of the list.** Live screens first by name (case-insensitive, then id), revoked last. A revoked screen stays listed for 30 days (`REVOKED_LISTED_FOR` [ASSUMED]) so the lead can see it ended; one with no revoke time stays. There is no other retention sweep (known issue).
5. **The revoke** (`RevokeWallScreen`): `get` (takes the screen's write lock, so a claim that is running finishes first), `revoked_at` set, status `revoked`, **token hash removed**, one audit entry `wall-screen-revoked` (actor the lead; snapshot `{screen_name, was}`, no hash, no token). A screen revoked already is answered as it is (the first revoke time) and audited no second time. A screen that never collected its token can be revoked (it cancels the pairing). Idempotent by state, and by the replay cache on the key.
6. **Network scope later**: the list is a use case (`ListWallScreens`) over a view type (`ScreenSummary`); the response carries `scope: "tenant"`. A network list is a new use case over member tenants with its own response `scope`, not a parameter of this one; `boardScope` is already in every row.

### DEC-1051 A revoked screen stops at its next request, not at the end of its hour (TEN-043; refines DEC-761 item 2)
Status: accepted. The bound the task asked to record.
1. **Exchange.** `find_by_token_hash` returns active screens only and a revoke drops the hash, so a revoked screen's device token gets no new wall token: the exchange is the one 404 (tested end to end).
2. **A wall token already issued** (one hour, `WALL_TOKEN_LIFETIME`) used to keep working until it ran out. Now `auth.ensure_screen_live` asks the registry on every request a wall may make: in `require_role` (the board, the coordination phone, the stream, the network routes TEN-067 adds, and every other `require_role` route a wall is let into) and explicitly in the three reads that use `current_actor` alone and that a wall may reach (`GET /fhir/HealthcareService` and `/{id}`, `$validate`). A wall whose screen is not an ACTIVE screen of the bound tenant is the 401 of a lapsed token; the BFF turns a 401 into the end of the wall session (`withBff`), so the display goes to pairing. **Bound: the screen's next request, immediately across processes (no cache; one indexed read per request).** The board polls every 60 seconds and on every stream event, so a revoked display is cut off within a minute of the revoke and at its next event.
3. **What is not cut**: the open `GET /events` stream of that screen stays connected until it reconnects. It carries only `{serviceId, kind, changedAt}` pings (no figure, no name), and the screen's refetch that each ping causes is refused. Known issue with the trigger. Any route that reads `current_actor` alone and refuses a wall by its own role logic never gives a wall data; the three it does are covered. A wall token is still good, up to its hour, for a route that is not behind `require_role` and not one of the three (none known).
4. **Fail closed.** A registry that cannot answer fails the request (500); it never lets it through. A wall actor with no device id is refused.
5. **Cost and "last seen".** The same statement (`Q-SCREEN-SEEN`, write) answers "still active?" and sets `lastSeenAt` only when it is absent or older than 30 seconds (`SCREEN_SEEN_EVERY`), so a screen that reads every minute causes about one small write a minute; the lead's "last seen" is therefore at most 30 seconds old. Only an active screen is written.

### DEC-1052 The device record gains `pairedAt`, `lastSeenAt`, `revokedAt` (expand-only, no migration)
Status: accepted. `Device.paired_at/last_seen_at/revoked_at` (default None), node properties `pairedAt`, `lastSeenAt`, `revokedAt` (absent when unset; no null stored). `ConfirmPairing` stamps `paired_at` with the clock; screens paired before this change read as having no paired time (`never-connected` if they are still unclaimed, the list shows "Not recorded"). New registered statements: `Q-SCREEN-LIST` (read, no lock) and `Q-SCREEN-SEEN` (write), each with a Scenario (`Marked` screen name for both tenants); `Q-SCREEN-GET/SAVE/BY-TOKEN` carry the three fields. No migration: the properties are optional and no index is needed (a tenant has a handful of screens).

### DEC-1053 The display says so, and cannot loop (W08 refined; DEC-761 items 4 and 5)
Status: accepted.
1. `POST /api/bff/screens/session`, when the back end refuses the device token the screen holds, answers 404 `{code: "disconnected", message: "This screen was disconnected."}`, forgets the device cookie (as before) **and ends the wall session cookie** (new). A screen with no device cookie still gets the plain 404 `not-found`.
2. The pairing page shows a warning banner "This screen was disconnected." with "Ask a shift lead to connect it again with the code below." above the new code, and keeps it through polling and replacement codes; a screen that was never paired shows none (`usePairing` gives `disconnected: true` only then).
3. **`/screen/reconnect`** (new page, always the pairing screen, no input): the wall page's server read of the board used to redirect a refused screen to `/screen/pair`, which redirects any display that still holds a wall session back to `/screen` (a loop, and a revoked screen reloaded within its hour would hit it). Now the refusal goes to `/screen/reconnect`, whose pairing screen asks for a new session from the device cookie, and when the back end refuses it, says "disconnected" and shows a code. The client-side path (refetch 401, `withBff` ends the session, `onUnpaired` to `/screen/pair`) is unchanged.

### DEC-1054 The page (`/lead/screens`) and its words (W9I; plain NHS wording, status never colour alone)
Status: accepted. A table "Wall screens in your organisation" (Screen, Status, Paired, Last seen, Action). Status is a word and a shape. Ages are measured against the back end's `asOf`, never the browser's clock ("Just now", "2 hrs 20 min ago", "Not seen yet"); a revoked row shows when it was disconnected. "Disconnect <name>" (the name is in the accessible name) opens a dialog "Disconnect <name>?": "This screen will stop showing the board straight away and go back to its pairing page. To use it again, pair it again with a new code." with Cancel and "Disconnect screen". One key per dialog (a second try sends the same key); a double press sends once; 404 says the screen is not in the list any more and reloads; 401/403 says the session ended with a sign-in link; any other failure keeps the dialog and says so. The list reloads after a revoke and every 60 seconds; a failed read never shows an empty table. Linked from the lead home (a "Shift lead pages" navigation, shown whatever the overview did) and from the pairing form ("See the screens already connected"; "See all screens" on the confirmation).

## Contracts

- Back end: `GET /screens`, `POST /screens/{deviceId}/revoke` (see `W9I-routes.md`); `auth.ensure_screen_live(request, actor)`, `auth.SCREEN_SEEN_EVERY` (30 s), `require_role`'s dependency now takes the request; `DeviceRegistry.list_screens()`, `DeviceRegistry.confirm_active(device_id, seen_at, refresh_after)`; `Device.paired_at/last_seen_at/revoked_at`, `Device.revoke(at)`, `ScreenState`, `screen_state(device, now)`, `ONLINE_WITHIN`, `REVOKED_LISTED_FOR`; `application/use_cases/screen_admin.py` (`ListWallScreens`, `RevokeWallScreen`, `RevokeWallScreenCommand`, `RevokeResult`, `ScreenSummary`); registered statements `Q-SCREEN-LIST`, `Q-SCREEN-SEEN`; audit action `wall-screen-revoked`, use case `RevokeWallScreen`.
- BFF: `GET /api/bff/screens` (lead), `POST /api/bff/screens/[id]/revoke` (lead, CSRF, Idempotency-Key); `POST /api/bff/screens/session` answers 404 `{code: "disconnected"}`.
- Front end: `lib/screens/admin.ts` (`screenListFrom`, `revokedFrom`, `STATUS_WORDS`), `components/lead/ScreenList.tsx`, pages `/lead/screens` and `/screen/reconnect`, `usePairing`'s `disconnected`, `ScreenClientError.disconnected`; test stand-in `PairingStandIn.list/revoke`, `REVOKED_SCREENS`.
