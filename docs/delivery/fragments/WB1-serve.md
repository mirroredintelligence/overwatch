## Decisions

- DEC-1110 **The API has a serving process (`diucs.bootstrap.api_main`).** `python -m diucs.bootstrap.api_main`, or `uvicorn diucs.bootstrap.api_main:app_factory --factory`. `create_serving_app(settings, parts)` checks the settings and the secrets, builds the container (nothing connects), and `build_api` calls `create_app` and sets every `app.state` a route family reads: `secrets` (the platform store), `cache` (the container's Redis), `token_exchange` (`ExchangeDeps`: the verifier, the operator directory, the platform chain), `link_pages` (cache and sealer), `sms_webhook` (`DirectoryInboundLines`, the hasher over the tenant-keyed store, the Service Bus, `Settings.base_url`), `network_services` and `network_admin` (`bootstrap/network_services.py`, the real registry and the two kinds of unit), and, by `install_platform_routes`, `platform_services` and `tenant_admin_services`. The container opens in the app's lifespan (`serving_lifespan`: `startup()` refuses to start when Neo4j cannot be reached, a migration fails or a node has no tenant; the parts and the container close in reverse order on the way out, whatever happened). uvicorn's own forwarded-header handling is OFF (`proxy_headers=False`): the edge decides who the client is. The access log hides link tokens (`RedactLinkTokens`, installed). **It refuses to start (exit with a message, not a 404) when:** a secret the API reads is missing or shorter than 32 bytes (`REQUIRED_SECRETS`: `bff-jwt`, `account-ref`, `phone-hash` and the seven keys each tenant's own is derived from; the message names the secrets and never a value); there is no secret store; there is no Service Bus connection (the webhook queues replies on it); in the `production` profile `DIUCS_BASE_URL` is not an https URL or is the placeholder (Twilio's signature is checked against it, so a wrong value would refuse every inbound text without a sound); `DIUCS_SYNTHETIC_ENABLED` is set (no synthetic link issuer is built, so the hook would answer 404 to every check: refuse instead of looking configured); the operator directory is not a GUID; the proxy settings do not parse. **It starts, and says so at WARNING, without** a postcode file, an address key, telemetry, an operator directory or an identity verifier (`startup_warnings`; each fails closed in use). Not built here, each needing a credential or a service: the process's secret store (`load_secret_store` returns None, so the process exits at start-up until the Key Vault adapter of B8 exists) and the Entra verifier (`RefusingIdentityVerifier` refuses every staff and operator sign-in). The smoke test builds the real app from a test container and serves the health route, the public profile, the token exchange, an authenticated FHIR route, the network read route, the SMS webhook and the link pages.
- DEC-1111 **Every declared Service Bus subscription is read, or is deleted.** Built: `alert-evaluator` on `capacity.events` (sessions, as the subscription requires): `AlertEvaluationConsumer` hands a `StatusChanged` to the existing `AlertEvaluator`, which until now nothing ran, so no status change raised an alert; and `notifier` on `alerts.events`: `EscalationNotifyConsumer` hands `ReportEscalated`, `WithdrawalEscalated` and `AlertEscalatedToLead` to the new `NotifyShiftLeads`, because those three events end a chain of reminders "for the shift lead" and nothing told the lead (see DEC-1115). Both run inside `TenantBoundConsumer` and are wired in `workers_main.serve` (`AlertWiring`, `build_runners(..., alerts=...)`). **Deleted** from `infra/servicebus-config.json` (11 subscriptions, never read; the behaviour each stood for is done another way): `capacity.events/analytics-aggregator`, `booking.events/{notifier, advisor-stream, analytics}`, `registration.events/{notifier, lead-queue-projector, analytics}`, `criteria.events/{notifier, flag-maintainer}`, `alerts.events/{escalation-timer, analytics}`. The advisor's live board and stream are the board projector's; the lead's registration queue and the criteria flags are reads of the graph (`registration_views`, the daily criteria review); the escalation timer is scheduled work (`alert-escalate`, the ladder); the planning analysis reads the decision log (W51). The publishers are not deleted: each topic still has a reader, and the outbox relay publishes to a topic, not to a subscription. A test (`tests/unit/bootstrap/test_service_bus_topology.py`) compares the topology file with the runners the worker builds: a declared subscription with no reader, or a reader of an entity that is not declared, fails it. `docs/spec/architecture.md` is reconciled. A feature that wants a notifier on bookings, registrations or criteria (a lead told of a new registration, B5) adds the subscription and its reader together.
- DEC-1112 **Cloudflare is trusted for the client address and the original host only when the request comes from Cloudflare** (`adapters/inbound/edge_proxy/cloudflare.py`, deployment-plan item 5). The outermost middleware trusts a request whose socket peer is inside Cloudflare's published ranges (a snapshot of `ips-v4` and `ips-v6` of 2026-10-31, replaceable without a code change by `DIUCS_EDGE_CLOUDFLARE_RANGES_FILE`, one range for each line, `#` comments), or inside a range named in `DIUCS_EDGE_TRUSTED_PEERS` (the platform's ingress, when the ingress accepts traffic only from Cloudflare and so is the peer the app sees), or that carries the origin secret in `X-Edge-Auth` (the secret `edge-origin` in the secret store, at least 32 bytes, compared in constant time; Cloudflare adds it with a transform rule; this is the authenticated origin pull of this design, because the container ingress does not verify a client certificate). For a trusted request the client address is `CF-Connecting-IP` (one valid address, else the peer is kept: Cloudflare counts as one address, a shared bucket and never a bypass) and the Host is `X-Forwarded-Host` (a request-header rule on Cloudflare, which replaces anything a visitor sent; only a valid host name, its port dropped). Every other request keeps its socket peer and its own Host. In every case `CF-*`, `True-Client-IP`, `X-Forwarded-*`, `X-Real-IP`, `Forwarded`, `CDN-Loop` and `X-Edge-Auth` are removed before a route sees them, so the host binder (`Host` only) and the limiters (`request.client`) cannot read a forged value. `DIUCS_EDGE=none` trusts no published range (the origin secret and extra peers still apply), for a deployment without Cloudflare. An IPv4 peer shown as an IPv4-mapped IPv6 address is read as IPv4. Twilio's signature uses `Settings.base_url`, not the request's host, so a rewritten host cannot change what is verified.
- DEC-1113 **Production sources of the link host and the wording.** `LinkBaseUrlFor` may now be async (`resolve_link_base` awaits it when it must); the production container's `link_base_url_for` is `DirectoryLinkBase(...).link_base_url` (`https://<the tenant's host>/l`; only the default tenant falls back to `Settings.base_url`; any other tenant with no host is `TenantRecordInvalid`, never another tenant's host), the same source the prompt and the ladder use. `wording_for` is `ConfiguredWording(ReadTenantConfig(uow_factory))`: the wording of the configuration in force of the BOUND tenant (a scope that is not the bound tenant is `TenantMismatch`, a network scope `TenantNotBound`, no wording is None and the booking request is refused as before). Because the reader opens a unit of its own and a unit cannot open inside another, `RequestBooking` now asks for the wording before its own unit opens (as it reads the board before it, DEC-146). `build()` refuses a plain-string or fixed link base for the serving dispatch table (`require_tenant_link_bases`, KI-505); the test container keeps its one base.
- DEC-1114 **`prompt-due` has a handler.** `prompt_due_handler(SendPrompts(...))` is in the dispatch table of both containers: one `SendPrompts` run for each scheduled work, keyed `prompt_key(service, due)` (so a redelivery is a replay and a grouped prompt that already served the service makes it do nothing), as the scheduler's system actor of the bound tenant, over the unit-of-work idempotency store (no driver is needed before the connection opens). The chain re-arms itself (`SendPrompts` schedules the next prompt in the same unit).
- DEC-1115 **Who the shift-lead notifier tells.** [ASSUMED] Every active `shift-lead` role of the bound tenant (the model has no link between a shift lead and a service, so an escalation goes to all of them), one K3 push each (the channel of every other K3: the safety officer's, the alerts'), once for each message (the message is marked in the unit that writes the pushes). The push names the service and what to do and holds no booking, alert or person identifier and no patient data; an alert with no service names none. Wording [ASSUMED]: "{service} has not reported / No figure has come in after the last prompt. Please phone the service."; "Withdrawn booking for {service} / A withdrawn booking has not been acknowledged by the advisor. Please check with them."; "{service} alert not acknowledged / No one has acknowledged the alert. Please follow it up." A tenant with no active shift lead is audited with a count of none and logged (the escalation has nowhere to go: H-762).
- DEC-1116 **Rows of the triage found already closed by earlier work** (no change made, recorded so the fold closes them): KI-124 (`Container.startup` makes an audit head for each active tenant, bound in turn), KI-134 and KI-142 (the worker's tenant list is `container.tenants`, the active tenants of the directory; the platform scope is never one), KI-576 (`serve` passes the network board projector to `ApplyProjection` as its notifier), KI-358 (every `RespondToBooking` is built with the sealer: the link pages' `deps.sealer`, the routes' `container.sealer`, the worker's). KI-96, 162, 243, 266, 387, 482, 490, 492, 502, 505, 527, 537, 587, 845, 852 and 161, 166, 167, 206, 401, 441 are closed by DEC-1110 to DEC-1114; KI-191 and KI-196 by the start-up warnings; KI-845 by the refusal to start.

## Hazards

| id | hazard | source | control | tasks | verified by | status |
|---|---|---|---|---|---|---|
| H-760 | A visitor chooses the client address or the host the edge reads, by sending the headers a proxy would add: the rate limits are dodged and the host binds another tenant | the trusted edge (DEC-1112) | headers are honoured only from Cloudflare's ranges, a trusted peer range or the origin secret; every edge header is removed before a route; `none` trusts no range; a trusted request with no valid visitor address keeps the peer | WB1 | `test_cloudflare.py` (32 cases), `test_api_main.py` (edge cases), `test_api_boot.py` (forged host reaches no tenant, forged address does not dodge the limit; mutation: removing the middleware fails 5 of 11) | controlled, tested |
| H-761 | Cloudflare adds a published range that the snapshot lacks: real traffic is treated as untrusted, so every visitor shares one rate-limit bucket (the peer's) and the original host is not read | the range snapshot (DEC-1112) | fails safe (a shared bucket, never a bypass); `DIUCS_EDGE_CLOUDFLARE_RANGES_FILE` refreshes the list without a deploy; the origin secret path does not depend on the list | WB1 | `test_api_main.py` (ranges file); not run: against Cloudflare | open: refresh the ranges at each release and when the limiter's bucket count falls to one |
| H-762 | An escalation that is for the shift lead goes to nobody: the tenant has no active shift lead, or the lead has no push subscription | `NotifyShiftLeads` (DEC-1115) | the audit entry records the event and a count of none; a warning is logged; the board, the phone task and the alert remain | WB1 | `test_notify_escalations.py` (unit and integration) | open: a second channel (text to the escalation contact of the tenant, `ContactKind.SHIFT_LEAD_ESCALATION`) is the follow-up |
| H-763 | The API runs with no staff or operator sign-in (no Entra verifier built) or with no Key Vault: a deployment that looks up is unusable | `RefusingIdentityVerifier`, `load_secret_store` | the process refuses to start without a secret store; with no verifier every sign-in is refused (fail closed) and the start-up warning says so | WB1 | `test_api_main.py` | open until B8 builds the verifier and the Key Vault adapter |
| H-764 | The alert evaluator runs in production for the first time: alerts, their pushes and their escalation timers start to exist for every subscriber | `alert-evaluator` runner (DEC-1111) | idempotent by message id (a marker in the unit); a service that is not there is dead-lettered, not retried; quiet hours and thresholds are the existing rules | WB1 | `test_alert_consumers.py`, `test_alert_runners.py` (emulator) | open: severity provisional MEDIUM until a pilot service's alert volume is seen |

## Contracts

- `diucs.bootstrap.api_main`: `ApiParts(secrets, verifier, event_bus, closers=())`, `ApiConfigError`, `RefusingIdentityVerifier`, `REQUIRED_SECRETS`, `EDGE_ORIGIN_SECRET = "edge-origin"`, `check_secrets(store)`, `check_settings(settings)`, `edge_for(settings, secrets) -> CloudflareEdge`, `startup_warnings(settings, container, parts) -> list[str]`, `serving_lifespan(container, closers, warnings)`, `build_api(settings, container, parts, provider=None) -> FastAPI`, `create_serving_app(settings, parts, ...)`, `load_secret_store(settings)`, `app_factory()`, `main()`.
- `diucs.bootstrap.network_services`: `build_network_services(container) -> NetworkServices`, `build_network_admin_services(container) -> NetworkAdminServices`.
- `diucs.adapters.inbound.edge_proxy.cloudflare`: `CloudflareEdge(ranges, extra_peers, origin_secret, trust_cloudflare)`, `CloudflareEdgeMiddleware(app, edge)`, `CLOUDFLARE_RANGES`, `parse_ranges(lines)`, `EDGE_AUTH_HEADER`.
- Settings (environment, prefix `DIUCS_`): `API_HOST`, `API_PORT`, `EDGE` (`cloudflare` or `none`), `EDGE_CLOUDFLARE_RANGES_FILE`, `EDGE_TRUSTED_PEERS` (a JSON list of ranges), `OPERATOR_DIRECTORY_ID`.
- Secrets: `edge-origin` (optional, at least 32 bytes), and the nine required names (`REQUIRED_SECRETS`).
- `diucs.bootstrap.container`: `prompt_due_handler(send)`; `WorkKind.PROMPT_DUE` is in `container.scheduled_work.kinds` of both containers; `_scheduled_work(..., serving=True)`; `link_base_url_for` and `wording_for` of `build()` are the directory's and the configuration's.
- `diucs.application.tenant_settings`: `LinkBaseUrlFor`, `resolve_link_base(source, scope)`, `require_tenant_link_bases(source)`. `diucs.application.tenant_wording`: `ConfiguredWording(reader)`, `WordingReader`.
- `diucs.application.use_cases.notify_escalations`: `NotifyShiftLeads(uow_factory, ids, clock, sealer).execute(NotifyLeadsCommand(message_id, event_type, payload)) -> NotifyLeadsResult(notified, duplicate, ignored)`, `ESCALATION_EVENTS`.
- `diucs.adapters.inbound.workers.alert_consumers`: `AlertEvaluationConsumer`, `EscalationNotifyConsumer`, `alert_runners(client, evaluator, notifier, tenants, observe)`, `ALERT_EVALUATOR_SUBSCRIPTION`, `NOTIFIER_SUBSCRIPTION`; `workers_main.AlertWiring(evaluator, notifier)` and `build_runners(..., alerts=...)`.
- Topology: `infra/servicebus-config.json` has no subscription without a reader (see DEC-1111).
