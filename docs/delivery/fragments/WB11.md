# WB11: wall screen administration and last-known by scope (TEN-072), and the network variants of the advisor's and the executive's screens (known issues W10-K3, G11)

Bundle WB11, branch `task/build-WB11` off `integration/build` ad3282b. Number blocks used: DEC-1230 to DEC-1239, H-870 to H-878. No migration (none needed).

## Decisions

### DEC-1230 The confirm step of pairing: `POST /screens/preview` (TEN-072, ScreenClaim; refines DEC-160)
Status: accepted (bundle WB11, under DEC-133).
1. **A small back-end read.** `PreviewPairing` (`pair_wall_screen.py`) and `POST /screens/preview` `{code}` (role lead only; every other role is the one 404, the platform operator the edge's 401; a `tenantId` or any other field in the body is a 400 by `extra="forbid"`). It answers `{firstSeenAt, deviceClass: "wall-display"}`. It burns nothing and writes nothing.
2. **First seen is derived, not stored.** The code's record holds the time it lapses; the time the screen first asked is that time minus the ten minutes of the code (`PAIRING_CODE_VALID_FOR`). No field was added to the record and no migration was needed. `deviceClass` is the one kind of device that pairs by a code (`wall-display`); the page says "Wall display".
3. **No new oracle for the code.** A wrong code takes a slot of the SAME failure allowance as a connect (`pairing-confirm:<tenant>:<lead>`, five a window); a right one gives its slot back. So five wrong codes typed into the preview and the connect together lock the lead out for the window (429), and a preview is never a way to guess a code. Every refusal (wrong, short, letters, expired, used, another tenant's, a role that is not the lead) is the one `NotAllowed` of pairing. Tests: `test_preview_pairing.py` (use case, 8), `test_routes_screens.py` (route: role matrix over 12 roles, no token, two tenants, one refusal, throttle).
4. **The organisation's name is the tenant's own, from its public profile**, added by the BFF (`POST /api/bff/screens/preview` answers `{organisationName | null, firstSeenAt, deviceClass}`), the same read the wall's heading uses; when the profile cannot be read the page says "your organisation". The back end reads no tenant name here.
5. **The step.** After the form is valid the lead sees "Check before you connect", "You are connecting a screen to {Organisation name}. It will show our organisation's capacity only. It never shows patient information." and "First seen {time} · Wall display", with Connect screen (`SCREENS-CLAIM-CONFIRM-BTN`) and Cancel (`SCREENS-CLAIM-CANCEL-BTN`). Cancel returns to the form with what was typed; a code the back end then refuses returns to the form with the message beside the code field. The existing wording of the form is unchanged.

### DEC-1231 Which board a screen shows: the lead's page and the one body key (TEN-072; TEN-067, DEC-132 item 5)
Status: accepted.
1. **`PUT /api/bff/screens/[id]/board-scope`** (roles `lead` and `tenant-admin`, the back end's two; CSRF; `If-Match: W/"<scopeVersion>"` and `Idempotency-Key` required, 400 when missing or malformed; body `{boardScope: "tenant"}` or `{boardScope: "network", networkId}`), `root: true`, only those two fields forwarded. Answers `{deviceId, boardScope, networkId, networkName, networkAvailable, scopeVersion}`. A stale version is the back end's 412 (the page says someone else changed it and reads the list again).
2. **The guard.** The input guard refuses every key starting with `network`. `withBff` gains `allowNetworkIdInBody`, which lets through ONE thing: the top-level key `networkId` of a JSON body, once, a string that is a network id. A nested key, a second network key (`networkIds`, `network_id`), a tenant, a scope or a source key, a value that is not a network id, the key in the query, in a header or in a form are all still the 400 before any work. `test/guards/bff-routes.test.ts` names the one route (`TAKES_NETWORK_ID_IN_BODY`) and fails if another route says it or if this one also says `allowNetworkId`.
3. **The page never sends a network it was not offered.** `GET /api/bff/screens` now passes `networks: [{id, name}]` (the registry's active memberships, W9B) and each row's `networkId`, `networkName`, `networkAvailable`, `scopeVersion`; the dialog offers the organisation's own board and one radio per offered network, and the id sent is one of them. An organisation in no network sees only the first option and "Your organisation is not in a network.". A screen set to a network that is no longer open to it starts on "Our organisation" and the dialog says so.
4. **Roles.** The BFF list and the board change accept the lead and the tenant administrator (as the back end does); the page `/lead/screens` is the lead's (the proxy) as W9I built it. A tenant administrator's own page is not built (known issue WB11-K2). Revoke and connect stay lead only.

### DEC-1233 The wall: one read, last known by scope, the fall back (TEN-072, TEN-067; design sections 5 and 6)
Status: accepted.
1. **One atomic read.** `GET /api/bff/wall/board` (a person who reads the board gets their own board with the own setting; a wall gets what its administrator chose) answers `{scope: {boardScope, scopeVersion, fallback, networkName}, board}`. `readWallBoard` (`lib/board/wall.ts`) reads the setting (`GET /screens/me/board-scope`), then the board of that scope, so a screen never shows one scope's figures under another's header. The page (`/screen`) uses the same function. A setting it cannot read is a 502 (never a guess); a revoked screen's 404/401 still send the display to pairing/reconnect.
2. **The fall back.** A screen set to a network that is no longer open to it (`fallback: true`), and one whose network closes between the two reads (404 on the network board), get their own organisation's board with the flag. Any other failure of the network board stays a failure (the screen keeps its last known figures and says so): it is never taken for a fall back. The banner is a `warning` Banner, `SCOPE-BANNER-NOTICE`: "No longer showing {Network name}. Showing: Our organisation." The back end's fall back answer carries no network name (it must not tell a former member about the network), so the name is the one the screen showed earlier in this browser session (kept in memory only); a screen that never showed it says "No longer showing the network board. Showing: Our organisation." The header keeps saying "Showing: Our organisation" and the banner stays on every refresh until the administrator changes the board.
3. **Last known is kept per scope.** `useBoardFeed` keys the figures it holds by the scope they were read under (`scopeKey`: board, version, fallback flag, network name). A read under another key replaces the figures at once, even if the new board is older, resets what had failed for the old scope, closes the stream and opens the one of the new scope. A board of the same scope is still never replaced by an older one. The merge with KI-54 (the heartbeat watchdog) keeps the watchdog for the board's own stream only (known issue WB11-K10). A read that fails after a change keeps the NEW scope's figures as last known and never brings the old scope back. A read that fails before any change keeps the old figures with the old header (truthful: the header names the scope they are of).
4. **The stream follows the scope.** A network screen listens to `GET /api/bff/wall/network-events` (`network-board`, `scope-ended`, the relay's network channel), a screen on its own board to `/api/bff/events`. The route is a wall's only; it names no network (the screen's record does).
5. **The wall network board** is the wall board with the header "Showing: Network, {Network name}" (`ScopeHeader` wall variant: no switch), the heading "{Network name} capacity", the organisation under each service name with the "Your organisation" marker on the viewer's own, `WALL-TILE` kept, no comment, no pending chip, no next-due time, and a paused listing as "?" / "Phone to confirm" / "Not available on the network. Phone to confirm." without a bar or an age line. The wall has no footer sorting line.

### DEC-1234 The network variant of the options filter (G11; TEN-051, TEN-053; DEC-136 item 1, DEC-134 item 8)
Status: accepted.
1. **`FilterNetworkOptions`** (`application/use_cases/filter_network_options.py`) and `GET /network/{network_id}/options?case=<case id>`. Roles: advisor and clinical (the roles that work a case and see a network); every other role is the one 404, with no read. The viewer is checked against the registry (`require_member`), then the three existing network reads give the rows (`NetworkBoardProjector.get_board`, `QueryNetworkDirectory`, `QueryNetworkCriteria`, each in its own read-only network unit), then ONE tenant unit of the advisor's own organisation reads the case, compares and writes the audit entry. No unit holds two scopes. The comparison is `check_hard_criteria` on the shared criteria (built as a `ServiceCriteria` with status current), the status is the board's (worked out at read time), the warnings are the tenant list's own (`status_warnings`, `data_age_warnings`, `criteria_warnings`, "Check age").
2. **Capacity-derived only; never a way to book.** Nothing of the case (age band, district, needs) is passed to a network read, a message or a log: the network is read first with no word of the case, the case is read in the advisor's tenant, and the two meet in memory. A row is the listing's opaque reference, the organisation's display name, the service name, category, status, figure, unit, age of the figure, travel range, why it fits, the checks, the criteria version and review date, and the service line (name and number) when the organisation shared one, and the place when it shared one. No comment, no pending count, no reporter, no tenant, grant or source service id. There is no request, no booking and no clinical escalation behind a row (DEC-136 item 1); the advisor phones the service and records the call in their own case.
3. **Own organisation left out.** The viewer's own organisation's services are in their own list; their rows (the listings whose source tenant is the viewer's) are dropped here, so the two lists never repeat each other.
4. **Fail closed.** A service that shared no criteria, or whose criteria cannot be built into a version, cannot be shown to fit: it is "not suitable: criteria not shared. Phone to confirm.". A paused listing is "not available on the network. Phone to confirm." with nothing else read of it. A case value is never in a reason ("outside criteria"). Not found postcode and out of area are flags; there are no district chips (those are the advisor's own tenant's).
5. **Audit.** One tenant audit entry per read, `use_case=FilterNetworkOptions`, action `R`, entity ids the case only, snapshot `{reference, scope: "network", services: [{ref (the listing's opaque reference), status, number, data_age_seconds, over_by, shown_as, criteria_version | reason code}]}`: what the advisor saw (DEC-035, DEC-042), with no organisation, tenant or service id. Nothing is written in a network scope by a read (the network scope invariants are asserted in the tests).
6. **No new graph statement.** The use case composes registered statements that already carry their scenarios (the case read, the projection reads, the audit append), so no `NamedQuery` was added and `test_tenant_isolation.py` was not affected (not run).
7. **Order.** Travel low end first, none last, then organisation, service, reference: an order, never a rank. Not suitable: organisation, service, reference.
8. **Tests.** Unit: `test_filter_network_options_rules.py` (22). Integration: `test_network_options.py` (26): the three scopes (the case in the advisor's tenant only, the rows from the network, the invariants of the network scope), each member sees the others and never its own, the role matrix over 12 roles (200 for advisor and clinical, 404 for the rest), a non-member, an unclaimed network and an unknown network are the same 404, another tenant's case is a 404, a member who left is refused and its services are no longer offered, closed (409) and incomplete (400) cases, a missing or malformed case reference (400), a process with no options service fails closed (500), travel and the service line when a member has shared a place, the audit entry with opaque references only, nothing of poison text or any tenant id in the answer. The producer projects no place or service line yet (`project_network.py`: `location=None, contact=None`), so a real world's rows have no pin and no number; the tests apply a directory projection to show both.

### DEC-1235 The BFF options route and its one extra key (WB11)
Status: accepted. `GET /api/bff/network/options?networkId=&case=` (advisor and clinical; `allowNetworkId`; `idScoped`). The query holds `networkId` and `case` (the advisor's own case reference `^[A-Za-z0-9_-]{1,64}$`) once each and no other key (a postcode, need or age is a 400 before the back end is asked).
