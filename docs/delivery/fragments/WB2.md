## Decisions

- DEC-1130 **Email goes through Twilio's own Email API, from the tenant's text subaccount** (deployment-plan item 6, the DEC-131 correction). `TwilioEmail` (`adapters/outbound/email_twilio/twilio_email.py`) sends `POST https://comms.twilio.com/v1/Emails` with the Account SID and Auth Token of the tenant's text line (`TenantSenderResolver.email_for` reads the line and its token exactly as `sms_for` does, so a tenant with no active text line has no email, and only the tenant's own secret reference is read). It answers 202 with an operation id, which is the provider message id of the Communication; `map_operation` maps an Operation to the statuses of a text (SCHEDULED and PROCESSING: queued; CANCELED: failed `canceled`; COMPLETED: failed `undelivered` or `failed` when any email failed, so a lost email is never called delivered; else delivered; else sent; else queued) and `operation_update(id)` reads `GET /v1/Emails/Operations/{id}`. 429, 5xx and a lost connection are transient (retried); every other non-202 answer is a `SendFailedError` (credentials, an unverified sender, a bad request: a set-up fault, not retried and not hidden as a refusal). The recipient must be one plain address, the subject one printable line; no address, subject, body or token is logged or put in an error. A new email channel takes provider `twilio` and holds no secret reference of its own; a channel stored before this decision keeps provider `smtp` and still resolves to `SmtpEmail` (expand-only: `ALLOWED_PROVIDERS`, `CHANNEL_PROVIDER` is the provider of a new channel). `plan_channel` makes Twilio email channels. The per-tenant verified sender (a domain identity in the Twilio Console matching the address) stays an onboarding step (class C). **[ASSUMED]** The request body (`from`, `to`, `content.subject/text/html`) and the Operation counts (`counts.delivered` and the like) are the best reading of Twilio's documentation, which could not be fetched from the build session (twilio.com is outside its network); the status words, the 202 and the paths are from the documentation. Both shapes are in `build_body` and `map_operation` alone, and the live check must confirm them before a real tenant sends (H-780).
- DEC-1131 **A phoned figure that contradicts the last text is flagged too (Q10, KI-99).** `differs-from-phoned` runs both ways, under the same reason (no new reason, no migration): a figure that differs from a phoned figure of the last hour (unchanged), and a phoned figure that differs from the last figure the service itself gave in the last hour. "The service itself" is a text, app, link or email report (a confirmation counts: it says the figure again); a feed figure and a phone call are not. Only the latest such figure counts; when two share the last instant, a disagreement with either flags. A phone call after a phone call is the advisor's correction and is not flagged. The lead's list describes the pair: "UCR East: the advisor phoned 6 at 14:20, but the last text said 2 at 14:00."
- DEC-1132 **The live stream can be read, and a whole-board change reaches the wall (KI-54, KI-55).** The stream sends a named `heartbeat` event (`{"changedAt": ...}`, the server's time in UTC) every 15 s in place of a bare comment, so the page can tell an open stream from a dead one: a page that has heard nothing (no heartbeat, no board event) for 45 s (three beats) takes the stream for dead, shows it as paused, closes it and opens a new one after 5 s (which refetches the whole board). A projector message with an explicit null service id becomes `event: board-whole` (`{"changedAt": ...}`); the board projector publishes one after the service message whenever the pressure of the rebuilt board differs from the board it replaced (the banner belongs to no one service), and every message the projector already published with no service id (a criteria approval) now reaches the wall instead of being dropped. A message that merely lacks the service id key is still dropped. The BFF relay forwards both events with the time only. The network stream keeps its comment keep-alive (no screen reads it yet; WB2-5).
- DEC-1133 **A text code is sent by its own consumer** (KI-270; `codes.dispatch`, subscription `code-sender`, `adapters/inbound/workers/code_sender.py`). `RequestTextCode` seals the code and the number (`sealed_code`, `sealed_phone`) to the outbox message id, the bound tenant and the recipient key `code:<phone hash>:<purpose>`, and publishes `SendCode` for a known number and `DiscardCode` for an unknown one (both written alike, H-96). The consumer discards a `DiscardCode` without opening anything; opens a `SendCode` (a six-digit code, a `+447` mobile, the purpose in the key, an `issued_at` with a zone, or the message is refused for good); drops a code older than its ten minutes; texts the K1 wording from the bound tenant's own sender; sends nothing, and does not retry, for a tenant with no text channel. A transient failure raises (the unit rolls back, the bus redelivers; the consumer's marker commits with the unit). It writes no Communication and no audit entry (the request wrote its own, purpose only); no log line holds a code, a number or the text. The topic has a one-hour time to live and no duplicate detection (a redelivery is absorbed by the marker). `infra/servicebus-config.json` and `/home/user/diucs-sb-config/servicebus-config.json` are identical; the emulator container was recreated from it; the topology test names `("codes.dispatch", "code-sender")` as read and declared.
- DEC-1134 **Rules of DEC-1100 as built.** Q8 (KI-7, KI-9): an explicit effective time must be strictly later than the latest figure (equal and earlier are refused; the reply names the latest figure's time); a default time is clamped to one microsecond after the latest figure (KI-8, `domain/rules/effective_time.py`). Q4 (KI-27): the window in which a Y confirms a figure is the larger of the tenant's stale limit and the service's own reporting interval (2 h, 18 h, 24 h), capped at 26 h (`confirmable_age.py`; link access and HandleInboundText share it). Q3 (KI-22): a due time at the closing time counts as inside the hours, for due times only (`prompt_hours.py`). KI-31: a latest figure later than the clock no longer raises. `number_after_prompt` and the prompt judgement are one function (`application/prompt_judgement.py`) for the text and the link (KI-159, KI-160).
- DEC-1135 **Workers.** KI-88: a scheduled message the bus took before a crash is scheduled again with the same message id; the scheduled-work consumer marks an id processed once. KI-89: `ScheduledWorkRepository.save` no longer overwrites a cancel committed between its read and its write. KI-103: each bus call has a ten-second limit; one poison row no longer backs off its tenant (the tenant waits only when the store is down or the whole round published nothing). KI-133: a receipt that beats the send's provider-id write is parked (`ProviderReceipt`, two registered statements, no migration: the label is created on demand and deleted when applied) and applied in the unit that records the send. KI-189: `errorCode` is read back into the Communication. KI-185 (H-46): the sender remembers the receipt of a send the provider accepted (10 000 per process, oldest forgotten first), so a redelivery after a failed commit records it and does not text again. **The memory is the process's**: a redelivery to another process or after a restart can still text twice (H-782). KI-388 (H-137): a prompt for a figure whose service is suspended or gone at send time is settled `failed` with `service-suspended`; an echo or a refusal still goes. KI-139, KI-137: a reminder that cannot be sent (the role ended, no phone) tells the lead, and a report cancels the ladders of every older prompt of the phone.
- DEC-1136 **ResolveReportFlag records a phoned figure through RecordAdvisorPhoned** (KI-287). The figure 0 is told as `not-accepting`, any other as `accepting` (the status follows from the number); the audit entry carries `told` and the `flag_id` the call resolved (`RecordAdvisorPhonedCommand.flag_id`). One open flag for each service and reason is now also kept by the store (`add_report_flag` refuses a second open one with a Conflict; no new statement) and decided by one pure function (`new_flag_reasons`) (KI-101).
- DEC-1137 **The serving process gives the capacity use cases the tenant's zone** (KI-415). `ReportCapacity` and `ConfirmCapacity` took a zone source in the use case, but every route, the link pages and the worker built them without one, so the echo times were London for every tenant. Each now passes `DirectoryZones(container.tenants)`; an architecture test (`test_serving_wiring.py`) fails when one is built without a zone source.
- DEC-1138 **One `UnitOfWorkIdempotency`** (`application/uow_idempotency.py`) replaces the three copies (KI-35, KI-149; one `put` was dead code). A scan keeps it one. The order of authentication and path validation for an invalid service id is pinned by three tests (KI-36). KI-149's second half (the Observation search returns the latest report only) is left as designed: the board and the reporter read the latest figure, and a history read has no consumer (WB2-8).
