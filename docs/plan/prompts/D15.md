**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Create the message catalogue and the capacity message templates (C1 to C11) as pure functions, plus an SMS segment counter. Use cases will call one entry point, `render(...)`, so wording lives in one place and can be checked by tests.

**Read first.**
- `backend/src/diucs/domain/codes.py` (F07): `Channel`.
- `backend/src/diucs/domain/rules/freshness.py` (D05): for the style of pure domain modules.
- `docs/spec/domain-rules.md` section 9 (Messages): wording and the catalogue id table.

**Rules you need.**
- No message ever contains a patient name, full postcode, NHS number or free text. Time fields arrive already formatted as "HH:MM" strings. The `unit` field arrives as the phrase to print (for example "referrals in the next 2 hrs" or "referrals").
- Wording (text channel):
  - C1: `DIUCS: {service}. We have {value} {unit} (as of {as_of}). Confirm or update: {link} Or reply Y, or a new number. By {reply_by}.`
  - C2: `DIUCS: {service}. How many {unit} can you take? Send a number (0 = closed). By {reply_by}.` (exact per-measure phrasing will be approved by IG later)
  - C3: `Thanks. {service}: {value} {unit}, as of {recorded_at}. Next prompt {next_due}.`
  - C4: `Updated: {service} {value} {unit}, as of {recorded_at}. Replaces {replaced}.`
  - C5: `Too late: the {cutoff} cut-off had passed, so {rejected} was not used. New question: {service} has {value} {unit} recorded. Reply Y if right, or send the new number, by {reply_by}.`
  - C6: `Y was used twice already. Please send the number for {service}.`
  - C7 [ASSUMED]: `{service}: {value} is outside the usual range of {low} to {high}. If it is right, send {value} again.`
  - C8 [ASSUMED]: `DIUCS reminder: {service} has not updated. Confirm or update: {link} By {reply_by}.`
  - C9: `DIUCS: {n} services need an update by {reply_by}. A) UCR West 3. B) UCR East 1. Reply Y if both right, or A 4, or B 2.` Items render as `{letter}) {service} {value}`; "both" when 2 items, "all" when more; the example replies use the first two items with value + 1.
  - C10: updated items as `{letter}) {service} updated to {value}.`, waiting items as `{letter}) {service} still needs a reply: Y {letter}, or {letter} and a number.`, prefixed `Thanks. `.
  - C11 [ASSUMED]: `DIUCS: reply Y if the figure is right, or send a number (0 = closed). For a booking, reply CONFIRMED or DECLINE.`
- Email (C1, C2, C8 only): subject `{service}: confirm or update by {reply_by}`; text body and a minimal HTML body with the link as a button-style anchor and the line "The link works once, needs no login, and expires at {reply_by}. This email has no patient information."
- Push (C1, C2, C8 only): subject (title) `{service}: confirm or update`; text `We have {value} {unit} recorded. Reply by {reply_by}.` (C2: `How many {unit} can you take? Reply by {reply_by}.`)
- SMS length: GSM-7 basic set, 160 chars for 1 segment, 153 per segment after; extension characters `^{}\[~]|€` count 2; any non-GSM character switches to UCS-2: 70, then 67 per segment.
