**Goal.** Give the back end one way to talk to Neo4j: a driver factory, a registry of named Cypher queries (only the id ever reaches telemetry, never the text), and an idempotent migration runner for constraints and indexes. Every Neo4j adapter and the test harness build on this.

**Rules you need.**
- Neo4j 5 Community. Do not use Enterprise-only features (node key constraints, role-based access, multiple databases). List in a comment in `migrations.py` what would change on Enterprise. **Open decision:** the production edition and Azure hosting are undecided; nothing here depends on that.
- First migrations, exactly (with `IF NOT EXISTS`, names kept):
  - `CREATE CONSTRAINT resource_id FOR (n:Resource) REQUIRE n.id IS UNIQUE`
  - `CREATE CONSTRAINT identifier_key FOR (n:Identifier) REQUIRE (n.system, n.value) IS UNIQUE`
  - `CREATE CONSTRAINT concept_key FOR (n:Concept) REQUIRE (n.system, n.code) IS UNIQUE`
  - `CREATE INDEX obs_by_service FOR (o:Observation) ON (o.effectiveDateTime)`
  - `CREATE INDEX task_by_status FOR (t:Task) ON (t.status, t.businessStatus)`
  - `CREATE INDEX svc_active FOR (s:HealthcareService) ON (s.active)`
  - `CREATE INDEX phone_hash FOR (p:Practitioner) ON (p.phoneHash)`
  - `CREATE POINT INDEX location_position FOR (l:Location) ON (l.position)`
- Every query has a unique id (for example `Q-SVC-LATEST`) and a mode, `read` or `write`. Registering a duplicate id is an error.
- Applied migrations are recorded as `(:Migration {id, appliedAt})` and skipped next time. Later tasks append migrations; never edit an applied one.
