**Goal.** Consume the `scheduled.work` queue and dispatch each due item to the right use case by its kind, skipping work that was cancelled after it was scheduled, and marking work done in Neo4j.

**Read first.**
- `backend/src/diucs/application/work.py` and `backend/src/diucs/adapters/outbound/graph_store/scheduled_work_repository.py` (P08): `WorkKind`, `ScheduledWork`, `Neo4jScheduledWorkRepository`.
- `backend/src/diucs/application/scheduling.py` (U03) and `backend/src/diucs/adapters/inbound/workers/outbox_relay.py` (I03): the `ScheduleWork` payload and the `ScheduledWorkDue` message the relay delivers. Match both.
- `backend/src/diucs/application/use_cases/missed_report_ladder.py` (U06): the ladder handlers and their command shapes.
- `backend/src/diucs/adapters/inbound/workers/consumer.py` (I04); `backend/tests/support/uow.py` (P06); `backend/src/diucs/bootstrap/container.py` (F08).
- `docs/spec/domain-rules.md` section 1.5 (the ladder).

**Rules you need.**
- Message on `scheduled.work`: `event_type="ScheduledWorkDue"`, payload `{"work_id", "kind", "about_id"}`.
- Load the `ScheduledWork` node by `work_id` through the unit of work. Status `cancelled` or `done` → complete and do nothing (cancel can race with delivery). Not found → `PermanentError`.
- After the handler succeeds, save the work with status `done` in the same unit of work.
- The dispatch table `Mapping[WorkKind, handler]` is built in the composition root. Register the four ladder kinds from U06. Kinds without a handler yet → `PermanentError("no handler for <kind>")`, so they show up in the dead-letter queue rather than being lost.
- This consumer never computes due times; Service Bus delivers on time.

**Build.** `backend/src/diucs/adapters/inbound/scheduler/scheduled_work_consumer.py`: `ScheduledWorkDispatcher(handlers)` with `async __call__(message, uow) -> None` (an I04 handler); `build_scheduled_work_consumer(handlers, uow_factory) -> IdempotentConsumer` named `"scheduler"`. Register the ladder handlers in `bootstrap/container.py`.

**Tests to write first.** Real Neo4j via `uow_factory`; seed `ScheduledWork` nodes with `Neo4jScheduledWorkRepository`; recording stub handlers; read the node back in a fresh unit of work.
1. A `reminder` item with status `scheduled` → the reminder handler is called with that `ScheduledWork`; the stored status is now `done`.
2. Status `cancelled` → no handler call; outcome completed; status still `cancelled`.
3. Unknown `work_id` → dead-letter outcome.
4. A kind with no handler → dead-letter outcome naming the kind; status unchanged.
5. Handler raises `RuntimeError` → retry; the stored status stays `scheduled`.
6. Malformed payload (missing `kind`) → dead-letter.
7. Container: the test profile of `build(...)` exposes a dispatcher with the four ladder kinds registered.

**Tenancy (DEC-130, DEC-131, DEC-132).** This platform is multi-tenant: a tenant is one legal entity and every node carries `tenantId`. Never accept, pass or read a tenant in your code. It is bound once at the edge from the signed token or BFF session, the link-token record, the called number, or the validated message property, and `run_query` adds `tenant`. Every statement you register must write `tenantId: $tenant` on each node it matches, merges or creates; only shared Concept and CodeSystem reference nodes and allowlisted global statements are exempt, and registration fails otherwise. Never take a tenant from a request body, query string or caller-controlled header. Uniqueness is composite (`tenantId` plus the key), including references, idempotency keys and message ids. A unit of work binds exactly one scope. Another organisation's data is reached only through a network projection, never a join. Write a two-tenant test: seed tenants A and B, run your use case or query as A, and assert nothing of B is returned or changed, including a B id given as input (answer as not found). Keep tenant data and secrets out of logs.

**Tenancy for Redis, Service Bus and SMS (DEC-130, DEC-131).** Redis keys, lock names and pub/sub channels get the prefix `diucs:<tenant>:` from the adapter, using the bound tenant; a missing tenant is an error, never a default, and the network board uses its network scope id as the prefix. Every Service Bus message sets `application_properties['tenantId']`; a consumer binds it before opening a unit of work and dead-letters a missing or unknown tenant as PermanentError. Message ids and idempotency markers are unique per tenant. Text and email use the tenant's own Twilio subaccount and sender identity, resolved from tenant config at send time; credentials are secret-store references, never graph properties or log text. Inbound SMS resolves the tenant from `To` plus `AccountSid` before verifying the signature with that subaccount's token; an unknown number gets the fixed empty answer and an id-only log.
