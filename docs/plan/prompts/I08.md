**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Wire the two inbound queues to the application: the reply processor turns each queued text into a `HandleInboundText` call, and the delivery tracker records provider receipts on the matching Communication stored in Neo4j.

**Rules you need.**
- `inbound.replies` payload: `phone_hash`, `text`, `received_at` (ISO UTC), `provider_message_id`. Build the U05 command with `idempotency_key = provider_message_id` and the reporter `Actor` shape U05 expects. A missing field → `PermanentError`.
- The use case owns all behaviour (parsing, policy, replies via the outbox). The processor only translates.
- `inbound.receipts` payload: the I07 status callback fields. Look up the Communication by provider id; unknown id → complete without error (a receipt can arrive before the send is recorded; log the provider id only). Never move a status backwards: `delivered` and `failed` are final.
- Both are `IdempotentConsumer`s named `"reply-processor"` and `"delivery-tracker"`.
- Leave a clear hook for trace context from application properties (O01).

**Build.** `backend/src/diucs/adapters/inbound/workers/reply_processor.py`: `ReplyProcessor(handle_inbound_text)` as an I04 handler. `backend/src/diucs/adapters/inbound/workers/delivery_tracker.py`: `DeliveryTracker()` handler using the unit of work's `communications`. Register both runners in the container behind a `workers` entry point.

**Tests to write first.** Real Neo4j via `uow_factory`; seed Communications with `Neo4jCommunicationRepository`; read back in a fresh unit of work.
1. A reply payload calls a recording `HandleInboundText` stand-in once with the phone hash, text, time and idempotency key.
2. Missing `phone_hash` → dead-letter outcome.
3. The same message delivered twice → the use case runs once; one `Processed` node in Neo4j.
4. One end-to-end case with the real `HandleInboundText` from the test container: seeded service, reporter and open prompt; reply "4" → a capacity Observation with value 4 is stored in Neo4j.
5. Receipt `delivered` for a known provider id → the stored Communication's `deliveryStatus` is `delivered`.
6. Receipt `sent` after `delivered` → stays `delivered`.
7. Receipt for an unknown provider id → completed, no error, nothing written.
8. `failed` with error code → stored as `failed`.
