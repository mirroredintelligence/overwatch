**Goal.** Define the criteria port and implement it on Neo4j: versioned service criteria stored as `Basic` resources with profile ServiceCriteria, one current version per service, and full history kept.

**Read first.**
- `application/ports/outbound/repositories.py` and `graph_store/service_repository.py` (P01): pattern.
- `domain/model/criteria.py` (D20): `ServiceCriteria`. `domain/rules/criteria_workflow.py` (D21): statuses and transitions.
- `graph_store/resource_store.py` (G05), `extensions.py` (G04); `backend/tests/support/` (F10).
- `docs/spec/fhir-data-model.md`: "Criteria (Basic, profile ServiceCriteria)". `docs/spec/domain-rules.md` section 4.2.

**Rules you need.**
- Node labels `Basic:ServiceCriteria`; properties `id, version, status, ageMin, ageMax, postcodeDistricts[], reviewBy, createdAt, changeReason`; `-[:SUBJECT]->(:HealthcareService)`, `-[:ACCEPTS_NEED]->(:Concept)`, `-[:EXCLUDES_NEED]->(:Concept)` (need-category system), `-[:AUTHOR]->(:PractitionerRole)`, `-[:SUPERSEDES]->(:Basic)` to the previous version.
- The service points at its current version: `(:HealthcareService)-[:CURRENT_CRITERIA]->(:Basic)`. Saving a version whose status is `current` moves that relationship in the same transaction.
- Only one version per service may be `current`: an `add` or `save` that would leave two raises `Conflict`. Old versions are never deleted.
- If the G04 registry cannot emit `ACCEPTS_NEED`, `EXCLUDES_NEED`, `SUPERSEDES` or `CURRENT_CRITERIA` from the extensions, write them with named queries right after the resource store `put`, in the same transaction.
- `reviewBy` is a date (`YYYY-MM-DD`); `ageMax` may be absent (no upper limit).

**Build.**
- Port `CriteriaRepository` (async): `current_for_service(service_id) -> ServiceCriteria | None`, `current_for_services(ids) -> dict[str, ServiceCriteria]` (skips services without one), `get(criteria_id)`, `add(criteria)`, `save(criteria)`, `history(service_id) -> list[ServiceCriteria]` newest version first.
- `graph_store/criteria_repository.py`: `Neo4jCriteriaRepository(tx, store)`, pure `criteria_to_fhir` / `criteria_from_fhir`, queries `Q-CRIT-CURRENT`, `Q-CRIT-CURRENT-FOR`, `Q-CRIT-VERSIONS`, `Q-CRIT-SET-CURRENT`.

**Tests to write first.**
1. Unit: `criteria_from_fhir(criteria_to_fhir(c)) == c` for UCR West v3 (age 18+, DT1–DT4, accepts fall-no-injury and frailty, excludes suspected-fracture, head-injury-anticoagulants, iv-therapy, review by 2026-12-12).
2. `assert_round_trip` for v3; `node_props("ServiceCriteria", id=...)["postcodeDistricts"] == ["DT1","DT2","DT3","DT4"]`; the json equals `criteria_to_fhir(c)` apart from `meta`.
3. v3 saved as `current` → `MATCH (:HealthcareService {id:"svc-ucr-west"})-[:CURRENT_CRITERIA]->(c) RETURN c.version` is 3.
4. Add v4 `current` while v3 is current → `Conflict`, nothing written.
5. Add v4 `pending-approval`; save v3 `superseded`; save v4 `current` → `current_for_service` is v4; `CURRENT_CRITERIA` points at v4 only; v4 `SUPERSEDES` v3; `history` is [v4, v3].
6. Accepted and excluded needs are `Concept` nodes shared between versions (`count_nodes("Concept")` does not grow when v4 repeats v3's needs).
7. `current_for_services(["svc-ucr-west", "svc-none"])` has one key; `get("missing")` is `None`.
