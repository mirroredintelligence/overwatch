**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. **The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Define the ports for sending texts, emails and push notifications, and the `Communication` record of every message sent, stored in Neo4j. The senders are recording fakes because they stand in for external providers; the record store is real Neo4j.

**Read first.**
- `backend/src/diucs/domain/codes.py` (F07): `Channel`.
- `adapters/outbound/graph_store/driver.py`, `queries.py`, `migrations.py` (G01).
- `backend/tests/support/` (F10): `write_tx`, `read_tx`, `assert_round_trip`, `count_nodes`.
- `docs/spec/fhir-data-model.md`: "Message record (Communication)"; `docs/spec/architecture.md`, flow F1.

**Rules you need.**
- One `Communication` per message sent, with its delivery status. `payload_text` is the text sent and never contains patient data (the templates guarantee it; do not add other free text).
- Delivery statuses: `queued`, `sent`, `delivered`, `failed`, `received` (inbound).
- Replies are threaded to the prompt they answer through `in_response_to`.
- The recipient is a `PractitionerRole` id, never a phone number. Phone numbers live only in the protected contact store (P16).
- `message_id` holds a catalogue id such as "C1". Annotate it as `str` (the `MessageId` StrEnum from D15 is a `str`), so this task does not depend on D15.
- Stored as `(:Resource:Communication {id, status, sent, received, payloadText, deliveryStatus, providerMessageId, inResponseTo})` with `json` as well, plus `-[:TOPIC]->(:Concept)` (system `https://diucs.example/CodeSystem/message-id`), `-[:MEDIUM]->(:Concept)`, `-[:RECIPIENT]->(:PractitionerRole)`, `-[:ABOUT]->` its subject, `-[:IN_RESPONSE_TO]->(:Communication)`.
- Unique constraint on `Communication.id`; index on `Communication.providerMessageId`.

**Build.**
- `application/ports/outbound/messaging.py`:
  - `SendReceipt(provider_message_id: str, accepted: bool)`.
  - `SmsSender(Protocol)`: `async send(to: str, text: str, message_id: str) -> SendReceipt`.
  - `EmailSender(Protocol)`: `async send(to: str, subject: str, text: str, html: str | None) -> SendReceipt`.
  - `PushSender(Protocol)`: `async send(subscription: dict, title: str, body: str, url: str) -> SendReceipt`.
  - `Communication(id, message_id: str, channel: Channel, recipient_role_id: str | None, about_id: str | None, payload_text: str, sent_at: datetime, delivery_status: str, provider_message_id: str | None = None, in_response_to: str | None = None)`.
  - `CommunicationRepository(Protocol)`: `add`, `get(id)`, `by_provider_id(provider_message_id)`, `set_delivery_status(provider_message_id, status) -> bool`, `latest_prompt_for_phone(role_ids: Collection[str], message_ids: Collection[str]) -> Communication | None` (newest outbound communication to any of those roles whose `message_id` is in the set; the caller resolves a phone to role ids).
- `adapters/testing/recording_senders.py`: `RecordingSmsSender`, `RecordingEmailSender`, `RecordingPushSender`. Each keeps a `sent` list, returns receipts with ids `sms-1`, `sms-2`, and has `fail_next()` making the next send return `accepted=False`.
- `adapters/outbound/graph_store/communication_repository.py`: `Neo4jCommunicationRepository(tx, store)` (`store` is the G05 `ResourceStore`; the record is saved through it), queries `Q-COMM-ADD`, `Q-COMM-GET`, `Q-COMM-BY-PROVIDER`, `Q-COMM-SET-STATUS`, `Q-COMM-LATEST-PROMPT`.

**Tests to write first.**
1. Unit: `RecordingSmsSender.send("07700900123", "hello", "C1")` returns `SendReceipt("sms-1", True)`; after `fail_next()` the next returns `accepted=False`, and the one after is accepted.
2. Unit: email and push fakes record subject/title and body.
3. Integration: `add` then `get` in a fresh session equals the original (`assert_round_trip`).
4. Integration: `set_delivery_status("sms-1", "delivered")` updates the stored node and returns True; an unknown id returns False.
5. Integration: `latest_prompt_for_phone({"role-1", "role-2"}, {"C1", "C9"})` returns the newest matching one and ignores a newer "C3" echo.
