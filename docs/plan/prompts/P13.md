**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Add the registration and scope-list records and ports, implemented on Neo4j: a registration is a Task with code `register-service`; the scope list is one FHIR `List` whose entries point at services that may not have registered yet.

**Read first.**
- `application/ports/outbound/repositories.py`, `graph_store/service_repository.py` (P01): pattern.
- `domain/rules/registration.py` (D22): `RegistrationStatus` transitions, `ApprovalChecks`. `domain/codes.py` (F07): `ScopeFlag`, `ServiceCategory`.
- `graph_store/resource_store.py` (G05); `backend/tests/support/` (F10).
- `docs/spec/fhir-data-model.md`: "Scope list (List)", "Registration (Task, code register-service)". `docs/spec/domain-rules.md` section 6.

**Rules you need.**
- Registration Task: `status` follows Task states, `businessStatus` from registration-status, `authoredOn`, `lastModified`, `focus` the HealthcareService, `requester` the applicant's PractitionerRole, `owner` the reviewer's. The wizard draft is kept as an extension holding JSON (`ext_draftJson`) [ASSUMED]; the four approval checks as extensions `checkAutomatic`, `checkCallback`, `checkScope`, `checkCriteria`. Call-back and scope Provenance records are written by U28, not here.
- Scope list: one `List` with code `scope-list` and a fixed id `scope-list`. Each entry is `(:List)-[:ENTRY {flag, date, reason}]->(:HealthcareService)`, `flag` one of `in-pilot`, `later`, `out-of-scope`. Entries exist before the service registers, so `save_entry` for an unknown service creates a minimal inactive HealthcareService (`active false`, `name`, `category`) through the resource store, and never overwrites an existing service.
- Invitations may only be made for `in-pilot` entries (U24 enforces this; the repository just stores the flag).

**Build.**
- `domain/model/registration.py`: `Registration(id, service_id, status: RegistrationStatus, requester_role_id: str | None, owner_role_id: str | None, created_at, last_modified, submitted_at=None, draft: dict = field(default_factory=dict), checks: ApprovalChecks = ApprovalChecks(False, False, None, False), note: str = "")`; `ScopeEntry(service_id, name, category: ServiceCategory, flag: ScopeFlag, date, reason: str = "")`.
- Ports: `RegistrationRepository` (`add`, `get`, `save`, `list_by_status(status)` ordered by `submitted_at`, `for_service(service_id)` newest first); `ScopeListRepository` (`entries()` sorted by name, `get_entry(service_id)`, `save_entry(entry)`).
- `graph_store/registration_repository.py` (`Neo4jRegistrationRepository(tx, store)`) and `graph_store/scope_list_repository.py` (`Neo4jScopeListRepository(tx, store)`), with pure mapping functions and queries `Q-REG-BY-STATUS`, `Q-REG-FOR-SERVICE`, `Q-SCOPE-ENTRIES`, `Q-SCOPE-UPSERT-ENTRY`.
