**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Add report flags and service flags with their port and Neo4j repository. Report flags are separate records because capacity reports are never edited; service flags (`suspended`, `criteria-overdue`) change what the status rules and the options filter do.

**Read first.**
- `application/ports/outbound/repositories.py`, `graph_store/capacity_repository.py` (P01): Observation nodes the report flags attach to.
- `domain/codes.py` (F07): `ReportFlagReason`. `domain/rules/report_flags.py` (D12).
- `graph_store/resource_store.py` (G05), `queries.py` (G01); `backend/tests/support/` (F10).
- `docs/spec/fhir-data-model.md`: "Service flags (Basic, profile ServiceFlag)" and the `ReportFlag` paragraph under "Platform nodes".

**Rules you need.**
- Report flag: platform node `(:ReportFlag {id, reason, status, outcome, createdAt, resolvedAt, serviceId})-[:ON]->(:Observation)`. Status `open`, then `checked` or `accepted`. Written with named queries, not the resource store.
- Service flag: FHIR `Basic` with profile ServiceFlag, labels `Basic:ServiceFlag`, properties `code` (`suspended` or `criteria-overdue`), `status` (`active` or `inactive`), `reason`, `actor`, `at`; `-[:SUBJECT]->(:HealthcareService)`. Stored through the resource store so its json is canonical. Setting a flag replaces the existing flag with the same code for that service (one node per service and code, versioned by the store).
- A flag never edits the Observation or the HealthcareService.

**Build.**
- `domain/model/flags.py`: `ReportFlag(id, report_id, service_id, reason: ReportFlagReason, status: str, created_at, resolved_at=None, outcome: str | None = None)`; `ServiceFlag(service_id, code: str, active: bool, reason: str, actor_id: str, at)`.
- Port `FlagRepository` (async): `add_report_flag`, `open_report_flags(service_id: str | None = None)` oldest first, `save_report_flag`, `service_flags(service_id)` active only, `set_service_flag(flag)`, `services_with_flag(code) -> set[str]`.
- `graph_store/flag_repository.py`: `Neo4jFlagRepository(tx, store)`, queries `Q-FLAG-REPORT-ADD`, `Q-FLAG-REPORT-OPEN`, `Q-FLAG-REPORT-SAVE`, `Q-FLAG-SERVICE-ACTIVE`, `Q-FLAG-SERVICES-WITH`.

**Tests to write first.**
1. Seed UCR East and a report "obs-1" (via P01's repository). `assert_round_trip` for a report flag `out-of-range-twice` on "obs-1"; an `ON` relationship to the Observation exists.

5. `set_service_flag(suspended, active)` twice → `count_nodes("ServiceFlag")` is 1 and `service_flags` returns it; setting it inactive hides it.

7. The ServiceFlag node json equals its canonical Basic resource apart from `meta`.
