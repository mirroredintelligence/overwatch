**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Store what each COO, ICB or lead user wants to be alerted about, and the alerts themselves, in Neo4j, so the alert pipeline (U33, U34) can find subscribers, record acknowledgements and follow escalation chains.

**Rules you need.**
- The R4B `Subscription` and `SubscriptionTopic` element names are not verified yet, so preferences are stored as a platform node, not a FHIR resource: `(:AlertSubscription {practitionerId, kinds[], notUpdatedHours, quietStart, quietEnd, quietCriticalOnly, ackMinutes, deputyId, dailySummary, weeklySummary, updatedAt})-[:CONTACT]->(:Practitioner)`. One node per practitioner. R12 maps it to FHIR later.
- An alert is a Task with code `acknowledge-alert` through the resource store: `businessStatus` `new`, `acknowledged`, `escalated` or `closed`; `authoredOn`; `focus` the HealthcareService (absent for system pressure); `owner` the Practitioner alerted; extension `alertKind`; `partOf` the previous alert when it is an escalation; extension `escalationDueAt`.
- No patient data in either.

**Build.**
- `domain/model/alerts.py` (new): `AlertSubscription(practitioner_id, preferences: AlertPreferences, deputy_id: str | None, daily_summary: bool, weekly_summary: bool, updated_at)`; `AlertRecord(id, kind: AlertKind, service_id: str | None, owner_practitioner_id, status: str, raised_at, escalation_due_at: datetime | None, part_of_id: str | None, acknowledged_at=None)`.
- Ports: `AlertSubscriptionRepository` (`get_for_practitioner`, `save`, `subscribers_for_kind(kind) -> list[AlertSubscription]`); `AlertRepository` (`add`, `get`, `save`, `open_for_owner(practitioner_id)`, `chain(alert_id) -> list[AlertRecord]` from the root through every `partOf` link, oldest first).
- `graph_store/alert_repository.py`: `Neo4jAlertSubscriptionRepository(tx)`, `Neo4jAlertRepository(tx, store)`, queries `Q-ALERT-SUB-*`, `Q-ALERT-*`. Register both in the unit of work.
