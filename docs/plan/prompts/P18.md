**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. **The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Store clinical advice requests in Neo4j so the clinical queue (U40) survives restarts and shows who has taken what. Free-text notes never enter the graph.

**Read first.**
- `application/ports/outbound/repositories.py`, `unit_of_work.py` (P06): add the repository as unit-of-work attribute `clinical_requests`.
- `domain/rules/clinical_queue.py` (D23): `ClinicalRequest`, `take`, `return_if_idle`.
- `graph_store/resource_store.py` (G05), `case_repository.py` (P02); `backend/tests/support/` (F10, P06).
- `docs/spec/domain-rules.md` section 5.

**Rules you need.**
- A request is a Task with code `clinical-advice-request` [ASSUMED code] through the resource store: `businessStatus` `waiting`, `taken` or `advised`; `priority` `stat` for urgency `now`, `asap` for `within-15-min`; `authoredOn`; `focus` the case ServiceRequest; `requester` the advisor Practitioner; `owner` the clinical advisor once taken; extensions `why`, `takenAt`, `snapshotRef` (the audit record id of the options shown).
- Advice is stored on the same Task as `output`: the choice concept, the optional reason concept, and `noteHandle` (a handle from the protected text store, never the text) plus `advisedAt`.
- Presence (available, busy, away) is not stored here; it lives in the cache as heartbeat keys.
- Queue order: `now` before `within-15-min`, then oldest first.

**Build.**
- `domain/model/clinical.py` (new): `ClinicalAdvice(choice: str, reason: str | None, note_handle: str | None, clinician_id: str, at)`; `ClinicalRequestRecord(request: ClinicalRequest, requester_id: str, why: str, snapshot_ref: str | None, advice: ClinicalAdvice | None = None)`.
- Port `ClinicalRequestRepository` (async): `add`, `get`, `save`, `waiting()` in queue order, `taken_by(clinician_id)` (taken, not advised).
- `graph_store/clinical_request_repository.py`: `Neo4jClinicalRequestRepository(tx, store)`, queries `Q-CLIN-WAITING`, `Q-CLIN-TAKEN-BY`.

**Tests to write first.**
1. Seed a case (P02). `assert_round_trip` for a waiting request (now, "borderline criteria", requested 13:13Z).
2. Requests: within-15-min at 13:08Z, now at 13:13Z, now at 13:10Z → `waiting()` order is 13:10Z, 13:13Z, 13:08Z.
3. Save it taken by "clin-1" at 13:14Z → no longer in `waiting()`; in `taken_by("clin-1")`; the Task has an `OWNER` relationship.
4. Save with advice ("go-ahead", reason "within-criteria", note handle "h-123") → round trip equal; `node_props` shows `businessStatus "advised"` and no property holds note text.
5. Returned to the queue (`return_if_idle`) and saved → back in `waiting()`, owner relationship removed.
6. `get("missing")` is `None`.
