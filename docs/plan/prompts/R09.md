**Rules you need.**
- `POST /fhir/Task` with `code` `booking-request`, `focus` `ServiceRequest/{id}`, `owner` `HealthcareService/{id}` → `RequestBooking`. Role `advisor`. Needs `Idempotency-Key`. 201 with `status: requested`, `businessStatus: requested`, `intent: order`, `identifier` = the booking reference, `restriction.period.end` = reply-by.
- A second open request for the same service → 409 `conflict`, "There is already an open request for this service".
- `GET /fhir/Task/{id}`: `advisor` and `clinical` see everything; `reporter` for the owning service sees the projection (no `focus`, no `for`, REDACTED label); everyone else → 404.
- `PUT` on a booking Task → 405 "Booking status changes only through operations".
- `POST /fhir/Task/{id}/$respond`: parts `decision` (`confirm` or `decline`) and optional `reason`. Role `reporter` for the owning service.
- `$cancel` (advisor; part `reason`), `$withdraw` and `$not-reached` (reporter for the owning service; reason parts). An illegal transition → 409 `business-rule`.
- Status fields come from `to_fhir`, never hand-written. POSTs need `Idempotency-Key`.

**Build.** `backend/src/diucs/adapters/inbound/fhir_rest/routes_bookings.py` and Task mapping in `mapping.py`. Each route maps the request, calls the use case through `uow_factory`, and maps the result back.

7. `$withdraw reason=staffing` on a confirmed booking → `withdrawn`, `statusReason` withdrawn.
8. PUT → 405.
