**Goal.** Expose wall screen pairing over HTTP so a wall display can show a code, a shift lead can connect it, and the display can collect its board-only device token. Routes are thin over the U10 use cases.

**Read first.**
- `backend/src/diucs/application/use_cases/pair_wall_screen.py` (U10): `StartPairing`, `ConfirmPairing`, `ClaimPairing` and their commands and results.
- `backend/src/diucs/adapters/inbound/fhir_rest/app.py`, `errors.py`, `auth.py` (R01, R02).
- `docs/spec/ui-screens.md`, artboard "ScreenPairing"; `docs/spec/domain-rules.md`, section 7.

**Rules you need.**
- The pairing code is 6 digits, shown as "482 913", valid 10 minutes. Only hashes are stored (U10).
- The screen proves it is the same screen with a `screenSecret` returned once by the start call. It travels only in the `X-Screen-Secret` header, never in a URL.
- A wrong code and an expired code get the same refusal: 404 `not-found`, "That code is not valid or has expired."
- Only role `lead` may connect a screen; others get the non-revealing 404.
- JSON routes, not FHIR. The device token is returned once, from the claim call only, and is never logged.

**Build.** `backend/src/diucs/adapters/inbound/fhir_rest/routes_screens.py`, registered in `app.py`:
- `POST /screens/pairing` (no auth) → 201 `{ "pairingId", "code": "482913", "expiresAt", "screenSecret" }`.
- `GET /screens/pairing/{pairingId}` with header `X-Screen-Secret` (no auth) → 200 `{ "status": "waiting" | "paired" | "expired", "deviceToken"?: str }`. `deviceToken` appears only on the first `paired` response. A wrong secret → 404.
- `POST /screens` (role `lead`, `Idempotency-Key` required) body `{ "code", "name", "location" }` → 201 `{ "deviceId", "name", "status": "online" }`. Spaces are removed from `code` before `ConfirmPairing`.
- If `ClaimPairing` cannot report `expired`, add that status to `ClaimPairingResult` in U10's file, with a unit test there.
- Wire the three use cases in `bootstrap/container.py`.

**Tests to write first.** `api_client` with the test clock at 14:02 London.
1. `POST /screens/pairing` → 201 with a 6-digit `code`, `expiresAt` 10 minutes later, non-empty `screenSecret`.
2. `GET` with the right secret before confirmation → `waiting`, no `deviceToken` key.
3. Lead `POST /screens` with `"482 913"` → 201 `online`; `GET` → `paired` with a `deviceToken`; a second `GET` → `paired` without it.
4. `GET` with a wrong secret → 404.
5. Wrong code → 404 with "That code is not valid or has expired."; the same code 11 minutes later → the same 404.
6. Advisor token on `POST /screens` → 404; nothing changed in Neo4j.
7. After 10 minutes with no confirmation, `GET` → `expired`.
8. `POST /screens` without `Idempotency-Key` → 400.
