**Goal.** Let the advisor acknowledge a withdrawn or not-reached booking from the alert, so the 10-minute shift-lead escalation is cancelled.

**Read first.**
- `backend/src/diucs/application/use_cases/withdraw_booking.py` (U21): `AcknowledgeWithdrawal` and its command.
- `backend/src/diucs/adapters/inbound/fhir_rest/routes_bookings.py` (R09): how booking operations are routed and errors mapped.
- `backend/src/diucs/adapters/outbound/graph_store/booking_repository.py` (P02): `Neo4jBookingRepository`.
- `docs/spec/domain-rules.md`, section 3.2.

**Rules you need.**
- `POST /fhir/Task/{id}/$acknowledge`, role `advisor` or `clinical`, `Idempotency-Key` required. An empty `Parameters` body is accepted.
- Booking `withdrawn` → call `AcknowledgeWithdrawal`, which cancels the escalation work through `cancel_work` (U03). Response 200 `Parameters` with `acknowledged` (valueBoolean true) and `acknowledgedAt`.
- Booking `not-reached` → nothing to cancel; still 200 with `acknowledged: true`, so the front end treats both alerts the same.
- Any other status → 409 `business-rule` "Only a withdrawn or not-reached booking can be acknowledged".
- Acknowledging twice → 200 again, with no second audit entry.
- Wrong role or unknown id → the non-revealing 404.

**Build.** Add the operation to `routes_bookings.py`. If `AcknowledgeWithdrawal` rejects `not-reached`, handle that status in the route without calling it.

**Tests to write first.** `api_client`, Docker running. A booking for UCR West confirmed at 14:19 and withdrawn at 14:41.
1. Advisor acknowledges at 14:45 → 200, `acknowledged: true`; the escalation `ScheduledWork` node is `cancelled`.
2. A second acknowledgement → 200; the audit log holds one acknowledgement record.
3. A `not-reached` booking → 200; nothing scheduled or cancelled.
4. A `confirmed` booking → 409 `business-rule`.
5. Reporter token → 404.
6. Missing `Idempotency-Key` → 400.
