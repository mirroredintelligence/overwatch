**Goal.** Expose the consent-based support features over HTTP: a person creates, views and stops a support code; support staff open a shared session with that code (or a lead-approved ticket) and read its event timeline and traces. Routes are thin over O06 and O07.

**Read first.**

- `backend/src/diucs/application/ports/outbound/telemetry_query.py` (O07): session search, events and trace reads, and its fixture fake.
- `backend/src/diucs/adapters/inbound/fhir_rest/app.py`, `errors.py`, `auth.py` (R01, R02).
- `docs/spec/observability.md`, "The support and insight console", "Access" and "Privacy and governance".

**Rules you need.**
- A person sees and manages only their own code and access history. Role `support` may open a session only with a valid code, or with a ticket that a `lead` approved. Engineering sees traces only; product sees aggregates only (not in this task).
- Every open is audited by O06 and shown to the person as "14:02 by [Support role]", never a name.
- Responses carry ids, element ids, route templates, outcomes and timings only. Allowed keys: `kind`, `elementId`, `route`, `outcome`, `durationMs`, `status`, `offsetMs`. Field values and page text are never returned.
- A wrong or expired code → 403 "That code is not valid or has expired." (the same message for both).

**Build.** `backend/src/diucs/adapters/inbound/fhir_rest/routes_support.py`, JSON routes:
- Person: `POST /support/codes` → 201 `{ "code", "expiresAt" }`; `DELETE /support/codes/current` → 204; `GET /support/accesses` → `[{ "openedAt", "role" }]`.
- Support: `POST /support/sessions/open` `{ "supportCode" }` → 200 `{ "sessionId", "expiresAt" }` or 403; `GET /support/sessions?sessionId=&traceId=&reference=&role=&release=&since=` → `{ "items": [...] }` (aggregates only); `POST /support/sessions/{id}/ticket` `{ "ticket" }` → `{ "state": "pending" }`; `GET /support/sessions/{id}/events?filter=all|errors|friction|api|navigation` → `{ "meta", "standout", "events" }`, only while an access is open, else 403; `DELETE /support/sessions/{id}` ends the access; `GET /support/traces/{traceId}` → `{ "name", "totalMs", "spans": [...] }`.
- Lead: `POST /support/tickets/{id}/approve` → `{ "state": "approved" }`.
- Every POST and DELETE needs `Idempotency-Key`.

**Tests to write first.** `api_client`; the O07 telemetry fake with fixtures.
1. A reporter creates a code → `XXXX-XXXX` format; `GET /support/accesses` → `[]`.
2. Support opens with the code → 200 `sessionId`; the reporter's `GET /support/accesses` shows one item with role `support` and no name.
3. Wrong code and expired code → the same 403 message.
4. Events before any open → 403; after open → events whose objects hold only allow-listed keys (a fixture `value` field must not appear).
5. Ticket: `pending`; events still 403; lead approves → events readable.
6. An advisor calling `POST /support/sessions/open` → the non-revealing 404.
7. `DELETE /support/codes/current`, then opening with the old code → 403.
