**Goal.** After this task every integration test runs inside a bound tenant, and the harness knows what a "run" is. Each pytest session has one run identity (owner pid, start time, a short nonce) from which three scope ids derive: a run tenant, a second tenant for cross-tenant tests, and a run network scope. An autouse fixture binds the run tenant around every test under `tests/integration/`, a guard fails any test that leaves another tenant bound, `as_tenant` and `in_tenant` switch tenants inside a test, `uow_factory_a` and `uow_factory_b` hand out units of work bound to the two tenants, and `SequentialIds` can produce tenant-prefixed ids. The harness itself is otherwise unchanged: one Neo4j container per session, the whole-database wipe before each test, `count_nodes` and `node_props` global. Nothing here depends on the statements being stamped; in `warn` mode the bound tenant is simply passed along.

**Why.**
- DEC-130 item 9 and audit E sections 3.2, 6.4, 7.3 step 2: "each run uses a unique tenant". The test side of the seam must land before the generated two-tenant test (TEN-004) and before any repository is converted, so that every integration test already exercises the binding and the first unconverted-statement mistake shows up in a two-tenant test, not in review. It is useful immediately in owned mode (one container per run): it catches a statement that forgets the predicate.

- Plan section 1.5: tenancy-bound tests do not run in parallel on one Neo4j yet. Until every statement stamps `tenantId` a tenant-scoped wipe leaves unstamped nodes behind, and fixed ids collide across runs while the single-property constraints exist. So the wipe stays global and the container stays one per run in this task; the scoped wipe, attached mode and parallel runs are TEN-033 to TEN-035.
- Audit A section 4 and E 4.4: `SequentialIds` yields `id-1`, `id-2` in every instance, so two tenants, two tests or two runs all create `id-1`. **Rules you need.**

*1. The run identity: `backend/tests/support/tenancy.py`.*
- `@dataclass(frozen=True, slots=True) class RunIdentity` with `pid: int`, `started: int` (seconds since the epoch) and `nonce: str` (four lower-case hexadecimal characters). Properties: `token` is `f"{base36(pid)}-{base36(started)}-{nonce}"` where `base36` writes lower-case digits `0-9a-z` with no padding (`0` for zero); `tenant_id` is `"tt-" + token`; `other_tenant_id` is `tenant_id + "-b"`; `network_id` is `"net-" + token`. The longest possible value (pid up to 2**22, started up to 2**36) is 24 characters, so every id is a valid `ScopeId` of its kind (`tt-...` and `...-b` tenants, `net-...` network) and never starts with `net-` unless it is the network.
- `new_run_identity(*, pid: int | None = None, now: int | None = None, nonce: str | None = None) -> RunIdentity`: defaults are `os.getpid()`, `int(time.time())` and `secrets.token_hex(2)`.
- `parse_run_id(scope_value: str) -> RunIdentity | None`: the inverse, for the orphan sweeper of TEN-033. It accepts exactly the three shapes above (tenant, tenant with the `-b` suffix, network) and returns `None` for anything else (including `default`, a `tt-` value that does not decode, and the right shape with a bad nonce). The owner's liveness check is TEN-033's business, not yours.
- `class TenantLeak(AssertionError)` and the constant `LEAK_MESSAGE = "the bound tenant changed during the test: something bound another tenant and did not reset it"`. `assert_bound_to(expected: str | ScopeId) -> None` raises `TenantLeak(LEAK_MESSAGE)` when `current_scope_or_none()` is not that scope (including when it is unbound); the message never contains a tenant id.
- `as_tenant(tenant: str | ScopeId)`: a context manager that binds that tenant for the block with the production `bind_scope` and restores the previous binding on exit and on exception; an invalid id raises `ScopeInvalid`. `in_tenant(tenant)`: a decorator for `async def` helper functions that runs the helper inside `as_tenant(tenant)`; decorating anything that is not a coroutine function raises `TypeError` at decoration time. Neither introduces a second context variable: they use the production binder, so the code under test sees exactly what production code sees.
- `guard_async_test(fn, expected)`: wraps a coroutine function so that, after the body has finished (in the test's own task context) and only if the body did not raise, it calls `assert_bound_to(expected)`; if the body raised, its exception propagates unchanged (a leak never masks the real failure). The conftest uses it, see below.
