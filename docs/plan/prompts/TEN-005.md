**Why.**
- Audit A section 1: today's isolation is an accident of global uniqueness (`Resource.id` unique across the whole database, singletons for the audit head and the scope list); the instant uniqueness becomes composite every unmodified statement is a leak, so the constraints must exist before any repository is converted and before any second tenant. DEC-130 item 7: uniqueness becomes composite (`tenantId` plus the key); Neo4j Community 5.26 enforces composite uniqueness (lesson L126, which corrects the claim in L90). DEC-134 item 10 (the audit chain: each scope has its own; the existing chain becomes the default tenant's) and item 11 (no production data exists, only development data: a migration assigns existing nodes to a default tenant, and the generated test proves nothing is left unstamped).
- Audit A section 3.1 gives the table of every constraint and index and what it becomes, and the rules that make the swap safe: (1) create the composite constraint first, then backfill, then drop the old one (both can coexist, an unstamped node does not violate a composite constraint; dropping first leaves a window with no uniqueness and about twelve `ConstraintError` to `Conflict` mappings in the repositories depend on a constraint existing); (2) a composite constraint ignores a node whose `tenantId` is null, and Community has no existence constraint, so an invariant query is the only catch; (3) a schema statement and a data write cannot share a transaction (lesson L8; the runner already uses one transaction per statement and one for the record); (4) applied migrations are never edited; (5) the backfill needs a parameter (the default tenant id) and a loop, so the entry type becomes an object with parameters and loop steps, and `CALL { } IN TRANSACTIONS` is not available inside `execute_write`, so loop with `LIMIT` in separate managed transactions as `tests/support/neo4j.py` already does for the wipe.
- DEC-134 item 13 and audit A section 4 (the case reference row): the case reference is unique per tenant among open cases and reusable after close. Migration 0022 is lifetime-unique over 9,000 values, which is stricter than the rule and which a busy organisation exhausts. The replacement is a constraint on an open-only property (plan section 6). The old constraint stays until TEN-032, so reuse after close becomes possible then.
