**Rules you need.**

*Identifiers and scope kinds*
- A network id is a scope id of kind network: it starts `net-` and is 6 to 31 characters, `net-[a-z0-9][a-z0-9-]{1,26}`. A tenant id (TEN-006's format, `[a-z0-9][a-z0-9-]{1,30}`, checked with its `check_tenant_id`) may not start `net-`. `Network.owner_tenant_id`, `NetworkMembership.member_tenant_id`, `Grant.grantor_tenant_id`, `Listing.source_tenant_id` must be tenant ids; `network_id` fields must be network ids. A tenant id in a network field, or the reverse, is `ValidationFailed` (hazard H-N13). The prefix is TEN-006's `RESERVED_TENANT_PREFIX` (`"net-"`), imported into `network.py` as `NETWORK_ID_PREFIX`; `network.py` adds the network id pattern `net-[a-z0-9][a-z0-9-]{1,26}` (the same pattern as TEN-001's `ScopeId.network`); a parity test asserts that TEN-001's `ScopeId.network` and `check_network_id` accept and refuse the same strings over a fixed corpus plus a Hypothesis text strategy, and that `NETWORK_ID_PREFIX == NETWORK_PREFIX` of `application/tenancy.py`.
- Account references (`account_ref`) are opaque ids from the verified identity (an HMAC, never a name or e-mail): pattern `[A-Za-z0-9_-]{8,128}`. Do not run the patient-data guard on them: a long hex string can contain ten digits and would be refused at random. Display names (`Network.name`) and the agreement `reference` do pass `find_patient_data` and a length cap.

- `NetworkStatus`: `draft`, `active`, `suspended`, `closed`. `MembershipStatus`: `invited`, `active`, `left`, `removed`. `MembershipRole`: `owner`, `member`. `MembershipEndReason`: `left`, `removed`.
- `ListingStatus`: `pending`, `admitted`, `declined`, `suspended`, `withdrawn`. `ListingReason`: `outside-area`, `outside-pilot`, `duplicate-listing`, `data-quality`, `safety-concern`, `agreement-breach`, `other`. A reason is a code, never free text.

- `Network(id, name, owner_tenant_id, status: NetworkStatus, agreement: Agreement | None, created_at, closed_at: datetime | None)`. `name` 1 to 80 characters. `active` requires an agreement; `closed` requires `closed_at`.

Invariants: `invited` has no `joined_at`, `left_at` or `end_reason`; `active` has `joined_at` and nothing after; `left` has `end_reason = left` and `left_at`; `removed` has `end_reason = removed` and `left_at`; `left_at` is not before `joined_at`; `left_at` is the leave date that history is marked with.

Invariants: `proposed` has no approval; `grantor-approved` has only the grantor's; `owner-approved` only the owner's; `approved` has both; `declined`, `ended`, `lapsed` and `superseded` have `ended_at` and the others do not; `ended` also has `ended_by_account_ref`; `version >= 1`; `allowlist_version >= 1`; `effective_to` is `None` or after `effective_from`; all datetimes timezone-aware (stored as given, compared as UTC); a grant never supersedes itself.

The key of a listing is `(network_id, source_tenant_id, source_service_id)`.

*Network and membership lifecycle* (functions in `network.py`)
- Network transitions: `draft -> active`, `active -> suspended`, `suspended -> active`, `active | suspended -> closed`. Nothing leaves `closed`. `activate_network(network, agreement, now)` needs the agreement.
- `owner_membership(network, id, now)` returns the owner's membership, `active`, role `owner`, `accepted_agreement = network.agreement`. The owner is a tenant like any other and may also project (DEC-132 item 2; plan section 7).
- `invite_member(network, existing_memberships, *, id, tenant_id, now)`: the network must be `active`; `tenant_id` is not already a member in a non-closed membership (`invited` or `active`) of this network (`Conflict`, no detail about the other record). A tenant whose earlier membership is `left` or `removed` may be invited again: that is a new membership with a new id; the closed row is never reopened and never edited, so its leave date stays (DEC-132 item 6; audit F 4.5; audit A proposed reopening the row, F's rule wins because it keeps history without a second record).
- `accept_membership(network, membership, *, agreement, account_ref, now)`: `invited -> active`, `joined_at = now`, `accepted_agreement` must equal the network's current agreement version (`Conflict` otherwise).
- `end_membership(network, membership, *, reason, now)`: `active -> left` (reason `left`) or `active | invited -> removed` (reason `removed`). The owner's membership cannot end while `network.owner_tenant_id` equals its tenant (`NotAllowed`). `joined_at` is kept; `left_at = now`. Ending twice returns the record unchanged (idempotent for retries) only when the reason is the same; a different reason on a closed membership is `InvalidTransition`.
- `was_member_at(membership, instant)`: `joined_at <= instant` and (`left_at` is `None` or `instant < left_at`). History queries use it; live reads use `status is active`.
- `is_agreement_behind(network, membership)`: the network has an agreement and the member's accepted version is missing or lower (hazard H-N09).
- No `suspended` membership status: a suspended tenant simply stops reporting and its projections turn not-updated by staleness (TEN-073 stops its relay, TEN-057 degrades the read); record this in your DEC. Leave takes effect at the commit; a notice period (audit F's `leaving` state) is not modelled (record this in your DEC; TEN-077 may schedule the call).

*Grant rules* (`rules/grant.py`)
- `propose_grant(...)` builds a `proposed` grant, version 1, no approvals. `scope` and `purpose` must be exact `GrantScope` / `GrantPurpose` members (a string `"capacity"` is refused). `effective_from` may not be earlier than `proposed_at`: sharing is never backdated. `effective_to` is optional.
- Transition table (everything else is `InvalidTransition`; `transition_grant(current, target)` mirrors `transition_registration`):
  - `proposed -> grantor-approved | owner-approved | declined | ended | lapsed`
  - `grantor-approved -> approved | declined | ended | lapsed`
  - `owner-approved -> approved | declined | ended | lapsed`
  - `approved -> ended | lapsed | superseded`
  - `declined`, `ended`, `lapsed`, `superseded` are terminal.
- `approve_grant(grant, *, approver, approver_tenant_id, network_owner_tenant_id, account_ref, now)`: the grantor's approval needs `approver_tenant_id == grant.grantor_tenant_id`; the owner's needs `approver_tenant_id == network_owner_tenant_id`; otherwise `NotAllowed` (the role check, that the person is an administrator, belongs to the use case). The two approvals may come in either order. When the grantor tenant is the owner tenant, the two approvals still need two different `account_ref` values (two people); the same account twice is `Conflict`. A second approval by the same party: the same `account_ref` returns the grant unchanged (idempotent retry), a different one is `Conflict`. Approving does not change the version.
- `decline_grant(...)`: either party, only before `approved`; the result is `declined` with `ended_at`.
- `end_grant(grant, *, by_tenant_id, account_ref, now)`: only the grantor tenant (`NotAllowed` for anyone else, including the network owner: the owner can remove a member, not end a member's grant). Allowed from any non-terminal status. The result is `ended` with `ended_at = now` and `ended_by_account_ref`; approvals and the window are untouched. Ending an `ended` grant returns it unchanged; ending a `declined`, `lapsed` or `superseded` grant is `InvalidTransition`. Ending stops future sharing only: nothing here deletes or edits what was shared (DEC-132 item 3).
- `lapse_grant(grant, *, now)`: any non-terminal status to `lapsed` with `ended_at = now`. `lapse_grants_for_member(grants, membership, *, now)` returns lapsed copies of every non-terminal grant of that member in that network and leaves terminal grants and other members' grants alone.
- `revise_grant(current, *, new_id, effective_from, effective_to, agreement, allowlist_version, proposed_by_account_ref, now)`: only from `approved`. The result is a new `proposed` grant, `version = current.version + 1`, `supersedes_id = current.id`, same network, grantor, scope and purpose (a different scope is a different grant). A higher `allowlist_version` than the current one needs an `agreement.version` higher than the current grant's (widening needs a new agreement version, audit F 4.6). Dates follow the `propose_grant` rule.
- `supersede_grant(old, successor, *, now)`: `old` is `approved`, `successor` is `approved` with `version = old.version + 1` and `supersedes_id = old.id`, and `now >= successor.effective_from` (`Conflict` before that). The result is `old` as `superseded` with `ended_at = now` and `effective_to = successor.effective_from`. If `old.effective_to` is set and earlier than `successor.effective_from` there would be a gap: `Conflict`. No overlap: `is_effective(old, t)` is false from `successor.effective_from`.
- `is_effective(grant, now)`: `status is approved`, both approvals present, `ended_at is None`, `effective_from <= now` and (`effective_to is None or now < effective_to`). Start inclusive, end exclusive, compared as UTC. This is the only definition of "effective"; nothing stores it.
- `was_effective_at(grant, instant)`: for history. Both approvals present, status in `approved`, `ended`, `lapsed`, `superseded`, `effective_from <= instant < end_instant(grant)` where `end_instant` is the earlier of `effective_to` and `ended_at` (when set). A grant that never had both approvals was never effective.
- `effective_grant(grants, *, network_id, grantor_tenant_id, scope, now)`: the effective grant with the highest version for that member and scope, or `None`.
- `may_project(grant, membership, now)`: true only when `is_effective(grant, now)`, `membership.status is active`, `membership.left_at is None`, `membership.member_tenant_id == grant.grantor_tenant_id` and `membership.network_id == grant.network_id`. This is the gate the projector's apply step uses (TEN-054); every condition has its own red test.
- `end_reason(grant)` maps `ended`, `lapsed`, `superseded` to the `GrantEndReason` of the same name and everything else to `None`.

*Listing rules* (`rules/listing.py`)
- Transitions: `pending -> admitted | declined | withdrawn`; `admitted -> suspended | withdrawn`; `suspended -> admitted | withdrawn`; `declined` and `withdrawn` are terminal. A declined provider asks again with a new listing (`request_listing`), never by reopening.
- `request_listing(existing, membership, *, id, network_id, source_service_id, now)`: the membership must be `active` and in this network; the source tenant is the membership's tenant; a listing for the same key that is `pending`, `admitted` or `suspended` makes it `Conflict` (hazard H-N12: two listings of one real service by one member).
- Only the network owner tenant admits, declines, suspends and reinstates (`NotAllowed` for the source tenant and for any other tenant); `decline` and `suspend` need a `ListingReason`. Only the source tenant withdraws its own listing. `withdraw_for_leave(listings, membership, *, now)` withdraws every non-terminal listing of a member that has left.
- `listing_presentation(status)`: `admitted -> shown`, `suspended -> unavailable`, anything else `hidden` (`ListingPresentation` enum in `listing.py`: `shown`, `unavailable`, `hidden`). A suspended listing stops projecting and reads as unavailable (DEC-136 item 3).
- `visible_scopes(listing, membership, grants, now) -> frozenset[GrantScope]`: empty unless the listing is `admitted`, the membership is `active` and belongs to the listing's tenant and network, and then exactly the scopes for which some grant of that member in that network `is_effective`. `shows_on_board(...)` is true only when both `directory` and `capacity` are in that set (a tile needs the directory data for its name and hours and the capacity data for its figure; `criteria` is optional). Nothing here ranks or scores a member.
- `may_project_listing(listing, membership, grant, now)`: the listing is `admitted` and `may_project(grant, membership, now)`.

*Failure modes and fail-closed rules.* Any enum argument that is not exactly its enum, any naive datetime, any tenant id in a network field (or the reverse), any scope or purpose outside the lists, any approval by the wrong tenant, any status that does not match its approvals: raise, never default. No function reads the clock, a global or an environment value. Error messages name the field, not the value.
