*The projection message and the documented exception.* One more class in the module, deliberately not an event:

```python
PROJECTION_WORK: Final = "projection.work"     # queue name; registered in QUEUES by TEN-055
PAYLOAD_EXCEPTIONS: Final[frozenset[str]] = frozenset({"ProjectionRequested"})

ProjectionValue = str | int | float | bool | None | tuple[str | int | float | bool, ...]

@dataclass(frozen=True, slots=True)
class ProjectionRequested:
    message_type: ClassVar[str] = "ProjectionRequested"
    network_id: str
    source_tenant_id: str
    grant_id: str
    grant_version: int
    kind: GrantScope
    source_service_id: str
    source_version: int
    allowlist_version: int
    body: Mapping[str, ProjectionValue]
    at: datetime
```

- It is not in the `DomainEvent` union, not in `_TOPIC_BY_CLASS`, and `from_payload("ProjectionRequested", ...)` raises `ValidationFailed` like any unknown event type. It is decoded only through `ProjectionRequested.decode(payload)`; `to_payload()` returns the same shape as the events, with `body` as a JSON object (tuples as lists; `decode` turns lists back into tuples).
- The module docstring states the exception in these words or very near them: "Exception to the ids, counts and codes rule. `ProjectionRequested` is the only message in this module whose payload carries more than identifiers, counts and codes: its `body` holds the allowlisted projection fields (service name, category, location district, opening hours, service-level contact, capacity figures, criteria). The allowlist is `diucs.domain.rules.projection.ALLOWLIST`; this module checks the shape of the body, `diucs.application.projection` checks its keys against the allowlist before the message is published and again before it is applied." A test asserts `"ProjectionRequested"` and `"allowlist"` appear in `events.__doc__`.
- The body's structure is checked here as a floor, whatever the allowlist says: at most 40 keys; each key matches `[a-z][a-z0-9_]{0,39}`; no key equals, after lower-casing and removing `_` and `-`, any member of `FORBIDDEN_FIELDS` normalised the same way (so `patient_name`, `PatientName`-style spellings and `nhs_number` are all refused); every value is a scalar, `None`, or a flat tuple of at most 50 scalars (no nested mapping, no bytes, no datetime object: timestamps are ISO strings with `Z`, times `HH:MM:SS`, dates `YYYY-MM-DD`); floats are finite; every string is at most 200 characters and `find_patient_data(value) == []`.
- `kind`, `grant_version`, `allowlist_version`, `source_version` are validated like the event fields. `body` may be empty (a retraction or an ids-only request is valid). Whether the producer sends the DTO in `body` (audit B) or sends ids and lets the consumer rebuild it in two units of work (audits A and C, plan TEN-054) is TEN-054 and TEN-055's decision; both fit this interface. The consumer takes the source scope and the network from the message properties, never from this payload (DEC-130 item 6); the payload fields are for cross-checking only.
- A class-level audit test keeps the exception bounded (see test 9).
