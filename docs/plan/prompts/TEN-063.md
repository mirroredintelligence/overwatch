You are a software engineer picking up one task in the `overwatch` repository (product name: DIUCS capacity, the design system calls it Community Overwatch). You have no memory of any earlier work. Everything you need is in this prompt and in the repository.

**The product.** DIUCS capacity helps NHS urgent-care single points of access (SPOA) see, in one place, how many referrals or beds each community service, ward or virtual ward can take now. Services report by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The platform is multi-tenant (DEC-130 to DEC-136).** Each organisation is a tenant: the legal entity and data controller for its own data. Every graph node carries `tenantId`; the tenant is bound once, from a verified source, never from a request body; `run_query` adds it; a unit of work binds exactly one scope; another organisation's record reads as not found. Organisations collaborate in a Network: sharing happens only through a Grant (grantor tenant, network, scope, purpose, dates, approved by the grantor's administrator and by the network owner) and a read-only, allowlisted projection that a worker copies from the member's scope into the network scope. The network view is read-only and capacity-derived. Patient-level data (bookings, cases, communications, reporters, audit) never crosses. Read `.claude/skills/diucs-delivery/references/multi-tenancy.md` before you start. No code, test, fixture, template or message you write names a place, an organisation or a telephone number; names come from configuration.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

*1. Rules (section 1 of the document, stated as rules, each with its source DEC or audit reference).*
- Same layout and same components as the tenant view. The only differences are the scope header, an organisation label on every row, the removal of everything private to a tenant (pending counts, booking state, reporter contact, case data, comment lines, next-due times, audit), and no write action.
- The network view is a list of facts. It never sorts or colours organisations as better or worse, shows no score or rank, and says "Not ranked" where order could be read as rank. Order is category, then organisation name, then service name.
- No booking, no "Request booking", no "I phoned", no "They declined", no clinical escalation, no alert subscription on a network row. The only action on a network row is to read the service line number and phone the service.
- The browser holds and sends no tenant, network or scope identifier. A viewer chooses between two fixed routes (`/` area routes for their organisation, `/network/...` for the network); the back end binds the scope from the route and the verified token. - Figures come from each organisation's own reports and age from the report time. A stale figure is shown as Not updated or Last known with the time of the last figure; the network board never shows an old figure as current.
- Network rows carry no comment line (the free-text comment is not shared), no "next due", no pending chip and no reporter information.
