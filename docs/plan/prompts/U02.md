**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Goal.** Build `ConfirmCapacity`: a "Y" that says the figure on record is still right. It is stored as its own report type, derived from the latest number, and capped at two in a row.

**Read first.**
- `application/use_cases/report_capacity.py` (U01): reuse `record_report`.
- `application/idempotency.py` (P15); `domain/rules/reply_policy.py` (D11) for `MAX_CONSECUTIVE_CONFIRMS`; `domain/model/capacity.py` (D02).
- `adapters/outbound/graph_store/capacity_repository.py` (P01): how reports and `derived_from` are stored (`DERIVED_FROM` relationship).
- `backend/tests/support/` (F10, P06) and `tests/integration/application/conftest.py` (U01 seed helpers).

**Rules you need.**
- A confirmation is a new `CapacityReport` with `report_type=ReportType.CONFIRMED`, the same `value` as the latest report, and `derived_from=<latest report id>`.
- At most `MAX_CONSECUTIVE_CONFIRMS = 2` confirmations in a row, counted since the last `number` report. A third is refused and nothing is written.
- No report on record: nothing to confirm, refuse.
- Same echo, status recompute and events as U01. A text Y gets C3 with the confirmed value.
- `$confirm-capacity` (R05) and the link page's "Yes, still 3" (L01) also call this use case.

**Build.**
- `application/use_cases/confirm_capacity.py`: `ConfirmCapacityCommand(idempotency_key, actor, service_id, source: ReportSource, performer_role_id: str | None = None)`; `ConfirmCapacityResult` = `ReportCapacityResult` fields plus `confirmed_value: int`; `ConfirmCapacity(uow_factory, clock, ids, idempotency)`.
- In `domain/errors.py` add `ConfirmLimitReached(DomainError)` and `NothingToConfirm(DomainError)`.
- Audit `use_case="ConfirmCapacity"`, snapshot `{"value", "derived_from", "consecutive": n}`.
- If P01's `CapacityRepository` has no efficient way to count trailing confirmations, add `trailing_confirmations(service_id) -> int` to the Protocol and to `Neo4jCapacityRepository` with a named query `Q-CAP-TRAILING-CONFIRMS`, with its own round-trip test.

**Tests to write first.** `tests/integration/application/test_confirm_capacity.py`, real Neo4j via `uow_factory`, UCR West seeded with a number report of 3 at 08:15 London.
1. Confirm at 10:05: the newest stored report is type confirmed, value 3, and `node_props` shows a `DERIVED_FROM` link to the 08:15 report; result `confirmed_value=3`.
2. Second confirm at 12:05 accepted.
3. Third confirm → `ConfirmLimitReached`; still exactly two confirmed reports; no new `OutboxMessage` nodes from the failed call.
4. number, Y, Y, number, Y → the last Y is accepted.
5. No reports at all → `NothingToConfirm`.
6. Text source with performer role → C3 echo "UCR West: 3 referrals".
7. Confirm for an overdue service: `StatusChanged` from not-updated is written.
8. Replay of the same key returns the first result; one audit record.
