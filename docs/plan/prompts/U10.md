**Goal.** Build wall screen pairing. A wall display shows a 6-digit code; a shift lead types it into the admin page with a screen name; the display then collects a device token that can read only the board. Devices are stored in Neo4j.

**Read first.**
- `domain/rules/tokens.py` (D26): `new_pairing_code`, `format_pairing_code`, `new_link_token`, `hash_token`, `LinkTokenRecord`, `check_link`.
- `ports/outbound/tokens.py`, `graph_store/link_token_repository.py`, `adapters/testing/fixed_secrets.py` (P10).
- `ports/outbound/identity.py` (P16): check whether a `DeviceRegistry` port exists.
- `application/idempotency.py` (P15); `docs/spec/fhir-data-model.md` "People, devices and consent" (Device node); `docs/spec/ui-screens.md` "ScreenPairing".

**Rules you need.**
- Code: 6 digits shown "482 913", valid 10 minutes, only its hash stored.
- The screen holds a random secret from the start call, so only that screen can collect the token.
- Device token ≥128 bits, generated on collection, returned once, stored only as a hash. Device type wall-display. It never sees patient data.
- Only role `lead` may confirm. Wrong and expired codes get the same refusal.

**Build.**
- If no `DeviceRegistry` exists, add it to `ports/outbound/identity.py` (`get(device_id)`, `save(device)`, `find_by_token_hash(hash)`) with a `Device` dataclass (`id, status, name, location, device_type, token_hash`) and `adapters/outbound/graph_store/device_registry.py` `Neo4jDeviceRegistry` writing `:Resource:Device` nodes (properties `id, status, deviceName, tokenHash`, `TYPE` to a wall-display concept). Expose it on the unit of work as `devices` (edit P06's `UnitOfWork` Protocol and `Neo4jUnitOfWork`). Cover it with an `assert_round_trip` test.
- `application/use_cases/pair_wall_screen.py`: `StartPairing(uow_factory, clock, ids, rng, secret_store)` → `StartPairingResult(pairing_id, code_display, screen_secret, expires_at)`, storing two link-token records (purposes `wall-pairing`, `wall-pairing-secret`, `about_id=pairing_id`, 10 minutes). `ConfirmPairing` with `ConfirmPairingCommand(idempotency_key, actor, code, screen_name, location: str | None)`: burns the code, saves a device "paired-unclaimed", audit `use_case="PairWallScreen"`. `ClaimPairing` with `ClaimPairingCommand(pairing_id, screen_secret)` → `ClaimPairingResult(status: "waiting" | "paired", device_token: str | None)`: when paired and unclaimed, generate the token, store its hash, status "active", burn the secret; later claims return "paired" with no token.

**Tests to write first.** `tests/integration/application/test_pair_wall_screen.py`, real Neo4j, seeded `random.Random`, `FixedClock`, `FixedSecretStore`.
1. Start returns "ddd ddd"; no `LinkToken` node property equals the code or the secret.
2. Claim before confirmation → "waiting".
3. Lead confirms → a `Device` node "paired-unclaimed" named "[Screen name]" read back through a fresh unit of work; one audit record.
4. Claim with the right secret → token; device "active"; stored `tokenHash` equals `hash_token(token, secret)`; `find_by_token_hash` returns it.
5. A second claim → no token.
6. Wrong code, or right code after 10 minutes → `NotAllowed`, same message; advisor confirming → `NotAllowed`; wrong secret → `NotAllowed`; nothing written on refusal.
