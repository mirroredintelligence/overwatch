**Goal.** Build the text-code use cases used by registration, reporter set-up and re-verification: request a 6-digit code for a phone, then verify it.

**Read first.**
- `domain/rules/identity_policy.py` (D27): `CODE_VALID_FOR`, `CODE_MAX_TRIES`, `CODE_RESEND_AFTER`, `code_attempt`.
- `application/ports/outbound/identity.py` (P16): `CodeSender`, `CodeStore` and its `InMemoryCodeStore` fake (codes are short-lived and live in Redis in production, so this is one of the allowed fakes).
- `application/ports/outbound/tokens.py` (P10): `PhoneHasher`, `SecretStore`, `FixedSecretStore`.
- `PersonRepository.find_by_phone_hash` (P03) and `RegistrationRepository` (P13), both Neo4j; `backend/tests/support/uow.py` (P06).
- `docs/spec/domain-rules.md` section 7; `docs/spec/ui-screens.md` artboards "OnboardReporter1" screens 3-4 and "RegisterFlow1" screen 1.

**Rules you need.**
- Code: 6 digits, valid 10 minutes, 5 wrong tries then the code is dead and a new one is needed. A new code may be requested 60 seconds [ASSUMED] after the last; earlier requests return `retry_after_seconds` and send nothing.
- Only a hash of the code is stored (HMAC with the secret named `code-hmac`).
- A code is sent only to a known number: an open invitation's phone hash or a registered practitioner's phone hash, both looked up in Neo4j. For an unknown number return exactly the same result as success and send nothing, so callers cannot probe which numbers exist.
- Purposes: `register`, `setup`, `reverify`, `pin-reset`, `new-device`.
- K1 wording: "DIUCS: your code is 482913. It works for 10 minutes. Do not share it." [ASSUMED; confirm with IG].
- On success, return who the phone belongs to (practitioner id and/or invitation id) and mark the code used.
- Audit entries record purpose and outcome only, never the code or the number.

**Build.** `backend/src/diucs/application/use_cases/text_code.py`:
- `RequestTextCodeCommand(idempotency_key, phone: str, purpose: str)` → `RequestTextCodeResult(sent: bool, retry_after_seconds: int)` (`sent` is True for unknown numbers too).
- `VerifyTextCodeCommand(phone, purpose, code)` → `VerifyTextCodeResult(ok: bool, tries_left: int, needs_new_code: bool, practitioner_id: str | None, invitation_id: str | None, verified_at: datetime | None)`.
- `RequestTextCode(code_store, code_sender, phone_hasher, uow_factory, secret_store, clock, rng)` and `VerifyTextCode(code_store, phone_hasher, uow_factory, secret_store, clock)`.

**Tests to write first.** In `backend/tests/integration/application/test_text_code.py`. Seed an invitation for "07700 900456" in Neo4j through the P13 repository and a unit of work.
1. Known invited phone: one code sent through `RecordingSmsSender`; the code store holds a hash, not the digits.
2. Unknown phone: result identical to test 1, nothing sent.
3. Second request after 30 s returns `retry_after_seconds=30` and sends nothing; after 61 s a new code is sent.
4. Correct code within 10 minutes: `ok=True` with the invitation id; reusing it fails.
5. Correct code after 10 min 1 s: `ok=False, needs_new_code=True`.
6. Five wrong codes: `tries_left=0, needs_new_code=True`; then even the right code fails.
7. Audit nodes read from Neo4j contain neither the code nor the phone digits.

## Tenancy amendment

Until a decision in `decisions.md` records that tenancy is enforced, follow the transitional rule in `.claude/skills/diucs-delivery/references/multi-tenancy.md`: all Cypher through `run_query`, list tenant-pending statements in the evidence, and add a Tenant isolation section.

**Tenancy (DEC-130, DEC-131, DEC-132).** This platform is multi-tenant: a tenant is one legal entity and every node carries `tenantId`. Never accept, pass or read a tenant in your code. It is bound once at the edge from the signed token or BFF session, the link-token record, the called number, or the validated message property, and `run_query` adds `tenant`. Every statement you register must write `tenantId: $tenant` on each node it matches, merges or creates; only shared Concept and CodeSystem reference nodes and allowlisted global statements are exempt, and registration fails otherwise. Never take a tenant from a request body, query string or caller-controlled header. Uniqueness is composite (`tenantId` plus the key), including references, idempotency keys and message ids. A unit of work binds exactly one scope. Another organisation's data is reached only through a network projection, never a join. Write a two-tenant test: seed tenants A and B, run your use case or query as A, and assert nothing of B is returned or changed, including a B id given as input (answer as not found). Keep tenant data and secrets out of logs.

**Tenancy for Redis, Service Bus and SMS (DEC-130, DEC-131).** Redis keys, lock names and pub/sub channels get the prefix `diucs:<tenant>:` from the adapter, using the bound tenant; a missing tenant is an error, never a default, and the network board uses its network scope id as the prefix. Every Service Bus message sets `application_properties['tenantId']`; a consumer binds it before opening a unit of work and dead-letters a missing or unknown tenant as PermanentError. Message ids and idempotency markers are unique per tenant. Text and email use the tenant's own Twilio subaccount and sender identity, resolved from tenant config at send time; credentials are secret-store references, never graph properties or log text. Inbound SMS resolves the tenant from `To` plus `AccountSid` before verifying the signature with that subaccount's token; an unknown number gets the fixed empty answer and an id-only log. Tests use a fake secret store and prove a tenant-A message never reaches tenant B's channel, queue handler or number.

**Task-specific change (from the tenancy audit):** Code request and verify are unauthenticated: tenant comes from the invitation token, device or session, never a phone alone; codes are sent from the tenant's number (DEC-131 item 5) and keyed `code:<phone_hash>:<purpose>` under the tenant prefix; unknown-number responses must not reveal which tenants know the number.
