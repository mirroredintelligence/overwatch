**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Rules you need.**
- Approve: lead only; `in-review` → `approved`. Refused with `NotAllowed` listing `missing_for_approval` until automatic checks are ok, the call-back is confirmed, scope is `in-pilot`, and criteria version 1 is approved by a clinical lead. On approval queue the test prompt (I3) by the registered channel and record when.
- Send back: note required (short, no patient information); `in-review` → `needs-changes`; the note goes to the applicant by their channel.
- Not approve: reason required; `in-review` → `not-approved`. Reopen: `not-approved` → `in-review` (lead).
- Test answered: only an answer from the registered phone hash (or the registered app device) counts; records `test_answered_at`.
- Set live: lead only; requires `approved` and a test answer. Then `live`, `HealthcareService.active=true`, `Location.status="active"`, `Organization.active=true` (new resource versions through the resource store), schedule the first `prompt-due` work at the next due time with `schedule_work`, emit `registration.events/RegistrationApproved`. The board picks the service up on its next read.
- The registration record lists each step with who and when (submitted, call-back, scope, criteria, test answered, set live), for export.

**Tests to write first.** In `tests/integration/application/test_approve_registration.py`, seeding an `in-review` registration and its draft resources in Neo4j:
1. Approve with the call-back missing raises `NotAllowed` whose message names "Call-back done"; stored status unchanged.
2. All checks done: stored status `approved`; an I3 outbox message.
3. A test answer from another phone hash is ignored; from the registered phone it stores `test_answered_at`.
4. Set live before the test answer raises `NotAllowed`. After it: the HealthcareService node has `active=true` and a new `ResourceVersion`; a `ScheduledWork` node of kind `prompt-due` at the next due time and a `ScheduleWork` outbox message; `RegistrationApproved` outbox node.
5. Send back without a note fails; with a note it stores `needs-changes` and queues the note.
6. Not approve, then reopen: back to `in-review`.
7. The registration record lists the six steps in time order, read from Neo4j.
