**Goal.** Give the front end one typed way to call the back end's FHIR R4B API from server code (BFF route handlers and Server Components), plus the MSW test setup every later front-end task uses.

**Read first.**
- `frontend/package.json`, `frontend/vitest.config.ts` (from F03): how tests run and where a setup file goes.
- `docs/spec/contracts.md`, sections "HTTP surface (backend)" and "Front end": the paths, media type and the `fhirFetch` signature you must match.
- `docs/spec/architecture.md`, section "FHIR R4B interface": errors, ETag, Idempotency-Key.

**Rules you need.**
- Base URL comes from the server-only env var `DIUCS_FHIR_BASE_URL` (for example `http://localhost:8000/fhir`). Throw a clear error at call time if it is missing. Never expose it to the browser (no `NEXT_PUBLIC_`).
- Every request sends `Accept: application/fhir+json; fhirVersion=4.3`. Requests with a body also send `Content-Type: application/fhir+json; fhirVersion=4.3`.
- Optional headers: `Authorization: Bearer <token>`, `Idempotency-Key`, `If-Match` (an ETag such as `W/"3"`).
- Every request carries a W3C `traceparent` header (`00-<32 hex>-<16 hex>-01`). Pass one through if the caller gives it, otherwise generate one.
- A 2xx returns `{ data, etag }` where `etag` is the `ETag` response header if present. 204 returns `data: undefined`.
- A non-2xx throws `FhirError(status, outcome)`. If the body is an OperationOutcome, use it. Otherwise synthesise `{ resourceType: "OperationOutcome", issue: [{ severity: "error", code: "exception", diagnostics: "HTTP <status>" }] }`. Network failures throw `FhirError(503, …code "transient")`.
- `toBffError(error)` in `lib/bff/errors.ts` turns any thrown error into a `Response` with JSON `{ code, message }` and the same status (500 for unknown errors). It returns the issue `code` and a fixed plain message per status, never the back end's diagnostics text.

**Build.**
- `lib/fhir/client.ts`: `fhirFetch<T>(path, init)` and `class FhirError extends Error { status; outcome }`. `init`: `{ method?, body?, token?, idempotencyKey?, ifMatch?, traceparent? }`. `body` is JSON-serialised.
- `lib/fhir/types.ts`: minimal R4B types you need now: `Resource`, `OperationOutcome`, `Parameters` (with `parameter[].name`, `value*`, `part[]`), `Bundle<T>`, `Reference`, `Coding`, `CodeableConcept`. Hand-written, small; later tasks extend them.
- `lib/fhir/traceparent.ts`: `newTraceparent()` using `crypto.getRandomValues`.
- `lib/bff/errors.ts`: `toBffError`.
- `test/msw/server.ts` (`setupServer()` from `msw/node`), `test/msw/handlers/index.ts` (empty array export), `test/setup.ts` registering `server.listen({ onUnhandledRequest: "error" })`, `resetHandlers`, `close`; wire it in `vitest.config.ts`.

**Tests to write first.**
1. GET `/HealthcareService/a1` with MSW returning a resource and `ETag: W/"2"` → `data.id === "a1"`, `etag === 'W/"2"'`, request had the FHIR `Accept` header.
2. POST with body, token, idempotency key and ifMatch → MSW handler asserts all four headers and the JSON body.
3. `traceparent` header matches `/^00-[0-9a-f]{32}-[0-9a-f]{16}-01$/`; a supplied one is passed unchanged.
4. 404 with an OperationOutcome body → throws `FhirError` with status 404 and that outcome.
5. 500 with HTML body → `FhirError` with synthesised outcome.
6. Fetch rejects (network) → `FhirError` status 503.
7. Missing `DIUCS_FHIR_BASE_URL` → throws an error naming the variable.
8. `toBffError(new FhirError(409, outcome-with-diagnostics "secret"))` → status 409, body has `code` from the issue and does not contain "secret".
