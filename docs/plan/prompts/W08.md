**The product.** DIUCS capacity helps an NHS urgent-care single point of access (SPOA) in Dorset. Community services, wards and virtual wards report how many referrals or beds they can take, by text message, a one-tap link, or an installed web app. Call advisors see a live wall board and a filtered list of services that fit a patient's needs, then ask a service to take the patient by text and wait for CONFIRMED. Shift leads chase late reports, register services and keep criteria current. Nothing anywhere holds a patient name or NHS number.

**The architecture.** Hexagonal. A Python back end (package `diucs` in `backend/src/diucs`) with four layers: `domain` (pure rules, no I/O), `application` (use cases and ports defined as `typing.Protocol`), `adapters` (inbound: FHIR REST, SMS webhook, link pages, workers; outbound: Neo4j, Redis, Azure Service Bus, SMS, email, push; `adapters/testing`: fakes for external providers only) and `bootstrap` (settings and the composition root). Dependencies point inwards only. A Next.js front end in `frontend/` talks only to its own `/api/bff/*` route handlers, which call the back end's FHIR R4B API. Neo4j is the only database, Redis is a cache, Azure Service Bus carries messages and scheduled work.

**Rules you need.**
- Back end (R15): `POST /screens/pairing` → `{ pairingId, code: "482913", expiresAt, screenSecret }`; `GET /screens/pairing/{pairingId}` with header `X-Screen-Secret: <screenSecret>` → `{ status: "waiting" | "paired" | "expired", deviceToken? }`. The BFF keeps `pairingId` and `screenSecret` in an HTTP-only cookie; neither the secret nor the device token ever reaches browser JavaScript; `POST /screens` (lead token) `{ code, name, location? }` → `{ deviceId, name, status: "online" }`, 404 when the code is unknown or expired.
- BFF: `POST /api/bff/screens/pairing` (no session); `GET /api/bff/screens/pairing/[id]`: when paired, it creates a session `{ role: "wall", services: [], sub: deviceId, device: deviceId, backendToken: deviceToken }` and returns `{ status: "paired" }` (the device token never reaches the browser); `POST /api/bff/screens` (role lead, CSRF).
- Screen page `/screen/pair`: "DIUCS capacity wall screen", the code shown as "482 913" in very large digits, "Enter this code in the admin page to connect this screen.", "Waiting to be connected · code works for 10 minutes". Poll every 3 seconds. When paired, go to `/screen`. When expired, request a new code automatically and show it.
- Admin page `/lead/screens/new` at `app/(lead)/lead/screens/new/page.tsx` (every lead page sits under `/lead` so route groups cannot clash). Copy: "Add a wall screen"; fields "Code shown on the screen" (Required), "Screen name" (Required), "Where it is" (Optional); note "This screen will show capacity only. It never shows patient information."; buttons "Connect screen", "Cancel".
- Errors: empty code "Enter the code shown on the screen"; not 6 digits after removing spaces "The code has 6 numbers"; 404 "That code is not valid or has expired. Check the screen for a new code."; empty name "Enter a name for the screen".
- Connected: "Screen connected", "[Screen name] is now showing the live board.", rows Status "Online, updated 14:12", Shows "Capacity only. No patient information.", If it goes offline "The board shows Last known and says so"; buttons "Add another screen", "Done".
- Until W09 exists, the admin page checks `getSession()` itself and sends anyone who is not a lead to `/sign-in`.
- data-el: `WALL-PAIR-CODE`, `LEAD-SCREEN-CODE-FIELD`, `LEAD-SCREEN-CONNECT-BTN`.
